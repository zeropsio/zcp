## Universal voice rules (all surfaces)

- **V1 — porter-clones-and-runs framing + friendly-developer voice.** Voice addresses someone who clones the apps repo and deploys, not someone learning the framework or the platform. "This app uses Y for Z" / "this showcases how to integrate X with Zerops". Never "we chose", "during scaffold", "the agent owns", "the recipe author". **Voice depth**: write like a developer explaining the setup to a colleague, not like a platform engineer writing a runbook. Lead with what something IS in plain English; reach for mechanism precision (yaml field names, technical jargon) only when the porter needs it to avoid a trap. Worked **BAD** (sim apidev tier-3 db comment): *"Single-instance Postgres — restoring from snapshot still means downtime, the rehearsal-grade tradeoff. `minFreeRamGB: 0.25` absorbs query-burst spikes; bump verticalAutoscaling.minRam when working-set growth pushes query latency past your stage SLO."* Worked **GOOD** (jetstream tier-3 db comment): *"Deploy single node PostgreSQL database, used by the Laravel app to store data. Automatic, encrypted backups are enabled by default."* Worked **MIX** (the right blend): *"Single-node PostgreSQL — used by the api codebase to store items + job records. Snapshots-only durability at this rehearsal tier; bump `verticalAutoscaling.minRam` if your stage workload pushes query latency."* Plain-English service intro first, framework/recipe bridge second, scaling/yaml precision last and only when porter-actionable.
- **V2 — names what the recipe IS, not what it could be.** Names the specific framework + feature set. Never "any Node HTTP framework", "if you use Symfony instead", "alternative starter kits". Jetstream README has zero alternatives across 291 lines.
- **V3 — link text references real concepts the porter recognizes**, not internal corpus slugs verbalized. Use `[Laravel documentation]`, `[zsc health-check]`, `[multi-container setups]`, `[step-by-step NestJS tutorial]`. **Slug-stem test (HARD)**: the link text MUST NOT contain any of these corpus-slug stems, even when wrapped in English with a Zerops/managed prefix or a "reference"/"guide"/"service" suffix: `rolling-deploys`, `init-commands`, `managed-services-*` (any service name suffix), `env-var-model`, `env-var-references`, `env-var-secrets`, `subdomain-access`, `object-storage`, `build-from-git`, `cross-service-env-var`, `dev-loop`, `app-version-id`, `init-container`. Forbidden shapes (run-32 + run-33 evolution): `[managed NATS service]`, `[Zerops object-storage service]`, `[Zerops env-var model]`, `[Zerops rolling-deploys guide]`, `[Zerops rolling-deploys reference]`, `[per-deploy init-commands reference]`, `[Zerops managed NATS service]`, `[S3-compatible object storage on Zerops]` (still leaks `object-storage`). Test for the principle: read the link text aloud — does it sound like a porter naming what they want to learn (`[multi-container setups]`, `[zero-downtime deploys]`), or like an engine internal vocabulary leaking out (`[Zerops <slug-stem> reference]`)? The first passes; the second fails. Replace with a porter-recognized concept (`[zero-downtime deploys with multi-container setups]`, `[S3-compatible storage on the MinIO backend]`) or in-body completion.
- **V4 — porter-actionable phrasings tied to platform signal.** "Feel free to change this", "Configure this to use real SMTP sinks", "Bump … once …". Imperatives + customization invitations.
- **V5 — defer broad platform concepts to docs when inline explanation would sprawl.** Conditional, not mandatory. Use `https://docs.zerops.io/...` references when sprawl is likely; inline when 1-2 sentences cover it.
- **V6 — no authoring vocabulary in any porter-facing surface.** Forbidden tokens: `zerops_dev_server`, `zsc noop`, "the agent", "scaffold", "feature phase", "recipe author", "record-fact". (The yaml `start: zsc noop --silent` directive is legitimate yaml content; surrounding comments must not adopt authoring voice.)

## Recipe-repo root README

The root README is a **6-tier entry point**, not a documentation surface.

- **R1 — short** (~28 lines). Single intro paragraph + deploy button + cover image + 6-tier link list + catalog punt + Discord. Drop exact line count; keep "short entry-point" principle.
- **R2 — intro paragraph names framework + what it demonstrates.** One sentence; optionally a "with all the essentials …" follow-on naming features.
- **R3 — 6 tier links uniform shape.** `**TIER NAME** [[info]](path) — [[deploy with one click]](url)`. Both `[info]` and `[deploy]` for every tier.
- **R4 — trailing punt to recipe catalog**, not in-line teaching: "For more advanced examples see all PHP recipes on Zerops."
- **R5 — trailing Discord invite.**
- **R6 — no IG, no KB, no architecture description, no managed-services list.** Root README has zero `## H2` content sections. Zero exceptions.

## Tier README

Tier READMEs are short delta descriptions.

- **T1 — short** (Stage README is 7 lines; AI Agent is 8). Title + one-sentence framing + 2-3 line intro extract. Drop exact line count; keep "short delta" principle.
- **T2 — intro extract names this tier's DELTA**, not its absolute spec. "Stage uses the same configuration as production, but runs on the lowest scaling settings."
- **T3 — title links back to recipe deploy page**: `[recipe-name (info + deploy)](recipe-url)`.
- **T4 — no tier-promotion narrative.** Tier README does NOT say "promote to tier 5 when X" or frame the current tier as a stepping-stone.

## Tier import.yaml

- **TY1 — top-of-file comment mirrors tier README intro extract.** Length varies (2-4 lines). Drop exact line count; keep "mirror the intro" principle.
- **TY2 — per-service comment leads with plain-English service introduction; scaling math comes second.** 1-2 sentences naming SERVICE ROLE in this recipe in friendly-developer voice. Worked **GOOD** (jetstream stage db): *"Deploy single node PostgreSQL database, used by the Laravel app to store data. Automatic, encrypted backups are enabled by default."* / *"Spin up Valkey in single-node mode. Valkey is an open-source Redis-compatible key/value storage for caching, sessions, queues, etc."* — names what the service IS, names what it's USED FOR, adds a porter-relevant fact (encrypted backups; framework bridge). Worked **BAD** (sim stage db): *"Single-instance Postgres — restoring from snapshot still means downtime, the rehearsal-grade tradeoff. `minFreeRamGB: 0.25` absorbs query-burst spikes; bump verticalAutoscaling.minRam when working-set growth pushes query latency past your stage SLO."* — leads with operational tradeoff + scaling math, never names what the service IS in plain language. Worked **MIX** (the right shape): *"Single-node PostgreSQL — used by the api codebase to store items + job logs. Snapshots-only durability at this rehearsal tier; bump `verticalAutoscaling.minRam` if your stage workload pushes query latency."*
- **TY3 — optional services explicitly marked optional.** "Feel free to remove this service, if you wish to stage-test your app with as-close-as-possible production setup."
- **TY4 — comments name framework-canonical effects.** "Used by the Laravel app to store data" — not "consumed by the api codebase". Bridge frameworks where useful: "Valkey is an open-source Redis-compatible key/value storage for caching, sessions, queues, etc." helps a porter who knows Redis but not Valkey.
- **TY5 — service ordering with `priority` justified in human terms when non-default.** "Set higher priority for databases and object-storage, because the app depends on those services." (jetstream)

## Apps-repo Integration Guide (per codebase)

- **IG1 — IG #1 is engine-emitted "Add `zerops.yaml`" with verbatim yaml.** Agent does not author this slot.
- **IG2 — IG #2-#N are short by default; long only when the mechanism is non-obvious.** Jetstream's IG #2 is 4 lines (composer require + edit one file). #3 is 2 lines. #4 is one paragraph. **Each step does ONE thing.** Lead with the change — what the porter does — and explain only enough to make the change actionable. Long teaching is justified ONLY when the porter would otherwise miss a non-obvious mechanism (SIGTERM-drain semantics, build-time-bake timing, framework-specific subtleties). Worked **OK-but-too-long** (sim apidev IG #2 — Bind 0.0.0.0): 18 lines explaining VXLAN routing + a paragraph on PORT/run.ports sync, for a 2-line code change. The change itself is `app.listen(port, '0.0.0.0')` reading PORT from env — a 5-line IG would carry it. Worked **GOOD** (jetstream IG #2 — Add Support For Object Storage): "add `league/flysystem-aws-s3-v3` to your composer.json or `composer require league/flysystem-aws-s3-v3 ^3.0`. Update the Jetstream config `config/jetstream.php` to use `s3`." That's it — the porter does the change; the WHY is implicit (object storage is in the recipe). Showcase items are 1-3 paragraphs. Candidate items running 19-70 lines violate this hard. **Test**: if your IG body's paragraphs explain platform mechanism the porter doesn't need to make the change, trim them.
- **IG3 — IG body links to specific apps-repo GitHub lines** when relevant. Concrete, ungeneralized: `[league/flysystem-aws-s3-v3](https://github.com/.../composer.json#L14)`.
- **IG4 — no cross-framework adapt-paths.** Stays recipe-framework-specific. Zero "if you use Symfony" / "any PHP framework" / "Express's `app.set`" / "Fastify uses `trustProxy: true`" / "Webpack/Astro/SvelteKit/Next/Nuxt". Jetstream has zero across 291 lines.
- **IG5 — frame each IG step around a concrete change.** Concept explanation must serve that change. Step #2 = "Add Support For Object Storage" → `composer require league/flysystem-aws-s3-v3` + edit `config/jetstream.php#L79`. Concept explanation lives in the step's body insofar as it justifies the change.
- **IG6 — every IG step must be Zerops-forced or recipe-feature-specific platform integration.** The IG teaches the porter what THEY have to do because they're using Zerops. Steps that explain a recipe-internal convention the cloning porter inherits already-done — or generic best practices the porter would do on AWS/Heroku/Render too — teach nothing. **Test**: "must the porter take this action because Zerops changes the deployment/runtime contract, or because this recipe ships a feature whose platform integration the porter must complete (e.g. swap Mailpit for real SMTP)?" If neither: it doesn't belong in the IG. Worked **FAIL**: "Alias cross-service env vars under your own keys" — generic best practice; the cloned recipe yaml already aliases them; would be done on any platform with cross-service config. Worked **PASS**: "Strip the build-output prefix when shipping to `base: static`" — Zerops-forced (`dist/~` strip-prefix syntax is a Zerops yaml mechanism; static runtime serves from a fixed docroot). Worked **PASS**: "Setup Production Mailer" (jetstream IG#4) — recipe-feature-specific; Mailpit is a recipe choice the porter must replace with real SMTP credentials before going to production. Generic best practices belong in yaml comments or KB, not the IG. **Recipe-internal conventions belong nowhere on porter-facing surfaces** (the porter inherits the convention by cloning; teaching them about it is dead weight).

## Apps-repo zerops.yaml

- **Y1 — top-of-file block comment names the setup pattern.** ~5 lines. Names what each setup IS and what each does.
- **Y2 — comments are causal, porter-relevant, plain-English-first.** Mechanism + effect + (often) so-what — but **lead with what the field IS in plain language**, not with a mechanism summary. Examples: "Stderr logging sends output to Zerops runtime log viewer — no log files to manage or rotate." / "Readiness check gates the traffic switch — new containers must answer HTTP 200 before the L7 balancer routes to them. This enables zero-downtime deploys." Field-name documentation alone is insufficient; platform-engineering-jargon-first is also insufficient. Worked **BAD** (sim apidev env-var comment): *"Own-key aliases of the platform's cross-service injects — application code reads its own names so a managed service swap is a yaml-only edit. Same pattern across every service block below."* That's mechanism-first, jargon-heavy ("Own-key aliases", "yaml-only edit"). Worked **MIX** (the right shape): *"Cross-service env vars renamed under your own keys — DB_HOST, NATS_HOST, etc. The api code reads only these names, so swapping a managed service later is a one-line yaml edit, no app rebuild. Same pattern in every service block below."* Plain-English ("renamed", "one-line yaml edit, no app rebuild") replaces jargon ("aliases", "yaml-only edit"); concrete examples ("DB_HOST, NATS_HOST") ground the abstraction.
- **Y3 — comments explain framework requirements that motivate Zerops choices.** "PHP applications generally require a web server such as Nginx or Apache HTTP server."
- **Y4 — URL deferrals are conditional**, not mandatory. Use when inline explanation would sprawl; inline when 1-2 sentences suffice. Showcase has zero URL deferrals; jetstream has 4. Both are acceptable.
- **Y5 — comments name PORTER-customization opportunities.** "Feel free to change this value to your own custom domain, after setting up the domain access."
- **Y6 — init-command comments explain WHEN they run + WHY**, not what they are.
- **Y7 — comments use framework-canonical terms only.** Forbidden: authoring tokens (V6 list).
- **Y8 — no tier-promotion narrative inside yaml comments.**
- **Y9 — no decision-tree-of-alternatives in comments.** Comments name THIS choice, not "alternatives are X, Y, Z and we picked W because…".
- **Y10 — each setup section opens with a 1-2 line preamble** naming the setup's PURPOSE + what it optimizes for + (when applicable) what it deliberately omits. Showcase: `# Worker — background job processor consuming from Redis queue. Same codebase as the app, different entry point. No HTTP traffic — no healthCheck, readinessCheck, or documentRoot.`
- **Y11 — when a setup has fewer fields than its sibling, comments name the deliberate absences.** "No HTTP traffic — no healthCheck, readinessCheck, or documentRoot."
- **Y12 — skip `extends:`; repeat envVariables inline per setup.** When inline repetition spans many lines, lead with a one-line note: showcase shape `# Same service wiring as prod — only mode flags differ.` Recipe yaml is read top-to-bottom by porter; flat yaml beats DRY-with-indirection.
- **Y13 — group causal command sequences with one block comment above the list, not per-command inline.** For `buildCommands` and `initCommands`, write a single block comment narrating the whole sequence in causal order rather than annotating each command separately. Showcase line 82-92 carries the canonical shape: one block comment names the build sequence's purpose + ordering rationale; individual commands stay un-annotated.
- **Y15 — comment when non-obvious; self-documenting field names skip.** Density target: **≤40%** comment lines per yaml file (jetstream golden = 36%; showcase ≈ 40%; run-32 candidate = 56-63%; run-33 candidate = 50-59% — none at golden bar). Self-documenting field names need NO comment: `hostname:`, `type:`, `buildFromGit:`, `enableSubdomainAccess: true`, `mode: HA`, `priority:`, plain `${db_*}` / `${cache_*}` env mappings (the pattern is comment-worthy ONCE per file, not per-mapping). Comment when: the field's value is non-default, the choice has a Zerops-forced reason, the field deserves a porter-customization invitation (Y5), or the comment names mechanism+effect+so-what (Y2/Y14). Worked **FAIL**: `# hostname: api` over `hostname: api` — the field name self-documents. Worked **PASS** (jetstream): comments cluster around `setups:` block boundaries + `envVariables` blocks + non-default `documentRoot`/`prepareCommands`; many fields have NO comment because the field name says it.

## Factuality guards (cross-surface)

- **F-SUBDOMAIN — Zerops subdomains do NOT rotate.** Platform-issued subdomains (`<host>-${zeropsSubdomainHost}.prg1.zerops.app`) are stable per service identity for the lifetime of the service. Fail any prose that claims subdomains rotate, are randomized after deploy, change between deploys, or are otherwise unstable. Common overclaim phrases (case-insensitive): `\bdomain[s]? rotate\b`, `\bsubdomain[s]? (rotate|change|randomize)\b`, `\b(rotate|rotates|rotated|rotation) (the|each|every|after) (subdomain|domain|deploy|build)\b`, `\bunstable\b.*\bsubdomain\b`. Rewrite to describe the URL as a porter-controlled value (custom domain swaps it; `enableSubdomainAccess: false` turns it off; otherwise it's stable).
- **F-BOXDRAWING — yaml comments must be ASCII-only.** Box-drawing characters (codepoints U+2500..U+257F and block elements U+2580..U+259F) render as visual separators in some terminals but ship mojibake in others. Recipe yamls go through copy-paste-share lifecycles; ASCII survives, box-drawing doesn't. Concrete pattern to scan against: `[─-╿▀-▟]`. Replace with a single blank line or a `# section ---` ASCII line if the author wants visual grouping. Per-recipe TEACH-channel reference: `principles/yaml-comment-style.md` (loaded at codebase-content + env-content; the positive-shape atom at the authoring phase). This rule is the refinement-pass backstop for fragments that slipped past the authoring phases (parent absorption, copy from a prior recipe, etc.).
- **F-XSURF-REF — yaml comments state mechanism+reason in one breath; no cross-surface deferrals.** Spec §"Surface 7" voice (per-codebase `zerops.yaml`) is mechanism+reason in one breath; the comment must stand on its own. Spec §"Surface 3" voice (tier `import.yaml`) forbids cross-tier shifts in service-block comments (*"Cross-tier shifts surface implicitly through the contrast between adjacent tier yamls — neither reference recipe writes 'promote to tier N when…' sentences in service blocks. Don't."*). **Scan** every yaml comment line in every `zerops.yaml` AND every tier `import.yaml` for: (a) **cross-codebase-surface deferral** — `see IG #<digit>`, `see KB`, `the pattern is taught in`, `live below`, `at the field site`, `the full mechanism is documented at`, `for the rationale see` (the run-42 audit's `cross-surface-reference` defect-class shape); (b) **cross-tier deferral** — `Same as tier <digit>`, `see tier <digit>`, `as tier <digit> ships`, `promote to tier <digit>`, `unchanged from tier <digit>` (the run-42 audit's tier 1/2 "Same as tier 0" framing). FAIL: rewrite the comment to state mechanism+reason in one breath, self-contained — let the inter-surface / cross-tier contrast surface implicitly. Run-42 dogfood evidence: apidev/zerops.yaml:47-48 said *"See IG #5 for the schema-ownership rationale this pair enforces"* (Surface 7 deferral); :63-64 said *"The pattern is taught in IG #3; the specific shapes worth flagging at the field site live below"* (Surface 7 deferral); environments/1 + environments/2 import.yaml service blocks led with *"Same dev / stage pair as tier 0"* before the per-service detail (Surface 3 cross-tier deferral). Cross-references: spec §"Surface 7" / spec §"Surface 3" + `briefs/codebase-content/synthesis_workflow.md` §"Yaml comments stand alone".
- **F-EXECONCE-SEMANTICS — `zsc execOnce` key shape must match command lifetime.** `${appVersionId}` keys resolve to a fresh string every deploy and re-run every deploy (per-deploy gate — right for idempotent migrations); static keys (`bootstrap-seed`, `<slug>.<op>.v1`) run once per service lifetime (right for non-idempotent seeds). The per-codebase `principles/init-commands-model.md` atom is the authority; this rule is the refinement-pass backstop. **Scan**: walk every `zsc execOnce <key>` line in every zerops.yaml (`buildCommands` / `initCommands` / `runCommands`). FAIL when the key contains `${appVersionId}` AND the command tail is `seed` / `init` / `bootstrap`-style (`seed.js`/`seed.ts`/`init.js`/`bootstrap.js`/`prisma db seed`/`artisan db:seed`/`scout:import`-style — non-idempotent one-shots) AND any adjacent yaml comment OR README/IG/KB prose claims once-only / never-re-runs semantics (`once-only`, `never re-runs`, `skips if the key already ran`, `runs once per service lifetime`, `stamps each key`, `per-deploy ledger.*skips`, `idempotent` paired with `${appVersionId}` over a non-idempotent op). Either the key shape needs to switch to a static slug (`bootstrap-seed` / `<slug>.seed.v1`) OR the prose needs to acknowledge per-deploy re-run. Run-42 dogfood evidence: apidev/zerops.yaml:41-51 claimed *"stamps each key into a per-deploy ledger and skips it if the key already ran"* on a `${appVersionId}-seed` line — `${appVersionId}` resolves fresh every deploy → seed re-fires every deploy regardless of the ledger. init.ts was idempotent so the lie was prose-only, but the prose-fact mismatch is a factuality regression. Cross-reference: `principles/init-commands-model.md:7` (`${appVersionId}` per-deploy semantics) + `:10` (static-key once-ever semantics).

## Scoring loop

For each stitched fragment:

1. **Hard-rule pass FIRST.** Walk every rule prefixed V (universal voice), every rule prefixed Y7 (no authoring vocabulary), and IG4 (no cross-framework adapt-paths). These are HARD RULES — a single hit ACTs regardless of how the fragment scores on Voice/Trade-off/etc. criteria. Run-32 phase 2 lesson: a fragment scoring 8.5+ on the Voice criterion (rich friendly-authority phrasings) can STILL contain `zerops_dev_server` and require an ACT — the criterion score is independent of hard-rule presence.
2. **Criterion pass.** Then walk rules under the fragment's surface section.
3. For each candidate-violation, check threshold: cite the violated rule + the exact fragment text + the preserving edit. All three present: ACT. Any fuzzy: HOLD with a note.

Bias toward ACT — snapshot/restore reverts a wrong ACT automatically.

## Out of scope here

Cross-codebase coherence (env-var naming across siblings), factuality (URL correctness), stitching artifacts — refinement should HOLD with a class-named notice. Not refinable from this rule list.
