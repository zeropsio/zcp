**Mate's preview pane.** Mate shows a service's page in its preview pane, a frame on Mate's own origins: `https://mate.zerops.io`, and this container's `/mate/` on its `*.zerops.app` address. A page that sends `X-Frame-Options` (any value: it cannot name another origin) or a `Content-Security-Policy` whose `frame-ancestors` leaves those origins out reads "refused to connect" there, and a framework's security defaults often send one. So the dev and stage services send no `X-Frame-Options`, and their `frame-ancestors` is the app's own sources plus Mate's — `'self' https://mate.zerops.io https://*.zerops.app` where the app allowed only itself, without `'self'` where it allowed nothing — set in the app's own policy header, since a second one only narrows it. Production keeps the app's strict framing. The dev setup may carry it where the stage builds another one: production never builds the dev setup. The stage builds the setup production builds, so leave that setup as it is and give the stage Mate's preview variant of it, a setup that `extends` it and changes only the framing: on a static service its `run.routing.headers` (a list is replaced whole, so repeat the headers it keeps; a value carries its own quotes: `Content-Security-Policy: "\"frame-ancestors 'self' https://mate.zerops.io https://*.zerops.app\" always"`), otherwise a `run.envVariables` value the app's header code reads (`FRAME_ANCESTORS`, the app keeping its strict headers where it is unset). Deploy the stage with it, `zerops_deploy sourceService="<dev>" targetService="<stage>" setup="<the variant>"`; the application's stage and production build the setup the variant extends. `curl -sI <the page's URL>` shows what a page sends.
