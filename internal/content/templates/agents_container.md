ZCP control-plane container `{{.SelfHostname}}` inside this Zerops project. `zerops_*` MCP = primary surface for state/lifecycle/deploy/env/logs/verify. Bash/npx/SSH/zcli/psql/mysql/redis-cli = escape hatches for things `zerops_*` doesn't cover.

**Env here:** the project's vars — including each managed service's connection vars (`$db_connectionString`, `$cache_connectionString`, …) — are in this container's shell once the service is provisioned. Run ad-hoc ops in place by name: `psql "$db_connectionString" -c '…'` (mask when inspecting: pipe through `sed 's/=.*/=<set>/'`). Inside a runtime over `ssh`, reference the name THAT runtime wired (e.g. `$DATABASE_URL`, live after its first deploy) in a single-quoted body — not a sibling's bare `${db_*}`, which the default service isolation doesn't inject.

After bootstrap or adopt provision closes, service code SSHFS-mounts at `/var/www/{hostname}/` — the mount IS the service's runtime filesystem. **Edit** files there with Read/Edit/Write, not SSH. **Run** build/test/framework commands (`npm run build`, `npm test`, `npx …`, `php artisan`, `pytest`, DB migrations) INSIDE the service — `zcp run {hostname} <cmd> [args]` runs one there over SSH, in the folder of the code you stand in on the mount — because the runtime and its dependencies live in the service container, not on this host: started here, even where it works, it runs on this container and reads every file over the network. A shell line goes in as `zcp run {hostname} sh -c '<line>'`; a time limit goes on the command itself (`zcp run {hostname} timeout 600 <cmd>`), since stopping the call does not stop the command. There the same code sits at `/var/www` (no `{hostname}` segment), and plain `ssh {hostname} "cd /var/www && <cmd>"` reaches it too. Running in the service is the expected path for running code, not an escape hatch. Long-running dev servers are the one exception — start them via `zerops_dev_server`, never a backgrounded `ssh "… &"` (the channel dies with the call). Missing a CLI/tool? `zerops` has passwordless sudo on the container — install it ad-hoc (`ssh {hostname} "sudo apk add <pkg>"` on Alpine, `sudo apt-get install` on Debian — `cat /etc/os-release` if unsure) rather than working around its absence. That install is **ephemeral** (gone on the next deploy = fresh container); a tool the build or runtime needs durably goes in `prepareCommands` in `zerops.yaml`. That ad-hoc affordance covers the app's OWN tooling only — anything under `/opt/zerops/**` is platform-owned; a broken or missing binary there (e.g. `zcli`) is report-not-repair: never patch it with a compat shim, reinstall, or replacement.

**zcp's own Zerops key stays in this container.** `$ZCP_API_KEY` is the key zcp acts with: never pipe, copy or pass it to another service (over `ssh` or any other way), and never `zcli login` with it, here or anywhere — a login writes the key to disk, where it outlives the session and the app's dependencies can read it. Deploys go through `zerops_deploy`; when it, or any `zerops_*` tool, cannot do what is needed, say so to the person instead of running zcli yourself.

`zerops.yaml` lives at `/var/www/{hostname}/zerops.yaml`; per-service rules MAY exist at `/var/www/{hostname}/CLAUDE.md` — read if present. If `ls /var/www/{hostname}/` is empty, the service hasn't been bootstrapped yet — run `zerops_workflow action="start" workflow="bootstrap" route="adopt"` first.
