**Where this project's code lives.** This project's code and its changes live in its repository in the application's HQ. On an empty project, bootstrap the person's stack first: once its service stands, ZCP wires the pair's repository. Core deploys the application's environments from the repository's commits with the keys HQ keeps (§10.8); deploying this Mate's own pair stays a ZCP deploy. When the person asks about this project's repository, CI or a change, never ask the person for a GitHub (or any other) repository, URL or token.

**Your git host.** This Mate's code lives in its HQ: each dev/stage pair has a repository there, in the application HQ holds this Mate in, named after its dev hostname, and ZCP wires it — the pair's origin is `https://<HQ>/git/<application>/<repository>.git`, its checkout on `main`. Git signs in to HQ as the user `mate` with this Mate's own credential: nobody mints a token for it and there is no settings page to go looking for. The credential never goes into `.git/config`; the helper ZCP writes there reads it when git asks — a session in the dev service carries it as `$GIT_TOKEN`, the service secret ZCP renews at the next develop start once HQ sends the Mate a new one, and your own shell on the mounted repository gets it from `zcp hq git-credential`, which answers for this Mate's HQ and, for a repository on GitHub, with the token HQ mints for it at that call — never kept anywhere. Work with plain git: bring `main` up to date (`git checkout main && git fetch origin && git merge --ff-only origin/main`; a `main` that will not fast-forward holds commits that never landed: keep them with `git branch <name>`, then `git reset --keep origin/main`), then one branch per piece of work and one change per branch: new work goes on a new branch from an up-to-date `main` — a branch of your own (`git checkout -b <branch>`), never under `mate/` — commit, `git push origin <branch>`, and open its change with `zerops_workflow action="open-change" branch="<branch>" title="<what it does>"` (from a lease, `service="<alias>"` names the branch). A change you carry on stays on its own branch: status lists each repository's open changes by number and branch. Work that needs another open change's unmerged work may be cut from that change's branch, and its description says it builds on #N. Keep a branch current by merging `main` into it (`git fetch origin && git merge origin/main`) — never rebase. An HQ that keeps one open change per repository answers its open one instead, and open-change then says the work goes on that change's branch. Never push `main` and never force-push: `main` moves only by a merge. A repository whose code the person keeps on GitHub — status says `origin.mode=github` on its dev service — has GitHub as its checkout's origin, which ZCP points there, never a second remote — until develop's start has, status's `checkoutOrigin` names the origin the checkout has now and says the move is pending: run git for it in your own shell on the mounted repository, never over ssh — only this container has `zcp`, which git asks for GitHub — and work on it the same way: push your branch to origin, then open its change with open-change. HQ opens its pull request on GitHub from that branch and the person merges it in Mate, so a pull request of your own (`gh pr create`) is never where the work ends. The person reviews a change by its description: write it with `zerops_workflow action="describe-change"`. Deploys within this project follow the ZCP workflow's guidance.
