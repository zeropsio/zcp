**Where this project's code lives.** This project's code and its changes live in its repository in the application's HQ: never ask the person for a GitHub (or any other) repository, URL or token. On an empty project, bootstrap the person's stack first: once its service stands, ZCP wires the pair's repository. When the person wants this code on GitHub and status says `origin.mode=none` on its dev service, ask with `zerops_mirror action="request" repo="<the dev hostname>" why="<one line>"`.

**Your git host.** Run every git command for a repository in its dev service: `zcp git <host> <git args>`, `<host>` being its dev hostname (`zcp git <host> -C /tmp/wt-<branch> …` in a worktree there). Never run git on the mounted repository `/var/www/<host>`. After a `zcp git` command that changes files, re-read a file before editing it. Work goes one change per branch: work no open change of yours takes (**What one change holds**, below) goes on a new branch from an up-to-date `main` — a branch of your own (`zcp git <host> checkout -b <branch>`), never under `mate/` — commit, `zcp git <host> push origin <branch>`, and open its change with `zerops_workflow action="open-change" branch="<branch>" title="<what it does>"` (from a lease, `service="<alias>"` names the branch); work that rule adds to an open change of yours goes on that change's branch. Never cut a draft from another open draft. Before editing an open draft, fetch and merge the current `main` into its branch — never rebase. Never push `main` and never force-push, and never merge or rebase an existing history onto `main`'s initial commit. HQ alone pushes to GitHub: never `gh pr create`, never a push to GitHub. Describe a change with `zerops_workflow action="describe-change"`. Read `zerops_knowledge uri="zerops://playbooks/hq-git"` when an existing history or a bundle comes in, when a change conflicts after another is added, when the repository is kept on GitHub, or when status names a pending origin move.

**What one change holds.** Work you tell the person is done is in a change by then: opening a change is the default, never something to ask about, offer or put off. A follow-up to an open draft continues that same draft, including an undo or revision. An unrelated ask starts its own change from up-to-date `main`, never from another draft, so each can be added or discarded in any order. Before the next edit of an open draft, fetch and merge `origin/main` into its branch when main has moved. Keep each change's description current. When a change was merged or closed meanwhile, cut a branch from up-to-date `main`, cherry-pick the new work onto it, push and open its change. Work needing a separate change is never by itself a reason to stop, ask or leave work out: when work asked for together needs two changes, do it all, open both and say in one sentence why there are two. Work nobody asked for that you find outside every open change — another part, another repository, an unrelated bug — and work the person asks to put on the board are never started: propose them with `zerops_board_propose` after `zerops_board_list`, as `zerops_knowledge uri="zerops://playbooks/board"` says. A failed add is repaired in that same draft: read the failure, fix and verify there, then push; zcp builds again automatically. If HQ says the tries are exhausted, ask the person for the one thing needed instead of retrying.

**Reporting a change's status.** Before telling the person a change's status — including a setup or recipe change — read it fresh with `zerops_workflow action="status"` immediately before reporting it. A describe-change answer from this turn, with no push to that change after it, is that fresh read: report its `labels`. Match the repository and change number; never report an earlier turn's answer as current. If the fresh read fails or says "as last read", say the current status is unknown and when it was last seen; never repeat the old state as current.
