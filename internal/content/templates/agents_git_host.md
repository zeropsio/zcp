**Your git host.** This Mate's code lives in its HQ: each dev/stage pair has a repository there, in the application HQ holds this Mate in, named after its dev hostname, and ZCP wires it; a repository of several parts stays one repository — never a dev service per part (`zerops_knowledge uri="zerops://playbooks/monorepo"`). The pair's origin is `https://<HQ>/git/<organisation>/<application>/<repository>.git`, its checkout on `main`. Git signs in to HQ as the user `mate` with this Mate's own credential: nobody mints a token for it and there is no settings page to go looking for. Run every git command for a repository in its dev service: `zcp git <host> <git args>`, `<host>` being its dev hostname, runs git in that service's checkout (`zcp git <host> -C /tmp/wt-<branch> …` in a worktree there), and zcp answers git's credential requests there — for HQ with this Mate's credential, for a fetch from a repository on GitHub with the read token HQ mints for that call — never kept anywhere, never in `.git/config`. Never run git on the mounted repository `/var/www/<host>`: git there and git in the dev service on one `.git` break it. After a `zcp git` command that changes files the mounted folder can show the old state for up to 20 s: re-read a file before editing it. Work with plain git through it: bring `main` up to date (`zcp git <host> checkout main && zcp git <host> fetch origin && zcp git <host> merge --ff-only origin/main`; a `main` that will not fast-forward holds commits that never landed: keep them with `zcp git <host> branch <name>`, then `zcp git <host> reset --keep origin/main` — unless `origin/main` holds only HQ's initial commit, when that `main` is the repository's first history: keep it as it is and cut your branch from it; merged, its change becomes `main`), then one change per branch: work that needs a change of its own (**What one change holds**, below) goes on a new branch from an up-to-date `main` — a branch of your own (`zcp git <host> checkout -b <branch>`), never under `mate/` — commit, `zcp git <host> push origin <branch>`, and open its change with `zerops_workflow action="open-change" branch="<branch>" title="<what it does>"` (from a lease, `service="<alias>"` names the branch); work that rule adds to an open change of yours goes on that change's branch. A change you carry on stays on its own branch: status lists each repository's open changes by number and branch. Cut new work from another open change's branch only when it needs that change's code, and say in its description that it builds on #N: HQ squashes each change into one commit on `main`, so once that base merges, the change built on it can conflict with `main` — merge `main` in, push, and describe it again, since the push makes it a draft. Keep a branch current by merging `main` into it (`zcp git <host> fetch origin && zcp git <host> merge origin/main`) — never rebase. Never open a change only to record another's merge or to update a plan, roadmap or log: put it in the change doing the work, or in the next one that has work in it. A file every change appends to — a work log, a diary kept in one file — makes each open change conflict with `main` once another merges: give each change an entry of its own, such as a file per change, or per day and change. An HQ that keeps one open change per repository answers its open one instead, and open-change then says the work goes on that change's branch. Never push `main` and never force-push: `main` moves only by a merge. A repository whose code the person keeps on GitHub — status says `origin.mode=github` on its dev service — is worked on like any other: its checkout's origin is its repository in HQ too, never GitHub, and no second remote names GitHub — a checkout an older ZCP pointed at GitHub is moved back by ZCP, at the Mate's start or develop's start, and until it is, status's `checkoutOrigin` names the origin the checkout has now and says the move is pending. A branch you pushed to GitHub yourself before that move is not carried on there by a push to origin — HQ pushes on only to branches it put on GitHub: finish that work on a new branch pushed to origin, open a new change for it with open-change, and tell the person the earlier pull request is superseded. Push your branch to origin, then open its change with open-change. HQ alone pushes to GitHub: it mirrors such a repository itself — `main` to GitHub's default branch, each open change's branch, each change's pull request — and a person merges the change in Mate, so a pull request of your own (`gh pr create`) is never where the work ends, and a push of your own to GitHub is refused: `zcp git` answers GitHub only for fetches. Never sync GitHub by hand either: never push its default branch, nor copy a merged change onto it from a clone of your own (a note of yours that says to is out of date once HQ mirrors the repository); a merged change reaches GitHub as its pull request, squash-merged there, and GitHub's default branch moves only by that merge. A pass says once when HQ starts mirroring a repository, and once when GitHub's default branch and HQ's `main` diverge — HQ then moves neither — with the one change that brings them back in step. The person reviews a change by its description: write it with `zerops_workflow action="describe-change"`. Deploys within this project follow the ZCP workflow's guidance.

**What one change holds.** A change is what a person reviews, merges and would revert as one: split work by blast radius, never by topic. A run of asks is the person's stream of asks — bigger, move this, no, put it back, sort these by date, add a toast — not a develop work session, and its work goes into one change of yours: push each ask to that change's branch, and describe the change once at the end of your turn, as a list, one item per ask. The next ask joins your open change when all of these hold: the change is this Mate's own, never another Mate's, one handed to you or one made for a task; it is still open and not being merged, nobody has commented on it or asked to merge it as far as you know, no other open change builds on it, and no other conversation or subagent of yours is working on it; the ask continues that change's run of asks, or is unrelated interface work while the change was updated within about the last two hours (develop's start and status show each open change's last update) — a follow-up to that change joins however long it has waited; and its blast radius stays in the interface: what a person sees and how the interface behaves on the client, with no change to data, server, wire, auth, security, billing, deploy configuration or dependencies — copy, layout, styling, the order something is shown in, a toggle, a toast, a default size, what opens or shows first, keyboard or focus handling, a small interface fix. An ask that undoes or redoes an earlier one stays in the change too, so its diff is the net result. Anything else gets a change of its own: data writes, a schema or migration; server, protocol or wire contracts; auth, security or billing; deploy or infrastructure configuration; dependencies; a cross-cutting refactor; anything large on its own; an urgent fix for production; work the person asked to ship or revert by itself; work in another repository. When describe-change refuses because the change was merged or closed meanwhile, cut a branch from an up-to-date `main`, cherry-pick the new commits onto it, push it and open its change. Before asking for review, fold two or more open changes of yours that this rule would have made one — by the same conditions as joining: merge their branches into one of them where its branch is checked out (`zcp git <host> fetch origin && zcp git <host> merge origin/<the branch it folds>`, then `zcp git <host> push origin <branch>`; in a worktree there, `zcp git <host> -C /tmp/wt-<branch> …` and `push origin HEAD:<branch>`; in a dev pool, `<host>` is a lease of that branch), describe it again as a list, one item per ask, naming the changes it folds ("Includes #21, #22"), close each folded one with `zerops_workflow action="close-change" branch="<its branch>"`, and tell the person in one sentence which changes you folded into which. Never fold a change someone commented on or asked to merge as far as you know, another Mate's, one handed to you or one made for a task. When the person says to keep pieces of work apart, or to put them together, that wins.

**Reporting a change's status.** Before telling the person a change's status — including a setup or recipe change — read it fresh with `zerops_workflow action="status"` immediately before reporting it. A describe-change answer from this turn, with no push to that change after it, is that fresh read: report its `labels`. Match the repository and change number; never report an earlier turn's answer as current. If the fresh read fails or says "as last read", say the current status is unknown and when it was last seen; never repeat the old state as current.

**What serves only the person.** A runtime that looks like it serves the person rather than the app — their cloud agent, their own tooling — leaves the group's Stage and Small Production only at their word: ask them, and record the answer with `zerops_workflow action="group-recipe" mateOnly={"<hostname>": true}` (false carries it in every tier). **A repository that already exists** comes into HQ as `main` itself: HQ makes every repository's `main` with one initial commit, and an existing history never goes on top of it. Code kept on GitHub: connect its origin first — `zerops_origin action="request" url="<its GitHub address>" repo="<the dev hostname>" why="<one line>"` — and once the person connects it, HQ takes the repository's `main` from GitHub, so `main` starts as GitHub's `main`; take it into the checkout as the answer says, and never clone it in and merge it. Code from anywhere else — a bundle, another host, a GitHub repository HQ cannot connect — goes in as a branch of its own, exactly as it is: fetch it in the dev service — from an address, `zcp git <host> fetch <address> <its main branch>:<branch>`; a bundle copied in first (`scp <bundle> <host>:/tmp/<name>.bundle`), `zcp git <host> fetch /tmp/<name>.bundle <its main branch>:<branch>` — then `zcp git <host> push origin <branch>`, and open its change from that branch with open-change; merged, HQ makes that history `main`, and the checkout's `main`, which holds only that initial commit, moves onto it (`zcp git <host> fetch origin && zcp git <host> checkout -B main origin/main`). Either way, never merge or rebase it onto `main`'s initial commit, and never merge HQ's initial commit into it. The Mate's own setup — the dev setups in `zerops.yaml`, `.zcp/dev-servers.json` — goes in afterwards as an ordinary change on a branch cut from that `main`; on a repository kept on GitHub that change is a pull request, merged by squash.
