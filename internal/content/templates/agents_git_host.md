**Where this project's code lives.** This project's code and its pull requests live in its repository on the group's Gitea (`$GITEA_URL`). On an empty project, bootstrap the person's stack first: once its service stands, ZCP asks the broker for that repository and writes its deploy workflow, `.gitea/workflows/zerops.yml`, into it. "The deploy workflow", "CI", "the Test step" and "a pull request" in the person's message mean that repository and that workflow — never ask the person for a GitHub (or any other) repository, URL or token.

**Your git host.** `$GITEA_URL` is the account's own Gitea — ZCP classifies a remote on that host as the forge kind `gitea`, not as an unidentified server — and `$GITEA_TOKEN` is your Mate's own bot token for it (scopes `write:repository` and `read:user`: git and the repository API work, `/admin` answers 403). Nobody mints a token for this host and there is no settings page to go looking for: the one you have is the one there is, and `git-push-setup` uses it. `$MATE_BROKER_URL` is where a repository comes from — ZCP asks the broker for the pair's repository rather than you creating one by hand. The token's value never goes into `.git/config`; the credential helper ZCP writes there reads it when git asks — a session in the dev service carries it as `$GIT_TOKEN`, the service secret `git-push-setup` writes, and your own shell carries it as `$GITEA_TOKEN`. A pair wired before that helper answered your shell gets it at its next delivery or `git-push-setup`; from then on git in your own shell on the mounted repository signs in to this host with nothing set by hand, and until then it is refused there while the dev service's own sessions work. After the broker rotates the token, git in your shell signs in with the new one — the helper reads the token as the container holds it now (`zcp mate git-token`) — while the variable `$GITEA_TOKEN` itself keeps the old value until the Mate restarts, and Gitea refuses that one ten minutes after the rotation: for the repository API, take the token from git in the mounted repository (`printf 'protocol=https\nhost=<the Gitea host>\n\n' | git credential fill`) rather than from the variable. Commits on this host are the bot's own, not a person's, and `main` is protected on every repository: work on your Mate's branch and land through a pull request. What ships code to the group's other projects is `.gitea/workflows/` in that repository — those workflows deploy with `zcli push` on a key the broker hands the job for that one push, and carry no Zerops token themselves, so read one before assuming how those deploys happen, and look at what the remote already holds before a push that would replace it. Deploys within this project follow the ZCP workflow's guidance, not the pipeline.
