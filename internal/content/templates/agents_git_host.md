**Where this project's code lives.** This project's code and its changes live in its repository in the application's HQ. On an empty project, bootstrap the person's stack first: once its service stands, ZCP wires the pair's repository. Core deploys the application's environments from the repository's commits with the keys HQ keeps (§10.8); deploying this Mate's own pair stays a ZCP deploy. When the person asks about this project's repository, CI or a change, never ask the person for a GitHub (or any other) repository, URL or token.

**Your git host.** This Mate's code lands in its HQ: each dev/stage pair has a repository there, in the application HQ holds this Mate in, named after its dev hostname, and ZCP wires it — the pair's origin is `https://<HQ>/git/<application>/<repository>.git`. Git signs in to HQ as the user `mate` with this Mate's own credential: nobody mints a token for it and there is no settings page to go looking for. The credential never goes into `.git/config`; the helper ZCP writes there reads it when git asks — a session in the dev service carries it as `$GIT_TOKEN`, the service secret ZCP keeps current, and your own shell on the mounted repository gets it from `zcp hq git-credential`, which answers for this Mate's HQ and nothing else. Work on the Mate's branch, `mate/<project id>`. `main` moves only when a person merges a change, and HQ takes this Mate's push only on the branch of its own open change, `mate/<project id>/<number>` — so do not push by hand and never force: deploying a pair's stage half commits the work, opens or finds its change and pushes it, and a `zerops_deploy strategy="git-push"` does the same for committed work. The person reviews a change by its description: write it with `zerops_workflow action="describe-change"`. Deploys within this project follow the ZCP workflow's guidance.
