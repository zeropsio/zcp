## Guided mode (user-only)

This project runs in guided mode: **the guided skill is the entry point for every request to build, change, extend, fix, or restyle the app.** Invoke it first — ahead of the service-edit routing above — on the first build AND on every later change. It drives `zerops_workflow` (develop / bootstrap) and the other `zerops_*` tools for you, wrapped in a PRD + thin-slice discipline. Guided is on, so this always applies; don't re-judge whether a request "qualifies" by how technical or specific it sounds.

The person you're working with may describe what they want in plain words — "track my workouts", "make the tickets more kanban-style" — and can't necessarily review code. Build them working software they can react to: resolve the architecture yourself, build it in verifiable increments, and hand back a live URL — never a spec. Infer silently; don't interview them with questions they can't answer.

**Apply the guided skill at `.claude/skills/guided/SKILL.md` before planning or building.** It routes the work: read the request → resolve or extend the architecture (classify → statefulness → audience × stakes → capabilities → tier → services) → write or update a compact PRD + thin vertical slices → build each slice on the dev runtime with tests → review → verify → live URL → next change. Each phase's detail lives in `.claude/skills/guided/phases/*.md`; open the phase file when you reach it.

**The PRD and slice files in `.zcp/guided/` are the durable ledger** (plain markdown, gitignored, private). They survive compaction: on a resume or a returning request, `ls .zcp/guided/`, re-read them, and call `zerops_workflow action="status"` to learn what exists and where the last slice landed. Slice done-ness is read from status, never stored.

Keep the ledger compact: max 3 architecture drivers, max 5 active decision rows, 1-7 boundaries (never padded for count), and one Preserve/Design-seam/parallel-safety note per slice. This is there to make implementation faster and safer, not to create ceremony.

**Infer, don't interview.** A casual request means the user can't specify the architecture, not that they want something casual. Resolve it and narrate the plan; ask only when a decision is one-way, costly, public, regulated, destructive, or about someone else's data — then one question, first, and wait. Progress is never gated on the user approving the PRD; they react to a live URL, not a document.

**Build on the dev runtime; parallelize only after a safety audit.** The dev service is a living server — edit, test, and reload it in place, and its URL serves each change immediately. Slice 1 (the walking skeleton) is serial. After that, prefer natural sibling slices that can run in parallel, but never split horizontally just to create concurrency. `Blocked-by: none` is necessary but not sufficient: the slice DAG must mark parallel safety, and unsafe/shared write scopes stay serial. Don't redeploy per slice. Promote to stage (a formal deploy) at a checkpoint — a milestone, a clean built-verification, or release — not after every change. "Verified" is a composite: acceptance tests green + review clean + the URL serves it; name the parts, and never claim test quality as a platform guarantee.

**Keep going.** A delivered feature is not the end — when the user asks for more, return to the start: extend the PRD, add slices, and build them the same way on the existing infra. Scale the ceremony to the ask — a small restyle or fix is one thin slice, not a fresh PRD.

**Pause before a public URL on sensitive ground.** If the story touches regulated or sensitive territory (legal/medical/tax/financial advice, health or payment data, personal IDs, client documents, charging cards, destructive public actions), don't auto-enable a public subdomain — ask the harm-gate question the skill specifies first, then proceed within what the user confirms.

**Make it look and feel right.** You know the idiomatic UI kit for the resolved stack and what makes an interface feel premium — use them. Lean on the kit for the accessibility + consistency floor; spend judgment on information architecture, real loading/empty/error states, and copy in the user's terms. Default to a product UI; go bespoke only for a true brand surface (a public landing/marketing page). Don't ship the kit's stock default look as the finished product, and don't over-animate.

Run everything through the `zerops_*` tools and the bootstrap → develop → launch pipeline — never `zcli`, never a raw platform API. Route platform facts (service types, versions, provisioning) to their owners via `zerops_knowledge uri="zerops://..."` and the workflow tools, not to memory.
