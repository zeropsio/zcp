# Develop work-session PID-claim across reconnect + Fit framework-awareness

**Source:** Wave-7 flow-eval (2026-06-04). Two real defects deferred from the matcher-fix turn because they're workflow-engine design passes (not single-file fixes) — backlogged with verified root cause + fix sketch + the open question that gates each.

## Finding 1 — develop work-session not re-claimed after a mid-session PID change (HIGH if real-usage-frequent)

**Verified root cause (greenfield-website-from-brief):** the agent started a develop session (`workflow=develop scope=["www"]` → develop-active envelope returned). Then its MCP connection dropped + reconnected (agent's own narration: *"Let me search for the zerops tools first since they were disconnected and are reconnecting"*) → new server PID. Every subsequent `zerops_deploy` / `zerops_verify` / `close-mode` response then carried `workSessionState:{status:"none","note":"No active develop session — deploy not tracked..."}`. So auto-close tracking + close-mode write were not associated with the session: the deploy/verify weren't recorded, and `close-mode www=auto` succeeded (it keys off ServiceMeta) but auto-close could never fire (no recorded deploy/verify on the session).

**Why it's not "dead-on-arrival for all develop":** Wave-6 classic-bun-simple + others had auto-close fire correctly — because there was NO reconnect (stable PID). The defect is specifically a mid-session PID change. Bootstrap sessions already survive a PID change (the InFlightBootstrap / `route=resume` claim path); develop work-sessions do NOT auto-claim — they recover only via an explicit `zerops_workflow action="status"` call, which the agent won't make if it just proceeds to deploy.

**Fix sketch (analyst):** make work sessions claimable across PID like infra sessions — at engine boot (or on the first work-session-scoped call), if exactly one dead-PID develop WorkSession exists for this project and no live one, claim it (rewrite the owning PID) instead of reporting `none`. Mirror the bootstrap-session claim. Guard against claiming the wrong session when multiple exist (fall back to the `action=status` recovery path then).

**Open question (gates priority):** how often does a mid-session MCP reconnect happen in REAL Claude Code usage (long-lived zcp server, one PID per session) vs. this being a flow-eval transport artifact? If real (e.g. context-compaction-induced reconnect is a documented scenario — CLAUDE.md "compaction survival"), this is HIGH (silent auto-close/verify-tracking loss after every compaction unless the agent happens to call status). If eval-only, it's low. **Decide with Karel before implementing.** Risk: work-session claim semantics + the registry; regression surface on the per-PID lifecycle (TestIsOpen / DeriveCloseState / the session registry).

## Finding 2 — Fit=exact is computed blind to framework (medium, regression_risk=possible)

`CompareStacks` (intent_dependencies.go) computes Fit only from service-type families (nodejs/postgresql), stripping framework. So any nodejs+postgres recipe scores `fit=exact` against any nodejs+postgres intent regardless of framework — a NestJS/Express recipe was labeled `fit=exact` for a Next.js intent, contradicting the recipe's own `why`. The Wave-7 recipe-matcher tokenizer fix (shipped) makes the CORRECT recipe rank first (0.95 framework band > 0.85 language band), so the wrong `fit=exact` is now less harmful — but the label still overstates suitability.

**Fix sketch:** fold a framework-family check into Fit so a recipe whose framework is absent-from / contradicts the intent cannot be `exact` — downgrade to a `framework-mismatch` fit, or drop. Single-owner: the fit label and the recipe's `why` must not contradict.

**Risk:** `regression_risk=possible` — Fit feeds the route-menu recommendation for ALL recipes; folding framework in could reshape fit labels for currently-correct matches. Needs a careful pass + the existing `TestCompareStacks_*` / route-menu tests re-verified. That's why it's deferred, not bundled with the (safe, additive) tokenizer fix.
