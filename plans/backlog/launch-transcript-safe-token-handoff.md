## Context

The launch-window token (`launchKey`) is generated by the user in the
Zerops dashboard (Settings → Access Tokens Management) and passed into
ZCP via the `zerops_workflow` MCP tool call's `launchKey` argument. The
agent constructs that call, so the value appears in the MCP tool-call
transcript that the client (Claude Code, etc.) records.

ZCP's P-LP-1 invariant covers everything ZCP itself controls:

- `launchProductionResponse` — no field for the key (pinned by
  `TestHandleLaunchProduction_LaunchKeyNeverInResponse`).
- `launchState` — no field for the key (pinned by
  `TestLaunchState_NoLaunchKeyFieldExists`).
- `launchAuditEntry` — no field for the key (pinned by
  `TestAuditLog_NeverContainsLaunchKey`).
- Auth-failure wrapping — error text never echoes the key value (pinned
  by `TestHandleLaunchProduction_Mutation_AuthFailureWrappedSafely`).

What P-LP-1 does NOT cover, and cannot cover by design:

- The MCP transcript itself — the client's record of the tool calls that
  passed through. The agent sent `launchKey=<value>` and that's part of
  the conversation context, persisted wherever the client persists
  conversations.

This is the residual leak surface. v1 ships with it as a known tradeoff
because all viable alternatives require either platform-side cooperation
or an out-of-band CLI handshake — neither was in v1 scope.

The original plan (`launch-production-feedback-fixes-2026-05-13.md` §6)
sketched two alternatives that survived to backlog:

## Sketch — Alternative A: zcli launch publish (CLI handshake)

The MCP server emits the import yaml + atom guidance. A separate
`zcli launch publish --launch-id=<id>` CLI command, run in the user's
terminal, takes the token via:

- `--token-stdin` (paste once into terminal stdin, never echoed)
- `$ZEROPS_LAUNCH_TOKEN` env var (set in shell before run)
- `--keyring` (macOS Keychain / libsecret integration)

The CLI command:

1. Reads the MCP server's state file for the matching `launchID` (sourced
   bundle + import yaml hash).
2. Calls Zerops platform directly (`projectAdminClient.CreateAndImport`).
3. Writes the launch outcome back to the MCP state file.
4. The agent's next `action=status` call surfaces the launched envelope.

Agent never sees the token. Transcript carries only `launchID` (already
non-secret — it's a derived hash).

**Cost when implemented:**
- `zcli` command (~150-300 LOC) + state-file handshake protocol (~100 LOC
  in MCP server) + atoms describing the new flow (~3 atoms).
- Cross-binary state-file locking (`flock` advisory locks) so MCP server
  and CLI don't race on writes.
- Atom corpus: agent guidance to "you cannot publish from MCP directly —
  emit launchID and the dashboard URL for the user to run zcli."

**Risk:** dual binary surface — MCP + CLI must agree on state-file schema
forever. Pre-production phase is acceptable; once shipped, breaking the
schema requires zcli version coordination.

## Sketch — Alternative B: Browser-mediated handoff

Zerops dashboard adds a "Pending Launches" page. When user clicks
"Approve $LAUNCHID", the dashboard:

1. Pops a confirm dialog.
2. Issues a one-shot token server-side, bound to that specific
   `launchID` + the user's clientUser identity.
3. Calls ZCP's MCP server's webhook endpoint (or writes to a shared
   state store) with the approval.
4. MCP server's next poll detects the approval and advances the workflow.

Agent never sees the token; user never pastes it anywhere. The token
exists only between the dashboard and the platform.

**Cost when implemented:**
- Platform-side: new dashboard page + per-launch approval endpoint +
  webhook delivery to ZCP (or shared signing mechanism).
- ZCP-side: webhook receiver + state-file approval column + poll logic
  in launch-production handler.
- Coordination with Zerops platform team.

**Risk:** webhook delivery requires the ZCP MCP server to be reachable
from the Zerops cloud — which is fine for in-container ZCP but breaks
for local-machine ZCP (the user's laptop is NAT'd). Local-machine ZCP
would need a polling fallback or a dashboard-side "copy this approval
code" out-of-band (which collapses back into Alternative A's CLI pattern).

## Why both are in backlog (not rejected)

The current transcript-leak surface is real but quantitatively bounded:
the token is one-shot, account-wide, and user-revocable. The window
between "token generated" and "user revokes after launched" is short
(typically minutes), and the audit trail in Zerops's dashboard lets the
user verify it wasn't used out of expected scope.

The cost of either alternative is non-trivial and one of them
(Alternative B) depends on platform-side cooperation. Defer until:
- A specific user pain surfaces, OR
- A specific security review demands it, OR
- The platform team independently proposes the dashboard-approval flow.
