## 2. Decisions this plan makes

**D-S1-a — The Zerops-environment detection rule is ONE explicit env var: `T3CODE_ZEROPS_PROJECT_ID`.**
Set and non-empty ⇒ Zerops environment. Nothing else votes. `zcp init z3` (S2) sets it from
`runtime.Info.ProjectID` (the injected `projectId`). Rejected: sniffing the injected `projectId` /
`zeropsSubdomain` directly — it makes the rule two-headed and a missing value fails silently instead
of loudly. The rule lives in `apps/server/src/zerops/ZeropsEnvironment.ts` and **S3 imports the same
helper** for its server-side `worktree mode = local` forcing. *Coordination item for main.*

Config, all `T3CODE_ZEROPS_*`, resolved in `apps/server/src/cli/config.ts` beside the existing keys:

| Key | Default | Meaning |
|---|---|---|
| `T3CODE_ZEROPS_PROJECT_ID` | — | the membership target; **presence enables Zerops mode** |
| `T3CODE_ZEROPS_API_HOST` | `api.app-prg1.zerops.io` | host or full URL, normalized the way zcp normalizes `ZCP_API_HOST`; base = `https://<host>/api/rest/public` |
| `T3CODE_ZEROPS_ALLOWED_ORIGINS` | `""` | comma-separated extra origins for CORS + the WS upgrade |
| `T3CODE_ZEROPS_MEMBERSHIP_TTL_SECONDS` | `900` | the membership cache window (see D-S1-c) |

**D-S1-b — `zerops-identity` mints the ordinary grant; nothing about the Zerops token is kept.**
`POST /api/auth/zerops-identity {token}` → `GET {base}/project/{projectId}` with that token
(S0.1: `200` member / `403 insufficientPermissions` / `401 notAuthorized` / `400 projectNotFound`,
30-40 ms) → on `200`, `GET {base}/user/info` for `userId` and the `clientUserList[]` entry whose
`clientId` equals the project's `clientId` (the role). Then `createPairingLink({subject: <userId>,
scopes, ttl: 2 min, label: "Zerops <role>", proofKeyThumbprint?})` and return the existing
`AuthPairingCredentialResult`. The token is a local; it is never written to the store, the session
row, a log annotation, or an error body. 403/401 ⇒ `401 auth_invalid`, no grant.

**D-S1-c — "Membership re-checked on connect" is implemented as a short session lifetime, not as a
second state field.** The server cannot re-verify a user's membership without that user's token
(S0.1: there is no member-list endpoint, and the search endpoints refuse cross-org callers). So the
Zerops session's TTL *is* the membership window: `zerops-identity`-derived sessions get
`ttl = T3CODE_ZEROPS_MEMBERSHIP_TTL_SECONDS` (default 15 min). When it lapses the next connect fails,
the client silently re-mints with the Zerops token it already holds (S0.1: those are 5-day tokens with
a refresh), and *that* re-mint is the real `GET /project/{id}` check. Removing the member therefore
ends access within one window, with no stored credential and no new session model.
Rejected: re-checking with the container's own `ZCP_API_KEY` (it cannot speak to *this user's*
membership) and a `POST /client-user/search` probe (unproven, and S0.1 measured the search endpoints
as hard-gated). *An open socket is not torn down mid-window — the brief's acceptance is "at the next
connect".*

**D-S1-d — Origin allowlist = same-origin ∪ `http://localhost:*` ∪ configured extras ∪ the two
desktop schemes.** Enforced at the WS upgrade (Origin present and not allowed ⇒ 403; **absent ⇒
allowed**, since a non-browser caller cannot be CSRF'd) and as the CORS `allowedOrigins` predicate.
The container's own 8080 origin needs no entry: the hosted client under `/z3/` is same-origin with
the API, and same-origin requests are not subject to CORS at all. `localhost:*` is the product-level
dev convenience of brief §4a, not a hack.

**D-S1-e — In a Zerops environment the hosted client is bearer/DPoP only.** The descriptor drops
`browser-session-cookie` from `sessionMethods`, and `POST /api/auth/browser-session` refuses. No
cookie means the cross-origin CSRF surface the wildcard CORS opened is closed by construction, and
the DPoP path (already implemented on both sides) becomes the recommended one.

**D-S1-f — `exec:operate` is a new scope, granted by `zerops-identity` and by
`AuthAdministrativeScopes`, never by `AuthStandardClientScopes`.** A project member already reaches a
shell in this container through code-server and through the agent, so exec adds no privilege over what
the door already grants — but a plain `one-time-token` pairing (a laptop paired to a non-Zerops
server) must not silently gain it.

## 4. Risks

1. **Streaming-RPC frame shape over the raw WS.** S0.9 pinned the request/`Exit` shape but not the
   `Chunk` frames a `stream: true` RPC emits. If the verification snippet I hand main does not
   collect, the fallback is a non-streaming `exec.run` returning the object directly — same
   acceptance, one less feature. Flagged, not assumed.
2. **`GET /user/info` costs a second round trip on every mint** (~37 ms, S0.1). Acceptable at a
   15-minute re-mint cadence; if it is not, the `role` becomes optional and `subject` comes from a
   single call — but S0.1 says `/user/info` is the *only* place `userId` appears.
3. **Descriptor drift.** `bootstrapMethods` is a closed literal union the client switches on; adding
   `"zerops-identity"` is additive but an old client that exhaustively matches will not compile.
   Only our fork's clients matter here (S4/S5).
4. **Rebase surface.** `ws.ts`, `http.ts` and `cloud/` are exactly where upstream moves ~15
   commits/day (brief §4 rule 6). Every touch outside `zerops/` is kept to a single added block or a
   single changed expression, so a conflict is a hunk, not a rewrite.
5. **`revokeBySubject` has no caller in S1** beyond its test and the ops path. That is deliberate —
   the brief lists it as a deliverable — but it must be reachable, so it lands on the
   `EnvironmentAuth` interface, not as a private helper.
