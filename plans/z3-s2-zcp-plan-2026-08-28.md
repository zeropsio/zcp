## 1. What changes, and what it replaces

The seed branch put z3 on its own declared port 3773 straight from the L7 and needed a
platform-owned recipe (`startCommands`) plus a Go sidecar to mint pairings and answer
`/healthz`. D2 drops all three. What survives from the seed: the init-step shape, the
`internal/service` exec-config pattern, the `/healthz` idea, the `internal/z3` constants file.

| Concern | Seed (`feat/z3-container`) | Here |
|---|---|---|
| how z3 is reached | own port 3773 from the L7 | nginx `location /z3/` on the existing 8080 origin |
| how z3 is supervised | `run.startCommands` in a mirrored recipe | `zsc unit create z3 "zcp service start z3"` (the sshfs primitive) |
| where the binary comes from | `npx --yes t3@0.0.35` at every start | local bundle first (`$PREFIX/node_modules/.bin/t3`), else one pinned `npm install` |
| pairing mint | `/z3-pair/<VSCODE_PASSWORD>` → Go sidecar | gone (S1's Zerops-identity door replaces it) |
| `/healthz` | Go sidecar, TCP-dials 3773 | static nginx, no process |
| workspace | `/home/zerops/app` | `/var/www` (D3) |

## 3. Decisions

**D-a. The step lives inside `Run()`, not behind a `zcp init z3` subcommand.** The platform
recipe's `initCommands` run bare `zcp init`; a subcommand nobody calls would never execute on a
fresh container, which is exactly the acceptance case. (`zcp init nginx`/`sshfs` are subcommands
because the recipe calls them explicitly.) No new subcommand is added — there is no caller.

**D-b. Local-bundle-first, one version constant.** `$PREFIX/node_modules/.bin/t3` present ⇒ used
as-is, no version check, no network (this is what makes the §4a dev loop and the release path one
code path). Absent ⇒ `npm install --prefix $PREFIX --no-audit --no-fund t3@<PinnedVersion>`, 180 s
timeout (measured: 55 s for 198 packages on the container, 58 s cold end-to-end). Failure ⇒
**degrade**, and the unit is NOT created — a unit whose ExecStart cannot resolve crash-loops,
which is worse than an absent unit and hides the real cause.

**D-c. `--base-path` is passed only when the installed bundle advertises it.** (main asked for a
decision.) Probe at unit start: `<bin> serve --help`, look for `--base-path`, 10 s timeout, any
failure ⇒ do not pass the flag. Rationale: version-gating cannot tell "our fork with base-path"
from "our fork before it" (both `0.0.35-dev.<sha>`), and the fetch fallback today resolves
*upstream* `t3@0.0.35`, which has no such flag — passing it unconditionally turns the fresh-container
path into a crash-loop. Not passing it degrades in the safe direction: the server boots, `/z3/`
answers, root-absolute assets 302 (S0.5's "loads but nothing works"), and `/healthz` still tells the
truth. Cost: one node startup (~1 s) per unit start, on the boot path only.

**D-d. `/healthz` does NOT carry `z3Up`; it carries `initComplete` + `initAt` only.** This follows
brief §9 ("no sidecar, no exec … `z3Up` is z3's own route answering. Two probes, both static in
nginx's hands") over §6's one-line acceptance wording. Stock nginx cannot branch a *response body*
on a subrequest: with `proxy_pass` + `error_page` the down-body is ours but the up-body is z3's, so
a single endpoint cannot answer `{initComplete, initAt, z3Up}` without a process. So:

- `GET /healthz` → `200 application/json`, `alias` onto the init marker file, `error_page 404` →
  a literal `{"initComplete":false,"initAt":null}`. No proxy, no exec, always answers.
- `z3Up` = `GET /z3/.well-known/t3/environment` → `200` + `content-type: application/json` +
  `"basePath":"/z3"` (main's coordination point 3). A stripped or mis-proxied prefix returns the
  SPA's `text/html` with `200`, so the **content-type assertion is the check**, never the status.

If the owner wants one endpoint, the cheapest route is a `{"z3Up":true}` route in the fork plus
`proxy_pass` + `error_page` here — one template hunk, no Go. Flagged, not taken.

**D-e. nginx strips the prefix** (`proxy_pass http://127.0.0.1:3773/;`, trailing slash), exactly
the S0.5-verified block, per main's coordination point 1. Consequence for the probe target: z3's
routes are at the loopback root, so `/z3/.well-known/…` reaches `…:3773/.well-known/…`.

**D-f. `/proxy/3773/` and `/absproxy/3773/` are closed** (`return 404`, regex location, evaluated
before `location /`). Owner decision: one door. 404 rather than 403 — the second door is not
advertised.

**D-g. The unit is created only when its file is absent.** `zsc unit` has only `create`/`remove`
(verified), units survive a restart (S0.2), and `zcp init` runs on every boot — so the check is
`stat /usr/lib/systemd/system/zerops@z3.service`. Init never restarts the unit: systemd owns that
at boot and the dev-push script owns it in the loop.

**D-h. The z3 unit's environment comes from a file written by init, not from inheritance.**
`zcp init` runs as a `run.init` command with the full Zerops env present; whether a
`zsc unit create`d unit inherits `projectId` is unmeasured. So init writes
`/home/zerops/.zcp/z3.env` (non-secret ids only — never a token) and `zcp service start z3` merges
it over the inherited environment. Rewritten every boot, so adding a variable never needs the unit
recreated (a unit's ExecStart is frozen at creation). Names per S1 (main): `T3CODE_ZEROPS_PROJECT_ID`
(= `runtime.Info.ProjectID`), `T3CODE_ZEROPS_API_HOST` (= `ZCP_API_HOST` else
`schema.CanonicalAPIHost`, bare host), `T3CODE_ZEROPS_ALLOWED_ORIGINS` (written only when the
service env `ZCP_Z3_ALLOWED_ORIGINS` is set — **the one name I chose myself**),
`T3CODE_ZEROPS_MEMBERSHIP_TTL_SECONDS` (never written; the server's 900 s default stands).

**D-i. Workspace is `/var/www`** (D3), replacing the seed's `/home/zerops/app`. Base dir stays
`/home/zerops/.t3` (survives restart, lost on redeploy — S0.10).

## 4. The argv and the constants

```
/home/zerops/.zcp/z3/node_modules/.bin/t3 serve \
  --mode web --host 127.0.0.1 --port 3773 [--base-path /z3] \
  --base-dir /home/zerops/.t3 --no-browser \
  --auto-bootstrap-project-from-cwd /var/www
```

Flag names checked against `../z3/apps/server/src/cli/config.ts`: `--mode` (choice), `--host`,
`--port`, `--base-dir`, `--no-browser` (boolean), `--auto-bootstrap-project-from-cwd` (boolean),
and `cwd` is a positional `Argument`, not a flag. A boolean flag immediately before the positional
parses (the POC ran `--no-browser /home/zerops/app` live).

`internal/z3` (one file, the single edit point): `PinnedVersion`/`PackageSpec`, `Prefix`, `BinPath`,
`EnvFilePath`, `BaseDir`, `WorkspaceDir`, `ServePort`, `BasePath`, `UnitName`, `UnitFilePath`,
`InitMarkerRelPath`/`InitMarkerPath`, and the `T3CODE_ZEROPS_*` env-name block with the contract
doc-comment. `BasePath` feeds both the argv and the nginx template, so `/z3` moves in one edit.

## 6. Live checks for main (the orchestrator runs these; I never touch a container)

After slice 3 is pushed to `z3-eval`'s zcp (`z3-dev-push.sh all`, then `zcp init` + `sudo -E zcp
init nginx` + `nginx -s reload`):

```
curl -sS https://<zcp-origin>/healthz                       # {"initComplete":true,"initAt":"…"}
curl -sSi https://<zcp-origin>/z3/.well-known/t3/environment | head -20   # 200 + application/json + "basePath":"/z3"
curl -s -o /dev/null -w '%{http_code}\n' https://<zcp-origin>/proxy/3773/ https://<zcp-origin>/absproxy/3773/   # 404 404
ssh zcp 'systemctl status zerops@z3 --no-pager | head -5; ls -l /home/zerops/.zcp/z3/node_modules/.bin/t3; cat /home/zerops/.zcp/z3.env'
ssh zcp 'sudo -n systemctl show zerops@z3 -p ExecStart'     # the argv, incl. whether --base-path made it
```

Degrade run (no network for the bundle), on a throwaway service only:

```
ssh <svc> 'sudo mv /home/zerops/.zcp/z3 /home/zerops/.zcp/z3.bak; cd /var/www && PATH=/usr/bin:/bin zcp init; echo "exit=$?"'
# expect exit=0, a "! Zerops Code (z3): …" line naming what breaks, and NO zerops@z3 unit file created
```

Restart-of-an-older-container check (the S4 "Enable Zerops Code" path):
`PUT /service-stack/{id}/restart`, then poll `/healthz` every 2 s — `initAt` moves within ~17 s,
the descriptor probe answers JSON within ~20 s (S0.2 budget: 30 s, ~14 s of L7 502 in between).
