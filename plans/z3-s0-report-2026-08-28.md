## The decision that shapes S3 — S0.3 / S0.4 / S0.13

| Number (4 246-file repo, 82 k files with `node_modules`) | mount | ssh + ControlMaster | host floor |
|---|---|---|---|
| full T3 turn (22 git calls, 2 checkpoints) | **12.7 s** | **1.37 s** | 1.04 s |
| checkpoint capture (7 calls) | 5.5 s | 0.60 s | 0.45 s |
| `status --porcelain=2 --branch` at the 30 s poll cadence | 1.4–2.2 s | 0.09 s | 0.06 s |
| workspace rescan (94 k dirents) | 2.6–16 s (twice past T3's 15 s timeout) | 0.48 s (`ssh host find`) | 0.41 s |
| 3 repos per turn | 21.0 s | 2.3 s sequential / **0.8 s parallel** | — |
| checkpoint with no `.gitignore` (76 k untracked) | **245 s** | 9.4 s | 9.8 s |

**Decisions:**
1. **S3 = SSH executor, no debate.** `ssh <host> git -C /var/www …` is 9× the mount and within 1.3× of the host; the mount is not "within budget" at any tree size that has `node_modules`. The rescan moves to the host too (`ssh host find`), or it trips `WORKSPACE_INDEX_SCAN_TIMEOUT_MS`.
2. **ControlMaster is required and already present.** 59 ms vs 8 ms per handshake × 24 round trips = 1.2 s/repo/turn. zcp's managed `~/.ssh/config` block (`internal/content/templates/ssh-config`) already sets `ControlMaster auto` / `ControlPersist 600` for `Host *` — the driver should still pin the options itself.
3. **Fan out per host.** Three repos in parallel cost what one does (0.8 s). Enumerate from the topology feed, never scan.
4. **Write visibility is right in the direction that matters, wrong in the other.** Agent edits through the mount reach host-side git within one 50 ms poll (write-through). Host-side creates/deletes reach the mount's *directory listings* only after the 20 s `dcache_timeout`; content and direct path lookups are immediate. Do not fix this with mount options (`dir_cache=no` makes status 6.6 s): after a host-side restore, refresh what z3 shows over SSH; the agent reads files by path, which is immediate.
5. **No file watching on the mount.** inotify never fires for host-side changes. Drop T3's trace2 hook-progress spawner (as planned) and poll over SSH.
6. **Guard the first checkpoint.** zcp's host-side `git init` writes no `.gitignore` (`internal/ops/git_identity.go:78-81`); a node app there is the 245 s case, and `status` never reveals it (it collapses untracked dirs). Refuse/warn when `ls-files --others --exclude-standard` is large — or have zcp's init write a `.gitignore` from the recipe's language (a small zcp slice alongside S3).
7. Two corrections to the brief: a turn is **22** git invocations (not 12–20); the temp index goes to the host's `.git` dir today (`t3-checkpoint-index-<uuid>`), fine under SSH, fatal over the mount.

## S1 — the door (S0.1, S0.9, S0.2)

- `GET /project/{id}` with the caller's token is the membership check, three-way on the status code alone: `200` member · `403 insufficientPermissions` non-member · `401 notAuthorized` bad token; a wrong id is `400 projectNotFound`, so nothing leaks. 30–40 ms. Role = second step (`/user/info` → the `clientUserList` entry whose `clientId` = the project's; only `OWNER` seen live; the SDK's role enum is stale). **Decision:** validate = `GET /project/{projectId}` per connect (cache minutes); `subject` = `userId` from `/user/info`; never reconstruct membership from `/user/info` alone.
- **CORS is a wildcard live** (`OPTIONS /oauth/token` from any Origin → `*`) — D1's exposure confirmed. **New third item:** every `t3 serve` boot mints an unconsumed `administrative-bootstrap` pairing link with wider-than-normal scopes (5-min TTL) — whoever reads the unit's stdout gets an admin credential per boot. S1 disables or consumes it in the Zerops environment.
- Two clients on one container work at the transport level (two pairings, two sockets, independent RPCs, no eviction); the wire protocol is effect RPC over JSON arrays (`{"_tag":"Request",…}` → `{"_tag":"Exit",…}`). Thread-level sharing = the phone half (Q-07).

## S2 — delivery (S0.5, S0.2, S0.10, S0.6)

- **`/z3/` on 8080 works end to end**: one `location /z3/` beside `/healthz`, outside the cookie gate, `proxy_pass http://127.0.0.1:<port>/` **with the trailing slash**, WS upgrade headers → mint → token → ticket → `101` through nginx + the L7, 60 s open, no drop. No collision with code-server 4.134.0's routes. **Decisions:** (a) ship Vite `base` in the same change — the shell 200s either way and every root-absolute asset dies, so a half-done base path passes a naive smoke test; (b) never `proxy_pass` without the slash: z3's SPA catch-all turns any mis-prefixed API call into a `200 index.html` — health checks assert JSON, not status; (c) the mint/pairing `origin` must become `<8080 origin>/z3`; (d) decide whether code-server's `/proxy/3773/…` (already a door to z3 behind the cookie) stays open.
- **"Enable Zerops Code" = restart → poll `/healthz`: 17 s to an answer, 19 s to `z3Up`, ~14 s of L7 `502` in between.** Budget 30 s, render the 502 as "restarting", poll `z3Up` not the status code. Container id unchanged across a restart.
- **What survives what:** restart keeps `state.sqlite`, `/home/zerops`, `/var/www`, `zsc`-created units (Q-01: yes) — only `/tmp` and live nginx edits die (the boot re-renders the template). Redeploy replaces the container with zero 502s (2 min 29 s) and loses **everything** (`~/.t3` recreated empty, units gone). Thread history is a redeploy away from gone — say so in the UI before any redeploy-shaped action.
- Cold `npx t3@<pin>` on an image-fresh container = **58 s** to `z3Up` (4 s with a warm cache) — the fresh-project first-boot number and the case for local-bundle-first. Node `v24.20.0`, tarball 20 MB, 282 MB installed (S0.6).
- **Restart = upgrade, proven on the platform recipe (z3-eval):** the hand-pushed dev binary was replaced by the latest release 9 s after the API call (`install.sh` re-ran from `initCommands`); `~/.zcp/z3`, `~/.claude` and `/var/www` survived; same ~14 s 502 hole (+2 s → +16 s). The container can even restart itself with its own project-scoped token. D2's "Enable Zerops Code = restart" holds end to end.

## S4 — client flow (S0.7, S0.8 side-findings)

- Registration is `POST /registration` with the undocumented `claimZcpPool: true` → `zcpClaimed` in the response, session token immediately, **no e-mail-verification gate, TOTP optional**. Pool-exhausted fallback = `POST /client/{clientId}/project` + `PUT /project/{id}/first-class-recipe/development-container {serviceImportYaml, recipeSource:"zeropsio/zcp", createIntegrationToken:true}`. The GUI waits on WebSocket pushes, never REST polls — z3 polls direct reads instead. **Decision:** S4 re-implements exactly these calls; the `serviceImportYaml` contract (`ZeropsYamlBuilder.generate()`) is traced before the fallback is coded.
- **Captcha:** Turnstile is not a required field at the API validation layer. Whether a missing token is rejected later is Q-10 — decided by the live run (Q-11) once you send e-mails. If enforced and hostname-bound, that is a platform-side item.
- **GitHub OAuth signup with the claim is unimplemented in the GUI** (no producer attaches `zcp:true` to `state`) and the callback is bound to Zerops' OAuth app. **Decision:** S4 ships e-mail/password only; GitHub-with-claim needs a platform change → yours to raise.
- **A `zcp@1` without `VSCODE_PASSWORD` is publicly open** (S0.8's `zcpb`: `200` code-server, no gate). "New project" goes through the first-class recipe or sets the password before enabling the subdomain.

## S6 — Zerops-aware client (S0.11, S0.12)

- **The `StateEnvelope` never crosses the wire.** `zerops_workflow action=status` returns ~9 KB of markdown; no tool result carries `{"envelope":…}`; `structuredContent` is unused in zcp. D5's premise is false as of `64f63ae8`. The fork side is ready — MCP tool results reach one provider-agnostic bus unmodified for Claude (`item.completed` with the raw `tool_result` block) and Codex (`mcpToolCall` item with `result.content`). **Decided after a live PROVE (14:39 UTC):** `structuredContent` is unusable — Claude Code 2.1.250 replaces the model-facing text with it (the atoms vanish). The envelope therefore rides **inside the text** as a trailing fenced `json zcp-envelope` block on every workflow-aware result; both providers forward it verbatim. zcp slice `feat/z3-envelope-wire` in progress (helpers + status/start, then the mutating tools; guard test + `docs/spec-z3.md`).
- **`zcp studio watch` is a doorbell**: `{"type":"connected"|"topology-changed"|"disconnected"}`, fires on service add/delete only (+0.55 s on import, +10 s on delete), **never on status transitions**. `zcp studio topology` is a direct read (CREATING at +1.05 s, ACTIVE at +16 s; 0.26 s/call) with id/hostname/type/status/adoption/URL but no live process. **Decision:** topology on every doorbell **plus** a slow poll (or the lifecycle feed) for status; the search endpoints are never needed.

## S7 — agent auth (S0.8)

`~/.claude/.credentials.json` alone (mode 600) makes a copied subscription login work, MCP included; the access token lives ~8 h; two containers used it concurrently without conflict; the refresh race past `expiresAt` is untested (Q-12). `codex login --device-auth` exists (codex-cli 0.150.1); `claude setup-token` exists and this build reads `CLAUDE_CODE_OAUTH_TOKEN`. **T3 passes the parent env to providers whole** (`ProviderInstanceEnvironment.ts:3-15`) — `ZCP_HARNESS` and `CLAUDE_CODE_OAUTH_TOKEN` reach the process; S7 must be deliberate about the parent env. **A `sensitive:true` service env write lands in `/etc/zerops-zembed/env.json` in ~2–2.5 s with no restart**, visible to new sessions at once; delete is the unnested `DELETE /user-data/{id}`. **Decision:** the setup-token card is viable without a restart; the provider is respawned (or the server re-reads the file) after the write.
