## 0. The cut, in one paragraph

A Zerops user with a Claude Pro/Max or ChatGPT subscription signs the agent CLI in **from inside z3**: a card
says "Claude — not signed in", its button opens z3's terminal with the login command already typed
(`claude /login`, `codex login --device-auth` — the strings the Zerops GUI walker uses, lifted verbatim),
the user follows the CLI's own prompts (URL is clickable — z3's Ghostty terminal regex-links plain
`https://…`), and the moment the credential artifact appears (`~/.claude/.credentials.json`,
`~/.codex/auth.json` — the same two paths the welcome panel probes) the z3 server (a) runs the existing
`zcp agent mark-oauth <agent>` (writes `ZCP_AGENT_OAUTH_<SUFFIX>=true`, idempotent) and (b) calls
`providerRegistry.refresh()` so the provider snapshot flips now instead of in ≤5 min; the card reads
"Authorized" from a live feed. Nothing credential-shaped enters the chat. The terminal is the UI.

## 4. Threat model (what S7 does and does not protect)
- The agent process and every paired project member share the container home: a credential file is project-wide. S7 does not change that; it is the platform's container model (one zcp per project).
- Authorization code and device URL travel over the terminal RPC (`terminal.write`/`attach`) exactly as they would in any terminal; they never enter a thread, a feed, or the ledger. The auth feed carries booleans and `providerAuth` only.
- The watcher mutates (flag write) only after a fresh provider verification; a planted or stale file cannot flip the flag by itself.
