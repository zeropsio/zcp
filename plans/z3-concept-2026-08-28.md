# Concept: Zerops Code (z3) — how to continue past the POC

Date: 2026-08-28
Scope: `../z3` (branch `zerops-poc`, fork of pingdotgg/t3code — "z3"), its POC ledger
(`docs/internals/zerops/{map,verified,hacks,questions}.md`), zcp branch `feat/z3-container`
(`7c98c793`), zcp specs (`spec-welcome-mode.md`, `spec-workflows.md §4.3/§5/§8`,
`spec-local-dev.md`), `plans/research/zcp-install-delivery-architecture-2026-08-24.md`, zcli
branch `kh-zcp-multi-vpn`, and the FE pool-claim code in `../frontend-legacy`.
Goal: agree the shape of the real implementation — connection, placement/delivery, git model,
client flow — under one hard constraint: **no Zerops platform/backend changes now.** The z3
server, the zcp binary, and the z3 clients are ours to change freely.

Labels: **Verified** (live probe or repo source) · **Candidate** (supported by the mechanics, not
built) · **Decision** (owner's call) · **Later** (known, deliberately out of scope).

---

## 0. What z3 is

A control surface for coding agents that live inside Zerops `zcp` containers. The z3 *server*
runs in the container next to `claude`/`codex` and the `zerops_*` MCP tools; the *clients* are
thin (web and desktop are one bundle — Electron only proxies to it; mobile shares the
connection/state layer). z3 is a new interface with a different flow, not a replacement: the web
GUI, zcp in code-server, and zcli all keep existing.

Upstream's one architectural rule, which we keep: *remoteness is expressed at the connection
layer, never by splitting the runtime.* One running server = one environment = one Zerops project.

## 1. Findings that shape the design

### Connection (Verified)
- The whole chain works from a browser with no VPN and no SSH: Zerops API (CORS `*`) → container
  public origin → pairing → RFC 8693 exchange → 30-day bearer → 5-min WS ticket → `wss://`.
- Today's mint is `GET /z3-pair/<VSCODE_PASSWORD>` on the 8080 origin, proxied to a loopback
  sidecar that shells `t3 auth pairing create`. It works, and it is the weak spot: a shared,
  long-lived container secret doing a per-user job; revocation = rotating the code-server password.
- The z3 server already contains the template for "external identity → session": the cloud-mint
  path verifies a third-party-signed proof, checks the subject against a stored id, and mints a
  2-minute pairing grant that the client exchanges normally. The session `subject` is a free-form
  string; there is no `revokeBySubject` yet. Auth policy is computed once from `--host`; a
  `0.0.0.0` bind already resolves to `remote-reachable`.
- Two pre-existing exposures that public HTTPS turns live: the WebSocket upgrade never checks
  `Origin` (cross-site WS hijack with the session cookie), and production CORS is wildcard.
- `t3 serve` has no base-path support: one URL helper overwrites `pathname`, the HTTP contract
  bakes `/api`, `/oauth`, `/.well-known/t3/environment`, the static catch-all and `/ws` are
  root-literal. ~5 contained edits, but one is a cross-package contract change.
- `--auto-bootstrap-project-from-cwd` registers the cwd as a project at startup — the direct fix
  for "connecting lands in an empty environment".
- Terminal: PTY over the same WS, `cwd` client-supplied, scriptable *in* (write bytes) but not
  framed *out* (no OSC 133, no exit codes). There is no exec RPC; project scripts are typed into
  a PTY.
- Desktop has no renderer of its own — the Electron window proxies to the same web bundle.
  Desktop-unique code is Electron-main (24k LOC): local server spawn, SSH launch, Tailscale,
  deep links, updater, keychain, webview preview. With the server always remote, only keychain,
  deep links, updater and the preview webview still matter.
- Mobile uses Bearer + Relay targets only; the fork's Zerops screens prefill the host of the
  existing Bearer flow — the user still types a pairing code.

### Git (Verified)
- t3 uses git for: per-turn checkpoints (baseline + capture, hidden `refs/t3/checkpoints/…`,
  throwaway index, parentless commits, destructive restore), diff/review (recomputed from refs;
  one `diff --no-index` per untracked file), thread worktrees (`~/.t3/worktrees/<repo>/<branch>`
  on the *server's* disk, branch `t3code/<hex>` renamed after the first turn), a 30 s status
  poller per open cwd, repo identity (bypasses the driver), PR/source-control via `gh`/`glab`
  (templates read from the object DB), and a commit→push→PR "stacked action" with LLM commit
  messages. Cost ≈ 12–20 git processes per turn plus a full workspace rescan.
- Seams: ~90 % of git goes through one runner as `git -C <path> …` (path in argv, process cwd
  irrelevant) — SSH-friendly. A second raw spawner (real cwd, `GIT_TRACE2_EVENT` temp file +
  local `fs.watch`) exists for streaming hook progress. Path-returning calls (`--show-toplevel`,
  `--git-common-dir`, `worktree list`) are stored and handed to providers/terminals as local cwd.
- Providers (`claude`, `codex`, …) are local child processes with `cwd = worktreePath ??
  workspaceRoot` and full permissions — the agents run their own git in the tree, outside every
  abstraction.
- The fork's own note (H-14): "inherited from upstream, which never had network-mounted
  workspaces"; Q-05 (checkpoint cost on a real repo) is unmeasured — 8 files / 60 ms only.

### zcp side (Verified)
- The repo lives on the dev service (`/var/www/.git` inside *its* container); zcp has no git
  state; zcp sshfs-mounts each service at `/var/www/<hostname>`; agents run in zcp with cwd on
  the mount; deploy = `zcli push` over SSH *on the source service*; identity is repo-local
  set-if-absent; git-push setup stores the PAT as a service-scope secret; delivery is derived
  from `GitPushState`; mount-side `git init` is forbidden (root-owned dirs via SFTP).
- Pool claim is not FE magic: registration sends `claimZcpPool: true`, the response carries
  `zcpClaimed`; on exhaustion the FE creates a project and imports the first-class recipe
  `zeropsio/zcp` (platform-owned). Both are plain REST — a z3 client can do the same.
- Adding a declared port to a running service = redeploy = container replacement. `ports` is
  not a top-level import key. `zcp@1` recipe/ports/`startCommands` are platform-owned.
- `install.sh` runs as `run.initCommands` on every container start and fetches `latest`;
  `zcp init` re-renders nginx and can create supervised units dynamically (`zsc unit create`,
  the sshfs primitive). `POST /service-stack/{id}/restart` exists. So **a restart is a zcp
  upgrade + full re-init, with no SSH and no recipe change.**
- zcli: multi-VPN and `zcli zcp` exist only on branch `kh-zcp-multi-vpn` (13 ahead of `main`),
  need root, and have no VPN-less path. Mobile/unattended/non-root are declared out of scope.

## 2. Design

### 2.1 One door: the container's public origin, Zerops identity as the only credential

**Flow (Candidate)**
1. Client signs into Zerops (email/password + TOTP, later GitHub OAuth — FE patterns
   re-implemented in `packages/client-runtime/src/zerops`).
2. Client lists projects, finds the `zcp@1` service by *type*, derives the container origin from
   the service's `zeropsSubdomain` (first line) — never the region constant.
3. Bootstrap: client calls the z3 server with its **Zerops access token**. The server (new
   bootstrap method `zerops-identity`, copied from the cloud-mint shape): validates the token
   against the Zerops API, confirms the user is a member of *this* project (the container knows
   its own `projectId` from env), mints a short-TTL pairing grant with `subject = <zerops user
   id>`, and the client runs the ordinary RFC 8693 exchange → 30-day bearer → WS ticket.
4. On each WS connect the server re-validates membership (cached a few minutes); a user removed
   from the project loses access at the next connect; `revokeBySubject` gives per-user
   revocation.

**Hardening in the same slice:** `Origin` allowlist on the WS upgrade (hosted z3 origins +
desktop scheme), CORS allowlist instead of `*`, bearer-only for the hosted client (no
cross-site cookie), DPoP-bound tokens for the hosted web (already supported server-side).

**What disappears:** `/z3-pair/<password>`, the sidecar mint, the client ever reading
`VSCODE_PASSWORD`, and every operator step that needed SSH. Upstream pairing codes stay in the
code for non-Zerops environments (fork discipline); they are simply not on the Zerops path.

**Operators use the same door.** With membership + `terminal:operate` we already drive a PTY
over WS. Add a framed **exec RPC** (new scope `exec:operate`; spawn, stream, return exit code —
or OSC 133 sentinels around a PTY write) so scripts, not only humans, can run commands in the
container. That is the concrete form of "use the WebSocket terminal instead of VPN/SSH". zcli
can adopt it later with an Integration Token through the same bootstrap. **VPN is out of the
product and out of the POC's operating path.** Multi-VPN stays what it is: a developer
convenience on a zcli branch, not a prerequisite.

### 2.2 Placement and delivery: z3 rides in the zcp binary, served under a path on 8080

Two options; the difference is who can put z3 into an *existing* container.

| | **P — path `/z3/` on the existing 8080 origin** | **O — own declared port 3773** |
|---|---|---|
| z3 server change | base-path support (~5 edits incl. one contract change) | none |
| zcp change | `zcp init z3`: fetch pinned bundle, start unit, nginx `/z3/` location *outside* the cookie gate with WS upgrade, `/healthz` | same minus nginx; **plus** a recipe change |
| Recipe / platform | **none** — everything ships in the zcp release | port + `startCommands` in the platform-owned `zcp@1` recipe |
| Pool container without z3 | client calls the **restart API** → boot pulls latest zcp → z3 up. Self-service, no operator | operator redeploys with the mirror recipe, per container |
| New project from z3 (first-class recipe import) | container boots with latest zcp → z3 present | container has no 3773 until someone redeploys |
| Auth isolation | z3 has its own auth; the location bypasses `__zcp_auth` | separate origin = separate cookie jar |

**Recommendation (Decision): P now, O when the platform bakes z3 into the image.** P is the
only option that satisfies "no platform change" *and* keeps the pool flow self-service. It also
aligns with the install-delivery research: upgrade = restart, version pinned at container start
(zcp pins the z3 bundle version the way it pins `t3@0.0.35` today).

Mechanics: `zcp init` gains a container-only step that (a) fetches the pinned z3 server bundle
(our build of the fork — GitHub release asset of `z3`, or a scoped npm package;
Decision), (b) starts it via the existing supervised-unit primitive with
`--auto-bootstrap-project-from-cwd`, `--host 127.0.0.1`, base path `/z3`, base dir
`/home/zerops/.t3`, (c) renders the nginx location, (d) writes the init-complete marker;
`/healthz` moves into the z3 server or stays as the tiny sidecar route (Decision — the sidecar
loses its mint either way). Client "predates" detection stays (302/404 on `/z3/…`) and turns
into a "Enable Zerops Code → restart" action.

Risk: a second boot-path network fetch (same class as `install.sh`; mitigate by shipping the z3
bundle inside the zcp release so one fetch covers both). Thread history (`state.sqlite` under
`/home/zerops/.t3`) survives restarts and dies on redeploy — with P, redeploys become rare.

### 2.3 Git: one z3 project per Zerops project; git runs on each dev service, files go through the mounts

**Mapping (Candidate — see §2.6 for the full model):** `project.workspaceRoot = /var/www` (the
mount base — the agent's cwd, from where it sees every service). The repos are the mounted dev
services `/var/www/<hostname>`, each backed by `/var/www/.git` *on its own host*. z3's git layer
therefore becomes **multi-repo**: the checkpoint/diff/status driver enumerates the mounted dev
services (from the zcp topology, §2.6, not by scanning for `.git`) and runs each repo's git on its
host — `ssh <hostname> git -C /var/www …` — grouping results by service. A turn that touched two
services yields two checkpoints and a diff grouped by service.

**Git executor:** replace the process runner behind the git driver with an SSH runner
(`ssh <host> git -C /var/www …`, one multiplexed ControlMaster connection per host — without it
12–20 handshakes per turn make this slower than sshfs), apply a path map at the driver boundary
for every path-returning call, put the throwaway `GIT_INDEX_FILE` in the host's tmp, route the
repo-identity resolver through the driver, and drop the trace2 hook-progress streaming (the
raw spawner). Status-poll and detection TTLs get tuned for round-trips.

**Worktree mode is off on Zerops** (thread env mode = local only). A worktree per thread has
no image on the platform: the served root is `/var/www`, and the agents/terminals would need
those directories locally. Parallel threads on one repo → parallel dev services, each with its
own mount (Later).

**Ownership split with zcp (Decision):** the repo rules stay zcp's — init over SSH-exec,
identity set-if-absent, PAT as a service secret, delivery derived from `GitPushState`, no
mount-side `git init`. z3 owns *turn-level* history: checkpoint refs, per-turn diff, restore,
review. Commit / push / deploy remain the zcp workflow, triggered from z3 (by the agent through
MCP, or by a z3 action that runs the zcp CLI). z3's stacked commit→push→PR action on Zerops
projects either delegates to zcp's git-push flow or is hidden — two commit pipelines is the one
thing not to have.

**What zcp gains:** per-turn checkpoint refs on the dev service — exact "what did the agent
change this turn", rollback, and a candidate source for the close-mode commit (squash the turn
refs into the real commit). Worth a spec section once measured.

**Gate before building the executor (PROVE):** answer Q-05 on a realistic repo (thousands of
files) on `z3probe`: checkpoint capture + status (a) over the sshfs mount, (b) over SSH on the
host; and the workspace rescan over sshfs. If sshfs is within budget, the SSH executor becomes
an optimisation, not a prerequisite — the order of streams below assumes it is needed.

Agents' own git is unchanged: they run in zcp with cwd on the mount, as zcp does today. sshfs
writes are write-through, so the host-side checkpoint sees the agent's edits (verify with the
mount's cache options in the PROVE step).

### 2.4 Client flow

**New user:** register inside z3 (FE registration re-implemented; `claimZcpPool: true`) →
`zcpClaimed` → wait for the project's zcp to be `ACTIVE` (direct reads, not the ES searches) →
"predates z3"? → restart via API → poll `/healthz` → identity bootstrap → land in the
project-level thread with zcp's onboarding prompt. The FE wizard/bridge and the code-server
agent panel are not on this path; z3 *is* the onboarding surface here.

**Existing user:** project picker (candidates by service type; several `zcp@1` in one project →
pick) or **New project** = project create + first-class recipe import `zeropsio/zcp` → `ACTIVE`
→ connect (a new container boots the latest zcp, so z3 is already there). Pool exhaustion
takes the same path.

**Inside a project:** the project starts with zcp alone; everything else appears because the
agent created it through `zerops_workflow` / `zerops_import`. How that growth reaches the
client is §2.6.

**Agent authorization** (Claude/Codex OAuth): today the FE dialog + `zcp agent mark-oauth` +
platform-written `ZCP_AGENT_OAUTH_*`. In z3 the device-code login happens in the z3 terminal;
how the authorization state is reflected (the 5-state matrix in `spec-welcome-mode.md §3`) is
open — see §4.

### 2.5 Clients

- **Web** — the product surface. Hosted static bundle (any static host; a Zerops static service
  is the obvious one). Zerops session in IndexedDB/localStorage, bearer sessions per environment.
- **Desktop** — same bundle. One smoke slice: build our fork's Electron shell with the remote-only
  configuration (drop local spawn/SSH/Tailscale from the Zerops build), keep keychain, deep link
  scheme, updater, preview webview. Purpose: learn the cost of carrying it; not a product priority.
- **Mobile** — already runs on an iPhone (personal-team build). The identity bootstrap removes the
  manual pairing code; the change lands in shared `client-runtime`, mobile mostly inherits it.
- Fork discipline holds: additive changes, upstream rebase stays possible; `AdvertisedEndpointProvider`
  is where a Zerops endpoint provider belongs if we ever need one (we do not for P).

### 2.6 Teaching z3 how zcp works: the project grows, the client shows the growth

**How zcp works (Verified, `spec-workflows.md`):** agents run inside zcp with the zcp MCP
attached. A fresh project holds only zcp. From the user's intent the agent runs *bootstrap*
(discover → provision → close: plan confirmed by the user, `zerops_import` creates services —
standard mode = `<name>dev` + `<name>stage` + managed deps — dev runtimes get sshfs-mounted at
`/var/www/<hostname>` and `git init`ed on their host, evidence written to
`.zcp/state/services/<hostname>.json`), then *develop* (a per-PID work session: code → deploy →
verify → derived auto-close; close-mode, git-push, build integration as orthogonal records).
Every workflow-aware tool response carries the `StateEnvelope` (phase, services with mode /
status / closeMode / gitPushState / stage pair, work session with deploy + verify attempts,
bootstrap step). `zerops_workflow action="status"` is the recovery primitive.

**Concept mapping (Decision):**

| zcp | upstream z3 | on Zerops |
|---|---|---|
| Zerops project = one zcp container | environment (one server) | 1:1 — the environment list *is* the project list |
| mount base `/var/www` | project (`workspaceRoot`) | **one z3 project per Zerops project**, root `/var/www`; never one per service |
| agent process + zcp MCP; work session per PID | thread = provider session | **thread = conversation = agent PID = zcp work session**; cwd is always `/var/www` — exactly as zcp runs the agent today, never per-service |
| services appearing (dev/stage pairs, managed deps), mounts | — | **new: Service map** — live panel, grouped Runtimes / Data / Infra, per service: type, status, URL, mounted, live process, dev↔stage pair |
| phase / bootstrap step / work session / close state | — | **new: Lifecycle strip** in the thread header — `bootstrap 2/3 provision` → `developing kanbandev` → `deployed ✓ verified ✓` → `task complete` |
| `zerops_*` tool calls in the agent stream | generic tool-call cards | **new: Zerops-aware cards** — plan (services to create, user confirms), import (per-service process progress), mount, deploy (build progress → URL chip), verify (HTTP 200 ✓), subdomain, errors with the structured code |
| mounted dev repos | checkpoints / diff / review | per mounted repo, grouped by service (§2.3) |
| Data Console (in zcp) | — | embedded from the same origin (`zcp studio console serve`) |
| launch-production → separate prod project (no zcp there) | — | a link + status on the service map, never an environment |

**Where the data comes from (Verified — the seam already exists on `main`):** `zcp studio` is a
frozen CLI seam built for the Zerops Studio VS Code cockpit — `topology` (the same
discover+classify JSON as `zerops_discover`), `watch` (live topology-change events over
websocket, as JSON), `console serve` (Data Console), `deploy`, `sync-env`. Token-blind, never
MCP, never raw `.zcp/state`. Two feeds, both additive to z3:

1. **Topology feed** — the z3 server runs `zcp studio topology` + `watch` per environment and
   republishes them to clients as a Zerops state stream (new contract slice). This covers changes
   this thread did not make (another thread, the web GUI, zcli).
2. **Lifecycle feed** — the z3 server already sees every tool call and result in the provider
   stream; a Zerops-aware reducer extracts the `StateEnvelope` from `zerops_*` tool results and
   publishes it per thread. No zcp change: the envelope is designed to be reconstructed from
   tool output, and it is per-PID by construction — exactly the thread's own view. Gaps (a
   thread whose last envelope is stale) are closed by the strip offering "refresh" = the agent
   calling `action="status"`.

**Who acts (Decision):** the client renders **state**; the agent performs **mutations** through
MCP. Service-map quick actions ("Deploy", "Show logs", "Scale", "Add Redis") are prefilled
prompts into the thread, not client-side API calls — zcp's invariants (check-before-mutate,
busy-truth, deploy gates, credential contract) live in one place and the client must not grow a
second orchestration path. Client-direct is only what is read-only or already caller-bound:
open a URL, browse/edit files through the mounts, a terminal on a service (`ssh <host>` in the
PTY), tail logs with the user's own token, the Data Console. `zcp studio deploy` exists for a
later "deploy from the UI" button once the confirmation UX is designed.

**Walk-through — "vytvoř mi kanban":**

| Agent (zcp) | User sees in z3 |
|---|---|
| discover: proposes `kanbandev` + `kanbanstage` (nodejs) + `db` (postgresql), asks for confirmation | **Plan card**: three services with types/modes; Confirm / Change (a reply, still text to the agent) |
| provision: `zerops_import` → processes; `zerops_mount kanbandev`; env discovery | Service map gains three rows in *creating* → *running*; `kanbandev` gets a *mounted* badge; file tree shows `kanbandev/`; import card with per-service progress |
| close: evidence written; develop starts | Lifecycle strip: `infrastructure ready · 3 services` → `developing kanbandev` |
| writes `zerops.yaml` + code in `/var/www/kanbandev/` | files change under `kanbandev/`; turn checkpoint on the `kanbandev` repo; diff grouped by service |
| `zerops_deploy kanbandev` → build → subdomain; `zerops_verify` | deploy card with build progress → URL chip; service map row shows *Open*; verify card `HTTP 200 ✓`; strip `kanbandev deployed ✓ verified ✓ · kanbanstage pending` |
| close-mode decision; git-push setup asks for a PAT | **decision card** (auto / manual); **credential card** — the token goes from the card to the service secret through the z3 server + zcp CLI, never through the conversation (credentials are user-owned, the agent never fabricates or sees them) — Candidate, needs a zcp verb |
| auto-close derived | strip `task complete`; next-task shortcut |

**Multiple threads:** each is its own PID and work session; bootstrap is exclusive per project.
The strip shows "infra session held by thread X" when another thread is bootstrapping (from the
envelope/registry), so the user is not surprised by a refusal.

**User questions, one card for every agent (Verified seam):** T3 already normalises "the agent
asks the user to choose" into provider-agnostic runtime events `user-input.requested` /
`user-input.resolved` carrying `UserInputQuestion {question, header?, options[{label,
description}], multiSelect?}`; Claude Code's `AskUserQuestion`, Codex's
`item/tool/requestUserInput` and Grok's ask all map into it, and the web client renders it.
What we add: card quality (multi-select, descriptions, free-text "Other", waiting state); zcp
asking structurally *always* under z3 — the z3 server sets `ZCP_HARNESS=z3` on the provider
process and zcp's atoms/error suggestions drop today's "when your harness exposes it" hedge for
plan confirmation, route choice, close-mode, launch scope, blockers; credential-class asks
render the credential card instead (the secret never becomes an answer the LLM reads).

## 3. What the POC built that this concept drops

| POC piece | Verdict | Reason |
|---|---|---|
| `/z3-pair/<password>` + sidecar mint (H-02, H-15, H-16) | replaced | identity bootstrap; no shared secret, no CORS-wildcard mint URL, no rate-limit guesswork |
| Own port 3773 + `deploy/zcp-container.yml` mirror | deferred (Option O) | needs the platform-owned recipe; P ships in the zcp binary |
| Local workspace `/home/zerops/app` (H-14, H-17, H-22) | replaced | a second copy of the code outside zcp's model; projects are mounts, git runs on the host |
| `npx t3@0.0.35` at boot (H-05) | replaced | our fork's pinned bundle, fetched by `zcp init` |
| Client reads `VSCODE_PASSWORD` (H-20) | gone | nothing on the client path needs it |
| VPN / multi-VPN in any flow (H-03, H-09) | out | one door over public HTTPS; exec RPC covers scripts |
| `t3 service` background install | unused | the container supervises z3 via a unit |

Kept from the POC: URL derivation from `publicZone`/`zeropsSubdomain` (H-01), the shared Zerops
session client (H-04), candidate grouping by service type, the `/zerops` page, `/healthz`
semantics (`initComplete` + `z3Up`), theme/branding.

## 4. Open questions and live verifications (PROVE list)

1. **Membership check shape** — which Zerops API call proves "this user may use this project"
   (`/user/info` → `clientUserList` vs `project.clientId` + role; or a 200 on `GET /project/{id}`
   with the user's token). Verify with two accounts, one non-member.
2. **Restart = upgrade** — `POST /service-stack/{id}/restart` on `z3probe`, confirm `install.sh`
   re-ran and the zcp version moved; confirm a `zsc unit create`d unit is recreated by init.
3. **Q-05 matrix** — checkpoint capture, `status --porcelain=2`, and the workspace rescan on a
   realistic repo: sshfs vs SSH-on-host; with and without ControlMaster.
4. **sshfs write visibility** — an agent edit through the mount is visible to host-side
   `git add -A` immediately (cache/writeback options of the mount).
5. **Base path** — WS upgrade through nginx under `/z3/`, Vite `base`, contract prefix; no
   collision with code-server paths on the same origin.
6. **z3 bundle distribution** — release asset vs scoped npm; size; Node 24 in the container.
7. **Registration API** — endpoint, verification/captcha steps the FE performs, GitHub OAuth
   signup with the claim (the FE's `github-auth` effect carries it).
8. **Agent OAuth inside z3** — device-code flow in the z3 terminal; how `zcp agent mark-oauth`
   / `ZCP_AGENT_OAUTH_*` are reflected without the FE dialog.
9. **Two clients on one container** (Q-07) — laptop + phone on the same threads.
10. **History durability** — `state.sqlite` across restart (expected: survives) and redeploy
    (expected: lost); whether to move the base dir to a persistent path (Later).
11. **`zcp studio watch`** — event shape, latency after an import, behaviour across the ES lag
    (`spec-workflows.md §3.5`); whether it needs a direct-read refresh on mutation events.
12. **Envelope extraction** — the `StateEnvelope` is recoverable verbatim from the provider
    stream's tool results for Claude Code and Codex (text vs structured content); size per turn.
13. **Multi-repo checkpoints** — cost of N mounted repos per turn on their hosts; the topology
    feed as the repo enumerator (never scan `/var/www` for `.git`).

Later, recorded and deliberately not now: cost / scale-to-min + wake-on-connect (H-11),
history off the container (H-10), dependency topology (H-12), `t3code:` prefix / URL scheme
rename (H-13).

## 5. Streams and order

Each stream is its own `/flow` run; zcp-side work lands with a new `docs/spec-z3.md` (the
reason `feat/z3-container` is parked today).

| # | Stream | Depends on | Rough size |
|---|---|---|---|
