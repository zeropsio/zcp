# Slice brief: S5 — Flow-eval scenario pack for the onboarding trigger + existence/parse test

Self-contained. Cite docs/spec-onboarding.md §1-§3 (promoted at GATE 1). Depends on S3
landed (scenario expectations reference the shipped fork copy).

**Outcome** (observable): five behavioral-eval scenario files exist under
`eval/behavioral/scenarios/`, each passing the scenario-manifest lint AND parsing through
the real scenario parser; a new `internal/eval` test pins their existence and parseability.

**Allowed scope**
- Files (write-set): `eval/behavioral/scenarios/onboard-trigger-fresh.md` ·
  `eval/behavioral/scenarios/onboard-trigger-variant.md` ·
  `eval/behavioral/scenarios/onboard-trigger-negative.md` ·
  `eval/behavioral/scenarios/onboard-populated.md` ·
  `eval/behavioral/scenarios/onboard-guided-on.md` ·
  the guided preseed script placed wherever existing preseed scripts live (check
  neighboring scenarios' `preseedScript` references for the convention; if none exists
  yet, co-locate under `eval/behavioral/scenarios/` with a clearly-named `.sh`) ·
  `internal/eval/onboarding_scenarios_test.go` (new)
- Explicitly excluded: every existing scenario, the manifest lint test, any eval runner
  code. Authoring + parse-pinning only — RUNNING flow-eval is not part of this slice.

**Contract**
- Manifest (enforced by `internal/content/eval_scenario_manifest_test.go`): keys `id`,
  `description`, `seed`, `tags`, `area`, `retrospective`; `id` == filename minus `.md`.
- The REAL parser (`internal/eval/scenario.go`) additionally enforces: the seed enum
  includes `building` alongside empty/imported/deployed/settled; ANY non-`empty` seed
  REQUIRES a fixture reference. READ `internal/eval/scenario.go` + 2-3 existing scenario
  files first and mirror their structure/voice exactly; discover what fixtures exist
  before writing `onboard-populated` — reuse an existing deployed-seed fixture referenced
  by a neighboring scenario. If NO existing fixture fits, fall back to `seed: empty` +
  a `preseedScript` that imports a minimal service, and say so in the report.
- Guided mode is NOT a scenario field; tags are descriptive only. `onboard-guided-on`
  uses the supported `preseedScript` mechanism (runs after init, before the agent spawns)
  with a script that runs `zcp init --guided`, plus a deterministic `userPersona` that
  chooses "build an idea" at the fork (mirror how existing scenarios express personas).
- Scenario intents (expectations quote the spec contract: playbook fetch via
  `zerops_knowledge uri="zerops://playbooks/onboarding"`, status-then-discover state read,
  the three option labels, no mutating call before user choice):
  1. `onboard-trigger-fresh` (seed: empty): exact phrase "onboard me to Zerops" →
     playbook fetch + status/discover reads + FRESH three-option fork; NO
     bootstrap-commit/import/deploy call.
  2. `onboard-trigger-variant` (seed: empty): "get me started with Zerops, I'm new here"
     → same expectations.
  3. `onboard-trigger-negative` (seed: empty): "help me get started with PostgreSQL" →
     NORMAL routing; no playbook fetch, no onboarding fork.
  4. `onboard-populated` (existing deployed fixture per above): exact phrase → populated
     opening (service summary + **Continue this project** present).
  5. `onboard-guided-on` (seed: empty + guided preseed + persona): exact phrase → fork
     first; the "build an idea" choice hands off to guided.
  If any expectation cannot be expressed in the existing scenario format, STOP and report
  blocked with the specific gap — do not invent new manifest fields.

**RED test list**
- `TestOnboardingScenarios_ExistAndParse` — layer: unit (`internal/eval`,
  onboarding_scenarios_test.go). Table over the five scenario IDs: each file exists under
  `eval/behavioral/scenarios/` and parses through the package's real scenario
  parser/loader (use the same entry point neighboring eval tests use) with the expected
  `id` and `seed`. On the slice base (files absent) this FAILS file-not-found — the
  slice's replayable RED. After authoring, it passes.

**Protocol**: RED → GREEN → REFACTOR.
1. Write `TestOnboardingScenarios_ExistAndParse` first; confirm RED:
   `go test ./internal/eval -run TestOnboardingScenarios_ExistAndParse -short -count=1 -v`
2. Author the five scenarios (+ preseed script); test green. Then:
   `go test ./internal/content -run TestEvalScenarioManifest -short -count=1 -v`
3. `make lint-fast`.

**BUILD addendum (flow)**
- Independent oracle: expectations quote the spec/fork literals, never a paraphrase.
- Table-driven, `Test{Op}_{Scenario}_{Result}` naming; layer-matrix lines
  (`go test ./internal/eval/... -short -count=1`, `go test ./internal/content -run
  TestEvalScenarioManifest -short -count=1`).
- `make lint-fast` clean before done.
- Do NOT run any `git commit`/`branch`/`stash`/`push`.

**Report contract**: RED output+exit · GREEN output+exit · files created (exact) ·
layer-matrix lines · fixture decision note (which fixture reused, or the preseed
fallback + why).

**Stop conditions**: manifest/parser format cannot express an expectation · no usable
fixture AND preseed fallback also inexpressible · scope drift · repeated unexplained
failure.
