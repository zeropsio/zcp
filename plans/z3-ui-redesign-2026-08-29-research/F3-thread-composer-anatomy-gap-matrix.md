# Gap fill — z3 thread + composer anatomy, gap matrix vs brief §7/§8

## Summary
Inventoried z3's thread/composer/chrome surfaces (30+ files, all read via cat -n/grep, no edits). Core finding: most surfaces already use semantic shadcn-style CSS tokens (text-foreground, bg-card, --error-surface), not hard-coded Tailwind palette classes — retheming is mostly a token swap. Two exceptions: Sidebar.tsx (10 hardcoded red/amber/sky/blue/emerald classes driving thread-status semantics — exactly the surface the Zerops 'status dot + label' vocabulary should own) and RightPanelTabs.tsx (violet/red/zinc/emerald PR-status tinting). The Zerops card system (ZeropsToolCard, 7 kinds: error/deploy/verify/import/mount/subdomain/plan) only renders for a SETTLED tool result inside the collapsible 'N tool calls' fold (MessagesTimeline.tsx:2599-2606, WorkGroupSection:1377-1418) — confirmed by reading the code path: the LIVE path (LiveWorkEntryTimelineRow:1500) never calls decodeZeropsCard, it only shows an icon+text label. So every 'X-with-progress' requirement in brief §7 (import-with-progress, deploy-with-build-progress) has NO live-updating card — progress during the call is invisible except via the separate ZeropsServiceMap/feeds poll, and the settled card appears after, inside the fold. The brief's 'credential card (S6)' — a secret-value form bypassing chat text — does not exist anywhere; a credential error only ever renders through the generic 'error' card kind. 'infra session held by thread X' and a post-completion 'next task' shortcut are absent (zero code hits). §8's question-card requirements (multi/single select, Other free-text, keyboard nav, 'waiting for you' in both card and strip) are FULLY implemented already (ComposerPendingUserInputPanel.tsx, strip.ts:122-124) — this is the one area ahead of the brief. T3-era vocabulary (worktree, T3 Connect, environment, Alpha/Dev/Nightly build art) permeates chrome (CommandPalette groups, docs/user/*.md, SidebarStageBackdrop.tsx) and is structurally live: the client-side 'Worktree' env-mode option (BranchToolbarEnvModeSelector.tsx) is never hidden even though server-side ZeropsPolicy.worktreesAllowed=false silently downgrades it — a dead/misleading option with no client-visible capability gate. Motion: composer/timeline avoid continuous repaint per AGENTS.md:155, using compositor-safe patterns (WorkingTimer direct-DOM ticking, animate-status-pulse opacity-only) — except a 2.2s-infinite transform sweep on every LIVE tool-call row (live-activity-focus, index.css:461-491) that is the same kind of effect Sidebar.tsx explicitly rejected elsewhere for repaint cost. auto-animate is used only in Sidebar/LegacySidebar list reordering, never in chat/composer. The TurnPlanTimelineRow (segment-bar + ✓/●/○ steps, :1221-1316) is the best existing anchor for the Zerops '17px process-step circles' vocabulary — closer than ZeropsToolCard's 'plan' kind, which is a third, separate 'plan' concept (workflow step X of Y) colliding in name with T3's Plan-mode and ProposedPlanCard.
