# Gap fill — agent-auth continuity (S7 worktrees, GUI zagent card)

## Summary
z3's S7 agent-auth work lives on two unmerged worktree branches (wt/s7 = server feed/IO, wt/s7-web = contracts+web card), 6 commits each, both drifted 39-53 commits behind main. Together they build a NEW third-value state machine (5 values: not-authorized/reconnect/local-only/authorized/authorized-token, refined by a live providerAuth check into a 6-presentation UI) mirroring the Zerops GUI's own `zagent-service-card` component 1:1, plus z3 ALREADY has an unrelated 'Authenticated/Not authenticated' surface for the same credential in apps/web/src/components/settings/ProviderInstanceCard.tsx + providerStatus.ts — so z3 will ship TWO different auth-status renderings of the same fact once wt/s7-web lands. The GUI's 'AUTHORIZED' text is a CSS text-transform:uppercase on literal string 'Authorized' (zagent-service-card.feature.html + .scss, colors #2e7d32/#b26a00 light, #56d364/#e8a33d dark) — not a hardcoded caps string, resolving the prior reader's search miss. The GUI's unauthorized dot pulses via a real `animation: zagent-auth-pulse 2.4s infinite` keyframe, which collides with z3's own house rule (AGENTS.md: 'No continuously repainting animations; they peg the GPU'); the GUI's OWN authorized-state dot already uses the fix pattern needed (a static box-shadow halo, no animation). A real naming collision exists: z3's composer already ships a user-facing 'Full access' label (ChatComposer.tsx:299, per-turn approval mode) that will read, in a Zerops-branded client, as the exact same string the GUI's project-role chip renders ('Full access' = ADMIN/OWNER, project-access-chip.component.ts) — two unrelated permission concepts, identical copy. Mobile has zero Zerops-specific code on either branch or main — confirmed absent. Collision risk for a redesign: packages/contracts/src/zerops.ts and rpc.ts are touched by BOTH wt/s7 and wt/s7-web (the commit message itself flags this as a to-be-reconciled duplicate); ZeropsPanel.tsx and ChatView.tsx are the exact mount points a redesign changes and are already mid-diff on wt/s7-web.

## 3. Who owns the mental model

**Verified ownership chain, GUI-side**: the running-service detail page's `zagent-service-card` (`Zerops Control Plane` box, live screenshot `06-service-detail.png`) is the canonical 'is my agent authorized' surface for a user managing a service from the dashboard — it is reached from project → service, shows the auth row alongside the four access buttons, and every mutation (Trigger/Re-trigger/Revoke/Set API token) is a popover action originating from this exact card (`zagent-service-card.feature.html:246-337`).

**z3-side, post-S7, there will be THREE surfaces answering a version of the same question, none of which is S7's own creation for two of them**:
1. `ZeropsAgentAuthCard` (wt/s7-web, new) — thread overlay + panel row, scoped to `claude-code`/`codex` only, answers 'can this specific agent-CLI act right now inside this Zerops container'.
2. `ProviderInstanceCard.tsx` + `providerStatus.ts` (main, pre-existing, untouched by S7) — the Settings → Providers page, scoped to *any* configured provider driver, answers 'is this provider instance's credential currently valid' via `getProviderSummary`: `Authenticated · <label>` / `Not authenticated` / `Needs attention` / `Unavailable`, using semantic Tailwind tokens `bg-success`/`bg-warning`/`bg-destructive`/`bg-muted-foreground/50` (`providerStatus.ts:7-20,51-63`) — for the SAME `claude-code`/`codex` drivers when running in a Zerops container, this is very likely reporting the same underlying `providerAuth`-shaped fact z3's own S7 code introduces as `ZeropsProviderAuthState` (`contracts/src/zerops.ts` 'A live check against Claude/Codex's own account endpoint').
3. `ProviderStatusBanner.tsx` (main, untouched by S7) — the thread's OWN 'no authenticated provider' banner, literally rendered in the exact same overlay stack `ZeropsAgentAuthCard` was just wired beside (`ChatView.tsx` diff, both under `pointer-events-none absolute inset-x-0 top-0`), reading `<Provider> is unauthenticated` / `Sign in via the CLI to authenticate again.` for the *active provider of the current thread* — not Zerops-scoped, but firing on the identical underlying condition (`status.auth.status === 'unauthenticated'`, `ProviderStatusBanner.tsx:34`) that `ZeropsAgentAuthCard`'s `needs-reauth` presentation also fires on (`agentLogin.ts:81-83`).

**What z3 must not duplicate**: (a) the GUI's per-service 4-action button row (Web Terminal/SSH/Cloud IDE/Desktop IDEs) — that's dashboard-level infrastructure access, orthogonal to agent CLI login and already fully owned by the GUI card; z3 has no reason to grow equivalent buttons. (b) A second 'is the provider driver authenticated' readout — `ProviderInstanceCard.tsx`'s `Authenticated`/`Not authenticated` headline and `ProviderStatusBanner`'s banner already exist and already fire off the identical `auth.status` field the S7 `providerAuth` addendum reads; a redesigned Zerops-styled panel should make `ZeropsAgentAuthCard` the ONE place a Zerops-hosted user looks, and either fold the banner's Zerops-specific case into it (as wt/s7-web's commit `f09727bdc` already gestures toward — `providerAuth` deliberately overriding `state`) or explicitly suppress `ProviderStatusBanner` when a Zerops agent-auth card for the same provider is already shown, rather than stacking two 'sign in again' messages for one underlying fact — currently (per the `ChatView.tsx` diff) BOTH render simultaneously in the same overlay with no de-duplication logic between them.

## 4. Non-animated equivalent for the pulsing unauthorized dot

GUI source: `.__zagent-auth-row--unauthorized .__zagent-auth-row_dot { animation: zagent-auth-pulse 2.4s ease-in-out infinite; }` plus `@keyframes zagent-auth-pulse { 0%,100% { box-shadow: 0 0 0 3px rgba(178,106,0,.16); } 50% { box-shadow: 0 0 0 6px rgba(178,106,0,.06); } }` (`zagent-service-card.feature.scss:194-219`). This is a continuously-repainting animation, forbidden for z3 by `AGENTS.md:155`: 'Our users drive agents all day and notice a dropped frame, a lying spinner, and a stale label. No continuously repainting animations; they peg the GPU on high-refresh displays.'

**The GUI's own codebase already contains the fix pattern**, one selector above the pulsing one: the `--authorized` variant's dot uses a **static** halo, no animation — `box-shadow: 0 0 0 3px rgba(46,125,50,.18)` (`.feature.scss:186-193`). A non-animated unauthorized equivalent for z3 is simply the same static-halo treatment at the warning hue: fixed `box-shadow: 0 0 0 3px rgba(178,106,0,.16)` (the keyframe's own 0%/100% resting value — i.e., freeze the animation at its start frame instead of looping it) plus the accompanying text label (`Not signed in`) and, if a compact dot-only view is ever needed without room for text, an outline ring one step further out (`0 0 0 3px + 0 0 0 6px rgba(178,106,0,.08)` composited as two static box-shadow layers) so the state still reads as 'wants attention' through a heavier static ring rather than through motion. z3's current `ZeropsAgentAuthCard` already satisfies this trivially since it ships **no dot and no animation at all** (verified: no `animation`/`@keyframes`/CSS-in-JS transition anywhere in `ZeropsAgentAuthCard.tsx`) — the risk is only introduced if a future Zerops-styled redesign imports the GUI's literal pulse keyframe wholesale; this note exists so that port strips the `infinite` iteration and keeps the static halo only.
