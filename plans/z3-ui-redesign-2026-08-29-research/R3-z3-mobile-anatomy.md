## 3. Theming mechanism

- **Runtime switching:** yes — named palettes × appearance. `AppearancePreferencesProvider` (`features/settings/appearance/AppearancePreferencesProvider.tsx`) reads `mobilePreferencesAtom` (`themeMode` system|light|dark, `lightThemeId`, `darkThemeId`, legacy `themeId`), resolves `activeThemeName = getMobileUniwindThemeName(themeId, appearance)` (`lib/mobileThemeRuntime.ts:41-46`: default id `t3-code` → `"light"|"dark"`, others → `"<id>-<appearance>"`), renders `<ScopedTheme theme={activeThemeName}>` (:266). Mode → `Appearance.setColorScheme` (:113-115, so native headers/sheets follow); text scale → `Uniwind.updateCSSVariables(themeName, vars)` for every theme name (:109). Per-appearance theme mixing UI: `ThemeAppearanceSection.tsx` (cards with light/dark orbs; docs `docs/user/mobile-appearance.md`).
- **Theme names** (`uniwind-types.d.ts`, generated by uniwind at build): `light, dark, t3-chat-light/dark, grove-light/dark, ocean-light/dark, ember-light/dark, iris-light/dark`. Metro registers `extraThemes` from `generated-uniwind-theme-names.json` (`metro.config.js:5,52-56`).
- **Generation pipeline (verified):** `packages/shared/src/themePalettes.ts` — `BUILT_IN_THEME_IDS` (:1), `MOBILE_DEFAULT_THEME_ID="t3-code"` (:4), `THEME_COLOR_ROLES` 57 roles (:18-76), `ThemeDefinition{id,label,appearance,colors,variants.dark}` with oklch values, `BUILT_IN_THEMES` (:730) → `src/lib/mobileTheme.ts::createMobileThemeVariables` (:208-283; roles → the 65 tokens, alpha derivations, contrast-fixed skill accent, `themeColorToNativeColor` oklch→sRGB :96-119 because RN rejects oklch) → `scripts/generate-uniwind-themes.mts` (`renderUniwindThemesCSS` :164-183 emits `@variant <id>-<appearance>` blocks incl. adaptive vars; `readDefaultThemeVariables` :201-216 regex-parses `global.css` light/dark into `generated-uniwind-default-theme-variables.json` for the JS bridge). Run `vp run --filter @t3tools/mobile generate` (`package.json:42`), `--check` for CI; `scripts/generate-uniwind-themes.test.ts` fails if outputs are stale and pins the exact theme-name list. The same `ThemeDefinition` also feeds web (`apps/web/src/themePalette.ts`), terminal theme (`terminalTheme.ts:81-101`), preview orbs (`packages/shared/src/themePreview.ts`), showcase harness (`SHOWCASE_THEMES = MOBILE_THEME_IDS`).
- **Adding a `zerops` theme:** one `ZEROPS_THEME: ThemeDefinition` (57 roles, light + `variants.dark`) appended to `BUILT_IN_THEME_IDS`/`BUILT_IN_THEMES`; regenerate; update the name-list assertion in the generator test; `MOBILE_THEME_OPTIONS` (`mobileTheme.ts:23-29`) picks it up automatically; web gets it too. Selection = user preference or `MOBILE_DEFAULT_THEME_ID`.
- **Making Zerops the default look:** the default `t3-code` palette is **hand-authored** in `global.css` (not generated) and labelled "T3 Code" (`mobileTheme.ts:27`), with preview colours in `themePreview.ts:10-22` `STANDARD_THEME_PREVIEW_COLORS`. Two options: (a) edit `global.css` light/dark values directly (JSON bridge regenerates from it); (b) extend the generator to render `light`/`dark` from a `ZEROPS` `ThemeDefinition` so global.css's variant blocks become generated — the script already has everything needed (`variablesFor`), only `renderVariant("light"/"dark", …)` currently emits adaptive vars only (:166-167). Answer to "could a JSON/TS token source generate global.css": yes, the TS source (`ThemeDefinition`) already generates 10 of 12 variants; the remaining two are a small script change.
- **Not covered by tokens** (needs explicit work in a skin): terminal ANSI palette, shiki highlighter themes, diff add/delete colours, iOS-system status tints (`threadPresentation.ts`, `ConnectionStatusDot`, swipe actions, PR tints), Live Activity tints, Android plugin colours, splash/icon colours, Clerk theme JSON, native module fallbacks.
