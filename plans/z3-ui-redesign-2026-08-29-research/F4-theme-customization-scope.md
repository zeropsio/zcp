# Gap fill — theme customization scope + colour paths that bypass roles

## Summary
z3's theme system is far deeper than the 5-theme picker: 8 distinct user-facing customization surfaces on web (theme library/editor with 57 color roles per theme, light/dark 'halves' mixing, JSON import, live Open VSX marketplace search/import, per-provider accent colors, 4 independent font-family pickers, a global appearance-contrast slider, and per-project favicon/artwork) plus a 9th read-only theme picker on mobile (6 themes, no editor/import/search). Zerops GUI's only precedent is a single localStorage light/dark/system class toggle (zef-preferred-theme) plus separate zen/compact-mode flags — zero color customization, and its own status-color model is a dozen hardcoded per-domain Material palette maps, not a themeable role system. At least 6 color surfaces bypass z3's 57-role system entirely and would NOT receive a Zerops palette without new code: --success/--info tokens (deliberately commented 'independent' in index.css), Ghostty terminal ANSI 0-15 colors (compiled into WASM, no JS override hook at all — the deepest bypass), Shiki/Pierre diff+code syntax token colors (two separate hardcoded theme-name literals, web vs mobile), mobile's 57-entry 'adaptive' Tailwind color set (generated build-time, parallel to but disconnected from the 65 mobile --color-* role vars), AuthSurfaceShell's literal T3-blue gradient hex, and provider-accent default swatches. Diff row/gutter tinting, by contrast, already flows from --success/--destructive so it inherits fixes automatically. WCAG: none of the four candidate Zerops teals (#00ccbb/#3cbdb2/#00b1a3/#00a49a) pass 4.5:1 with white text (best 3.10:1) — matching Zerops's own live production gap (Material badge already ships white-on-#00ccbb at 2.03:1); #0077cc passes on light surfaces (~4.5-4.66:1) but fails normal-text AA on z3's dark canvas/card (3.82-4.14:1, needs a lightened dark-mode variant, exactly the pattern z3's own --primary already uses); mint #00e5c0 clears AA by 10-12:1 on all three candidate dark surfaces even as body text, yet Zerops's own dark theme still reserves it for icons/borders/fills and uses lighter #58efd4 for on-fill text — a design choice, not a contrast requirement. z3 already has an untested literal-copy risk (T3_CODE_LIGHT/DARK_THEME_COLORS, themePalette.ts:314-437, the editor's stock-look seed) with zero test coverage, unlike index.html's boot script which IS covered by a parameterized drift test (themeBoot.test.ts) that would need only a one-line addition per new built-in theme.

### Which teal is canonical for which use — verified from source, not inferred

- **`#00ccbb`** — the live Angular Material **primary/interactive** color. Confirmed three ways: (1) SCSS source `$zeropsAlphaColor: #00ccbb` feeding `mat.define-palette` as `$appThemePrimary` (`frontend-legacy/libs/zef/src/styles/_theme.scss:3-11,35`); (2) `$colors: (identityAlpha: #00ccbb, ...)` (`_theme.scss:64`); (3) **live production token dump** (`theme-tokens.json`) shows `--mat-badge-background-color: #00ccbb`, `--mat-stepper-header-selected-state-icon-background-color: #00ccbb`, `--mat-datepicker-calendar-date-selected-state-background-color: #00ccbb`. Used for: buttons, badges, stepper/datepicker selection states — interactive controls, never body text. **Notable, verified finding**: the live token dump also shows `--mat-badge-text-color: white` paired with that `#00ccbb` background — i.e. **Zerops's own production Material badge already ships an AA failure (2.03:1)**, an existing gap in the source app, not something z3 would introduce.
- **`#3cbdb2`** — the **lighter logo gradient stop** ("main") — `frontend-legacy/libs/zui/src/logo/logo.component.scss:9-11` (`.c-logo-theme-main { fill: #3cbdb2 }`), also exposed as CSS var `--color-zerops-mid` (`apps/zerops/src/styles/app.scss:87`). Logo/brand-mark only.
- **`#00b1a3`** — the **darker logo gradient stop** ("secondary") — `logo.component.scss:13-16` (`.c-logo-theme-secondary { fill: #00b1a3 }`), reused as the pricing-table brand swatch (`apps/web/src/app/components/pricing/pricing.component.ts:46`, `'zerops': '#00b1a3'`) and as `service-stack-info-chips` text color (`libs/zui/src/service-stack-info-chips/service-stack-info-chips.component.scss:79` — **this one IS used as text**, against a presumably light chip background, not against the teal itself). Also present as a near-duplicate CSS var `--color-zerops-dark: #02b1a3` (`app.scss:86`) — one channel off from the SCSS literal, itself a small drift artifact worth flagging.
- **`#00a49a`** — **not from the live app at all.** Only appears as a Mermaid `classDef` stroke color in documentation-diagram tooling (`zcpd-guide/docs/.../*.md`, `-bcu--reference-zcpd/content/guide/*.md`) — a diagram-authoring convention, unrelated lineage to the app's brand palette. Should not be treated as a UI candidate on the same footing as the other three.
- **`#007e72`** — the fork's own **POC-derived, AA-corrected** deepening of `#00b1a3` specifically to fix the white-text failure (`z3/docs/internals/zerops/verified.md:20`, live-measured 2.61:1→4.82:1 by the POC's own methodology; this report's independent calculation gets 2.69:1→4.97:1, consistent within measurement-method variance). Not yet used anywhere in the live GUI — a fork-only artifact.

### The accent-collision flagged in the task
`#2563eb` (default provider-accent swatch, `ProviderAccentColorPicker.tsx:13`) is a saturated blue close in hue to `#0077cc` (Zerops's Material "accent/gamma" color, `$zeropsGammaColor`, `_theme.scss:24-32`, and `identityBlue`/`identityGreen`-family in `$colors`, `_theme.scss:66`). If `#0077cc` becomes a z3 role color (e.g. `accent`/`focus`), a provider instance left on the default first swatch would read as visually redundant with the app's own accent — cosmetic, not a contrast failure, cheap to fix by rotating the default swatch order.

### Architectural note on why the AA risk is smaller than the raw numbers suggest
z3's own role-driven components never pair raw color-on-white/color-on-black at full opacity for status use — `badge.tsx:27,31` uses **low-opacity fills + a separate foreground token** (`bg-success/8 text-success-foreground dark:bg-success/16`), and `alert.tsx:16-17` does the same (`border-info/32 bg-info/4`). This pattern is inherently safer than Zerops GUI's own solid-fill-badge-with-white-text pattern (the live AA failure noted above) — so importing Zerops's hue values into z3's *existing* tint+foreground convention avoids inheriting Zerops's own contrast bug, provided the foreground token (not the raw teal) is what actually renders as text, and provided any DIRECT text/icon usage of a Zerops teal follows the source app's own precedent (dark or black foreground, never white) confirmed above.
