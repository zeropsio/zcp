# Zerops-shaped "New project" in the mate client

Status: BUILD (owner approved 2026-09-02, desktop/web first, mobile in a later batch)
Home for the design decision once landed: `docs/spec-mate.md §4.7`

## Problem

The sidebar's `+` beside "All projects" (`apps/web/src/components/Sidebar.tsx:3583`) opens the
command palette's `add-project` view — T3's notion of a project: a folder or repo clone inside an
already-connected environment. In Zerops the project is a Zerops project, and the surface that
creates one is buried on `/zerops` (`ZeropsProjectsPage.tsx:214-290`), reachable only before the
user is connected. The two meanings collide in one control.

## Shape of the flow

`+` → route `/zerops/new`, a four-step wizard:

1. Scope — org picker, only when the account has more than one membership.
2. Project — name + location; locations from `GET /client/{id}/settings`, fastest preselected by
   parallel `pingUrl` probes (the platform GUI's own heuristic, already implemented at
   `ZeropsProjectsPage.tsx:145-200`).
3. Agents — which coding agents the container comes up with. Selection is baked into the import
   YAML as `ZCP_AGENT_AUTH_TYPE_<SUFFIX>`; authorization is NOT — it happens against the live mate
   server after the wait.
4. Provisioning — the existing waiter and identity connect, then an authorization offer for the
   selected agents, then the thread.

The palette's source picker is not deleted: it becomes a per-environment "Add workspace…" action,
which is where `spec-mate.md §5.4`'s hierarchy (project → environment members → threads) already
places it.

## Decisions taken

- Route, not a command-palette view: three inputs and a wait of up to ~6 minutes do not belong in
  a palette.
- Agent env keys go where the platform GUI puts them (after `ZCP_VSCODE`), and `ZCP_MATE_ENABLED`
  stays the last key — so the existing no-agent golden stays byte-identical.
- OAuth only in this pass. Token mode would put a user secret in the import document; it is a
  separate decision with its own surface.
- `tagList`, `maxCreditLimit` and `mode` stay as they are (`[]`, `null`, `LIGHT`).
- Mobile (`apps/mobile/src/features/projects/AddProjectScreen.tsx`, `features/zerops/`) carries the
  same collision and gets the same treatment in a later batch, once this one is settled live.

## Constraint found while briefing S1

`packages/contracts/src/zerops.ts:325` — `ZeropsAgentId = ["claude-code", "codex"]`. Only those two
can be authorized through mate (`subscribeZeropsAgentAuth`, `ZeropsAgentAuthorizationDialog`), while
`zcp init` installs any of the six the platform supports. So the picker offers what the container can
install, and step 4's authorization offer covers the intersection with `ZeropsAgentId`; the rest are
installed and say plainly that they are authorized from the terminal. Widening `ZeropsAgentId` is a
separate change with a server side to it.

## S5 shape, after reading the sidebar

There is no per-project row action menu to hang "Add workspace…" on. The sidebar has exactly two
affordances: the `+` at `Sidebar.tsx:3583`, and an empty-state "Add project" CTA at `:4069-4076`
(rendered only when the account has no projects and no threads at all). The only per-project control
is the settings gear inside the project-scope dropdown's `MenuRadioItem` (`:3556-3565`).

So S5 is: both `+` and the empty-state CTA route to `/zerops/new`, and the palette's `add-project`
view gets its entry point as a second icon button beside that gear, per project row. The palette
itself and every source in it stay exactly as they are — only who opens it changes.

## Conventions the builders work under (fork, verified)

- Tests: `vp test run <file>`, never the repo-wide suite. `packages/**` uses `@effect/vitest`;
  `apps/web/**` uses `vite-plus/test` with `renderToStaticMarkup` and a hand-rolled element walker
  (`ZeropsProjectPicker.test.tsx`), not testing-library.
- Routes are file-based; `routeTree.gen.ts` is generated by the `tanstackRouter()` vite plugin and
  must never be hand-edited. A new `routes/zerops.new.tsx` needs only its `createFileRoute`.
- Design system R1-R8 (`docs/internals/zerops/design-system.md:70-85`) is test-enforced. R3 (tokens
  only, `var(--zerops-*)`) and R4 (no legacy vocabulary) are the two a new component trips first.

## Step 4 splits — authorization cannot live in the wizard

`subscribeZeropsAgentAuth` is an RPC on the mate server inside the container, so agent authorization
is reachable only AFTER `connectZeropsIdentity` has landed the user in a thread. The wizard runs on
`/zerops/new`, outside any connected environment, and cannot offer it.

So the selection and the authorization are separated by the connect, and the wizard hands the
selection across the boundary the same way the first prompt already crosses it: a `localStorage`
marker keyed on `environmentId`, per `apps/web/src/zerops/firstPromptStorage.ts` (the pattern
`spec-mate.md` MC-8 pins for the onboarding prompt). Losing the marker costs an offer, never
correctness.

## Verified: the selection does not install anything

`zcp init` installs no agent. Its adapters only CONFIGURE binaries the `zcp@1` image already carries:
`Detect` gates on `LookPath` (`internal/init/adapters/cursor.go:63`, `grok.go:48`), and Claude's
returns `true` unconditionally because the dev container ships it (`claude.go:77`). What
`ZCP_AGENT_AUTH_TYPE_<SUFFIX>` decides is the declared auth mode — and the platform's own reader
(`extractServiceMetadataMulti`, frontend-legacy) SKIPS an agent that has no per-agent env at all,
treating it as unconfigured.

So the honest claim for the picker, and the one its copy makes, is: the selection decides which agents
come up configured for sign-in. "Installs the agent" would be false, and an earlier draft of the brief
said it.

## The key that works is `ZCP_AGENTS`, not `ZCP_AGENT_AUTH_TYPE_*`

Found by an adversarial pass over S1, verified: `grep -rn "AGENT_AUTH_TYPE" --include='*.go'` over zcp,
minus tests, returns nothing. `zcp init`'s adapters gate on `Detect`/`lookPath` alone, so
`ZCP_AGENT_AUTH_TYPE_<SUFFIX>` changes nothing inside the container; its only reader is the Zerops
GUI's metadata parser, which — because the key rides in `envSecrets` and so becomes `sensitive:true` —
reads it back as `REDACTED` and can tell presence but not mode.

`ZCP_AGENTS` is the container-side key. Contract at
`internal/content/templates/vscode-bootstrap-extension.js:105-126` (`resolveAvailableAgentIds`), read
live from the zembed store by the bootstrap extension and the welcome surface:

- key ABSENT ⇒ every agent offered; `ALL_AGENT_IDS` (`:78`) is exactly the five of `ZeropsAgentType`
- present ⇒ split on `/[\s,]+/`, lowercased, deduped, unknown ids dropped, **order preserved** —
  it is presentation order
- present but not a string ⇒ zero agents, failing CLOSED on purpose
- it is presentation policy: not authorization, not a security boundary

So the import document emits `ZCP_AGENTS` when the user picked agents, and emits NO key when the
selection is empty — `ZCP_AGENTS: ""` would hand back a container offering nothing. Absent and empty
are opposite meanings and one test must pin the difference.

Like `ZCP_MATE_ENABLED`, this is a key the GUI never writes and we do, because without it the
container does not behave the way the product needs. `ZCP_AGENT_AUTH_TYPE_*` stays for GUI parity.

## Review findings (adversarial pass over the finished slices)

Clean on S1+S3 apart from a comment that overclaimed. On S4+S5, four, two of them real:

1. **The wizard could create a second project.** `provisioning.state` is non-null only after a create
   succeeded, but the wait's only exit returned to the agents step with the name still filled — so a
   `timed-out` cap expiry (retryable per §4.4, not an error) put the user one natural click away from
   creating another project. Settled phases now exit to `/zerops`, the way the picker page already
   did.
2. **The row action left the scope menu open under the palette.** The row button's `stopPropagation`
   is required by the no-nested-buttons rule, and it also suppresses the menu's own dismissal; the
   settings gear closes the menu explicitly and the new action did not.
3. A dead memo (`resetConnectingTarget` re-created each render) — behavior always correct, the
   one-connect-per-settled-wait guard lives on the ref and was never at risk.
4. Doc rot in `ZeropsProjectsPage.tsx`'s header after the form moved out.

Explicitly cleared: the move left no orphans, and `/zerops`'s candidate picker, enable path,
auto-connect and registration handoff are the same logic re-homed.

## A gate the briefs missed: the surface manifest

`docs/internals/zerops/surfaces.json` must claim every component under
`apps/web/src/components/zerops/`, and `scripts/surface-manifest.test.ts` fails the build otherwise.
None of the slice briefs mentioned it (the conventions pass asked about the showcase scene registry
and found that one instead), so it surfaced only in the full sweep. Added a `zerops-new-project` row —
components, entry points, connection mode, contracts, reverse states, tests — plus its id in the
test's ordered id list. Two schema rules worth knowing next time: a `reverse` must name another action
of the SAME surface or read `none: <reason>`, and the id list is order-sensitive.
