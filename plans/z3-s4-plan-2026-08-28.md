## 1. Frame

**New account.** Sign-up form inside z3 (e-mail/password, no GitHub — S0.7) → `POST /registration`
with `claimZcpPool:true` → session token back immediately, `zcpClaimed` says whether the pool gave a
project → "Preparing your project" while we poll the account's projects and then the project's
services by **direct reads** until the `zcp` service is `ACTIVE` → probe the container origin's
`/healthz` → identity bootstrap → thread.

**Existing account.** Sign in (TOTP when demanded) → project picker built from zcp candidates across
every org → pick, or **New project** → connect → thread.

**"Enable Zerops Code"** is what the picker offers when `/healthz` says the container predates z3:
`PUT /service-stack/{id}/restart` with the *user's* token, then poll `/healthz` for `z3Up:true`.
Measured budget: 17 s to an answer, 19 s to `z3Up`, ~14 s of L7 `502` in between (S0.2) → cap 30 s,
render 502/network-error as "restarting", never as failure. Then identity bootstrap (S1's
`zerops-identity` grant → the ordinary token exchange) and land in the environment's thread with
zcp's onboarding greeting.

## 3. Design

### (a) Zerops session client — `packages/client-runtime/src/zerops/`
Rewrite from a blank file, with the POC (`git show poc-2026-08-28:packages/client-runtime/src/zerops/api.ts`,
601 lines) open as reference. Port as *ideas*, retyped: the `globalThis.fetch.bind(globalThis)`
brand-check fix (`api.ts:315-319` — an unbound `fetch` throws "Illegal invocation" in browsers);
one coalesced refresh promise so N parallel 401s cause one refresh (`api.ts:#refreshPromise`);
`zeropsRegionFromPublicZone()` + `buildZeropsContainerUrl()` (`api.ts:225-236`) — region from the
project's `publicZone`, never hard-coded; `activeClientsFromUser()` reading **every** `clientUserList`
entry; the storage-adapter shape from `session.ts:11-17` (async `get/set/remove`, versioned keys,
credential and selection stored apart) so mobile's secure storage drops in.
**D1:** the Zerops token is held client-side only. It is presented to the z3 server once per identity
bootstrap and the server must not persist it — S4 asserts that contractually (test: the bootstrap
request body/headers carry it, nothing else does), S1 owns the server half.

### (b) Registration in z3
`POST /registration` (`{email, password, name, accountName, languageId:"en", claimZcpPool:true}`;
`token` = Turnstile when enabled). Sources verified in the GUI: `registration.model.ts:8-19`,
`registration.page.ts:77-117` (`claimZcpPool` iff `?zcp=true`), `registration.form.ts:23-64`
(`languageId` hardcoded `"en"`, no password-complexity validator — only display hints for <8/>72
chars). Response = `{auth:{accessToken, refreshToken, expiresIn, twoFAMethods, sudoUntil}, user,
zcpClaimed?}`; session usable at once — **no e-mail-verification gate**. TOTP is post-signup only;
S4 ships no TOTP *enrolment*, only TOTP *login* (see (b′)). No terms/consent field exists.
**Q-10 (captcha), designed both ways:** the widget renders behind one flag. Off ⇒ no `token` field,
the API's validation layer does not require it (S0.7 live). On ⇒ Turnstile script + site key from
build config, `token` sent, and a `403`/score rejection maps to a "verification failed, try again"
state. Ship with the flag off, flip it if Q-11's live run is rejected. If Cloudflare binds the key to
the GUI's hostnames, that is a platform-side item — stop and report (§4 hard rule 1).

### (b′) Sign-in
`POST /auth/login {email,password}` → `auth`. **TOTP is signalled by `twoFAMethods.length > 0 &&
twoFAVerified !== true`** (`libs/zef/src/auth/auth.utils.ts:323-325`), followed by
`POST /2fa/totp/login {token}` (the 6-digit code, param named `token`, `auth.api.ts:90-95`).
Recovery codes are the same endpoint family; out of scope for S4 unless the live run needs one.

### (c) Waiting for the claimed project's `zcp` to be `ACTIVE`
The GUI waits on WebSocket pushes (`zcp-pool-claim-base.effect.ts:226-289`, 30 s navigate timeout;
`:468` 5-min provision timeout). z3 has no socket, so it **polls direct reads only**:
`GET /client/{clientId}/project?statuses=ACTIVE` (`ListClientProjects`, openapi `:12973`) →
`GET /project/{id}` (`publicZone`, `zeropsSubdomainHost`) → `GET /project/{id}/service-stack`.
Never `POST /project/search` on this path — it is Elasticsearch-backed and lags a fresh write.
2 s cadence, caps: project appears 60 s, zcp `ACTIVE` 300 s (matches the GUI's `PROVISION_TIMEOUT`),
`/healthz` 30 s. Every wait renders **what** it waits for and its cap; on expiry the panel offers
Retry and a "check the Zerops GUI" link rather than dying.

### (d) "Predates z3" detection
Plain, **header-less** `GET <container origin>/healthz` with `redirect:"manual"` and no custom
headers — any custom header forces a CORS preflight the container's nginx does not answer
(POC `connect.ts`). Three outcomes: JSON with `z3Up:true` ⇒ ready; JSON with `z3Up:false` ⇒
initialising, keep polling; **opaque redirect / non-JSON 200 / 404** ⇒ old container (a pre-z3 zcp
answers `302 → ?folder=/var/www`) ⇒ offer **Enable Zerops Code** = `PUT /service-stack/{id}/restart`
with the user's token, then the same `/healthz` poll with the 30 s cap and 502-means-restarting rule.
Never assert JSON by status code alone: under a mis-prefixed proxy z3's SPA catch-all returns
`200 index.html` (S0.5) — parse, then check the field.

### (e) Project picker (existing accounts)
Candidates derived per project across **every** org from `/user/info.clientUserList`. A zcp container
is identified by **service type**, never hostname: `serviceStackTypeInfo.serviceStackTypeVersionName`
starts with `zcp@` (POC `candidates.ts:62-65`) — a project may hold several, all are offered.
Groups `connected | ready | unavailable`; `connected` = the derived origin matches a registered
environment's `displayUrl` (origin-normalised). Keep the POC's split: a pure derivation function
(unit-tested, no I/O) behind a concurrency-capped fetching shell that re-renders incrementally.
The picker list itself may use `POST /project/search` (fast, membership-gated hard per S0.1) — but
anything *just created* is resolved through `GET /client/{id}/project`.

### (f) New project (and the pool-exhausted fallback — the same path)
Two REST calls, traced from the GUI:
1. `POST /client/{clientId}/project` — body `{name, description:"", tagList:[], location:<fastest
   location id>, clientId, mode:"LIGHT", maxCreditLimit:null, userRoles:[]}`
   (`zcp-pool-claim-base.effect.ts:704-761`). Reuse the account's existing project when it has one
   and the user picks that (the GUI reuses `projects[0]` unconditionally — S4 asks instead).
2. `PUT /project/{id}/first-class-recipe/development-container` — body
   `{serviceImportYaml, recipeSource:"zeropsio/zcp", createIntegrationToken:true}`
   (`service-stack-base.api.ts:161-177`, openapi `:14949`).

`serviceImportYaml` is what `ZeropsYamlBuilder.generate()` emits
(`.../zerops-services/yaml-templates/yaml-builder.service.ts:44-299`), called at
`zcp-pool-claim-base.effect.ts:661-668` with `{serviceName: getNextServiceName("zcp", existingNames),
enableAgent:true, enableVscode:true, agents:[], enablePublicAccess:true, vscodePassword:
generateSecurePassword()}`. The literal document (16-char password generated **client-side** via
`crypto.getRandomValues`, `libs/zef/src/core/utils.ts:451-467`; no `mode:` field anywhere):

```yaml
services:
  - hostname: zcp
    type: zcp@1
    maxContainers: 1
    enableSubdomainAccess: true
    verticalAutoscaling:
      minRam: 2
    envSecrets:
      VSCODE_PASSWORD: "<16 random alnum>"
      ZCP_VSCODE_AUTH_ENABLED: "true"
      ZCP_VSCODE: "true"
    zeropsYaml:
      zerops:
        - setup: zcp
          run:
            base: zcp@1
            initCommands:
              - zcp install
              - zcp init
              - sudo -E zcp init nginx
            ports:
              - port: 8080
                httpSupport: true
            startCommands:
              - command: zcp service start nginx
                name: nginx
              - command: zcp service start vscode
                name: vscode
```

`VSCODE_PASSWORD` is **mandatory** in our emission: without it a `zcp@1` with a subdomain is publicly
open (S0.8, `zcpb` answered code-server HTML to anyone). z3 never reads it back — it is generated,
sent, forgotten; a user who wants code-server reads it in the Zerops GUI. Then (f) joins (c)'s wait.

### (g) Landing in the thread
The z3 server is started by `zcp init z3` (S2) with `--auto-bootstrap-project-from-cwd` and cwd
`/var/www`, so on first boot it creates one project with `workspaceRoot=/var/www` and its first
thread (`serverRuntimeStartup.ts:196-250`) and publishes a `welcome` event carrying
`bootstrapProjectId`/`bootstrapThreadId`. The client therefore does nothing to *make* a thread: after
`registerZeropsIdentity` returns an `environmentId`, navigate to `/`, where `IndexDraftLanding`
(`_chat.index.tsx:38-73`) opens a draft on the single project. **zcp's onboarding greeting requires a
first message to exist** — S4 sends one fixed onboarding prompt exactly once per newly connected
Zerops environment (guarded by a local marker keyed on `environmentId`), never on reconnect. This
depends on an authorized provider; with none, the thread shows the S7 "Sign in to Claude" state
instead of a silent failure.

## 5. Risks / open questions

1. **Is `GET /client/{id}/project` really lag-free?** The whole (c) design rests on it. Cheapest
   settle: one live run — create a project, then hammer that GET and `POST /project/search` in
   parallel and compare first-appearance times (~5 min, owner's account, delete after).
2. **Q-10 captcha.** Settle with Q-11's live registration using throwaway e-mails (owner-gated); the
   flag in (b) means either answer is a one-line change.
3. **Turnstile hostname binding.** If enforcement is on *and* the key is bound to the GUI's
   hostnames, S4 cannot register from z3's origin — a platform-side item, stop and report.
4. **First-boot cost on a fresh pool container.** Cold `npx t3@<pin>` = 58 s (S0.10); local-bundle
   first (S2) makes it ~4 s. If a claimed container still fetches cold, (c)'s 30 s `/healthz` cap is
   too tight. Settle: measure once on a real claimed project after S2 lands.
5. **`ListClientProjects` for a brand-new account** may return the claimed project *before* its zcp
   exists, so (c) must not conclude "no zcp" from one read. Settle in the S4.4 test with a fixture.
6. **A second thread's provider is unauthorized** (S7 is phase 2). Until then the greeting only
   appears where the copied subscription login is present. Not a blocker; the UI must say so.
7. **`GET /project/{id}/service-stack` does not carry a live process** — an `ACTIVE` zcp mid-restart
   looks identical to a settled one. `/healthz` is the tiebreaker; never gate on status alone.
8. **The client label** (`clientMetadata.ts:89`) shows in T3's session list; make it name the device,
   not just "Zerops Code", or a user with laptop + phone sees two identical rows (S0.9/Q-07).

**Out of scope:** GitHub signup (unimplemented in the GUI + bound to Zerops' OAuth app — platform
change); mobile (D6/S5 inherits S4.1/S4.6 through the shared runtime); desktop; VPN; TOTP
*enrolment*; passkeys; reading `VSCODE_PASSWORD` back; any mutating Zerops call the agent should make
through MCP instead (§4 rule 3).
