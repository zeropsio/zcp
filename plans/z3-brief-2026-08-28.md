## 1. What you are building, in plain words

Zerops Code ("z3") is a new app for people who use Zerops. They sign in, land in a project, and
talk to a coding agent. The agent runs **inside their Zerops project** (in a container called
`zcp`) and can build and operate the whole project — create services, write code, deploy, read
logs — because it has Zerops tools (MCP) in its hands.

The app is a fork of the open-source T3 Code (MIT). T3's *server* runs inside the zcp
container; T3's *client* (web, desktop, mobile) is rebranded and gets a Zerops-specific flow.
A proof of concept exists and works end to end. Your job is to turn the POC into the real
thing under the decisions in §5 and the rules in §4.

```
  browser / desktop / phone                       Zerops project
 ┌─────────────────────────┐    public HTTPS     ┌─────────────────────────────────────────┐
 │ z3 client               │◄──────────────────►│ zcp container                            │
 │ sign in with Zerops     │    /z3/… + wss     │   z3 server ── spawns claude/codex        │
 │ threads, cards, map     │                    │     (cwd /var/www, zcp MCP attached)      │
 └─────────────────────────┘                    │   nginx :8080 ─ code-server, /z3/         │
              │ Zerops API (CORS *)              │   /var/www/<host> = sshfs mount of each   │
              ▼                                  │   dev service; git lives on that service │
        api.app-prg1.zerops.io                   └─────────────────────────────────────────┘
```

## 3. Vocabulary (read once)

| Term | Meaning |
|---|---|
| **zcp** | the Go binary + the container (`zcp@1` service type) that every Zerops project gets; runs nginx, code-server, agents, the MCP server. One per project. |
| **sibling / dev service** | any other service in the project. A *dev* runtime holds the code at `/var/www` on its own disk, with `/var/www/.git` there. |
| **mount** | zcp sshfs-mounts a dev service's `/var/www` at its own `/var/www/<hostname>`. Agents edit through the mount; changes land on the service instantly. |
| **dev / stage pair** | standard bootstrap creates `<name>dev` + `<name>stage` per runtime plus managed deps (db, cache…). |
| **bootstrap** | zcp workflow that creates infrastructure from the user's intent: discover (plan, user confirms) → provision (`zerops_import`, mounts, git init on the host) → close (evidence written). No code. |
| **develop / work session** | zcp workflow for code work, one session per agent process (PID): code → deploy → verify → "done" is derived, not stamped. |
| **StateEnvelope** | JSON attached to every workflow-aware tool result: phase, services (mode, status, closeMode, gitPushState, stage pair), work session (deploy/verify attempts), bootstrap step. Designed so a client can rebuild state from tool output. |
| **ServiceMeta** | `.zcp/state/services/<host>.json` — evidence that a service is under zcp management. |
| **`zcp studio`** | a frozen CLI seam on `main` (`topology`, `watch`, `deploy`, `sync-env`, `console serve`) built for the VS Code cockpit: JSON out, token-blind, never MCP. Your bridge from zcp to the z3 server. |
| **z3 server** | T3's server (`npx t3 serve`), our fork, running in zcp. Owns threads, provider sessions, checkpoints, terminal, auth. Event-sourced sqlite under `--base-dir`. |
| **environment / project / thread** (T3 words) | environment = one running server; project = a workspace root; thread = one conversation = one provider (agent) session. |
| **pairing / session** (T3 auth) | a one-time credential exchanged (RFC 8693) for a 30-day bearer; WS connects with a 5-min ticket. Sessions carry scopes and a free-form `subject`. |
| **provider** | T3's adapter for an agent CLI: Claude Code, Codex, Cursor, Grok, OpenCode. |

## 4. Hard rules

1. **No Zerops platform/backend change.** Not the REST API, not the `zcp@1` image, not the
   platform-owned zcp recipe, not pool provisioning. If a step needs one, stop and report —
   do not work around it with an operator-only path.
2. **The agent runs in `/var/www`**, exactly as zcp does today. Never move the workspace, never
   a per-service cwd, never a local copy of code inside zcp. z3 adapts to zcp, not the reverse.
3. **Client renders state; the agent mutates through MCP.** The client never grows a second
   orchestration path (no direct import/deploy/env calls from the UI). Read-only or
   caller-bound things are fine: open URL, files through the mount, terminal, logs, Data Console.
4. **One credential: the user's Zerops identity.** No shared secrets on the client path.
   Credentials (PATs, launch tokens) are user-owned: the agent never fabricates them, and when a
   direct path exists (card → server → service secret) they never pass through the conversation.
5. **zcp rules apply to zcp work** (`CLAUDE.md`): repo lives on the dev service; no mount-side
   `git init`; JSON-only stdout; a new `zcp init` step degrades instead of failing the boot;
   `/flow` for anything non-trivial; TDD (RED → GREEN); design decisions land in a spec —
   create `docs/spec-z3.md`, that is what unparks the container branch.
6. **Fork discipline in `z3`** — superseded 2026-08-28: z3 is a hard fork; the rules live in
   `../z3/docs/internals/zerops/fork.md` (zones, `imported.lock`, adapter SPI, intake) and
   `docs/spec-z3.md §7`. No `rebase upstream/main`; upstream enters by import/port only.
7. **Measure before building** where a stream says PROVE. Every measured fact goes into
   `verified.md` with a date and the command; facts older than a dependency bump are re-run.
8. **Report faithfully.** Failing tests are reported with output; skipped steps are named.

## 4a. Delivery during development — no releases

Nothing is released while z3 is built. The modified zcp and the forked z3 server reach the
container **by hand** (the `localflow` dev loop, generalised); one release happens at the end
(the "release gate" below). Why: a release is slow to iterate on, and the pool hands a new zcp
to fresh projects only after midnight — manual delivery lets us build, upload and try within
minutes and throw away what does not work.

Three artifacts, one script — **`eval/scripts/z3-dev-push.sh [zcp|z3|all]`** (target = the
`z3-eval` zcp; with the project's VPN up the existing `Host zcp` ssh entry resolves to it):

| Artifact | Built from | Delivered how | When |
|---|---|---|---|
| zcp binary | `make linux-amd` (via `build-deploy.sh`) | scp → `sudo install` → sha256 verify → `zcp init` + `sudo -E zcp init nginx` + `nginx -s reload` → restart `zerops@z3` if present | every zcp change |
| z3 server | `vp run --filter @t3tools/web build` → `cli.ts build` → **`cli.ts pack`** (the publish rewrite — `catalog:` → concrete versions — ending in a tarball; a plain `npm pack` is uninstallable) with version `<pkg>-dev.<sha>` | scp tarball → `npm install` into the container prefix **`/home/zerops/.zcp/z3`** (`…/node_modules/.bin/t3`) → restart `zerops@z3` if present | every server change |
| web client | `vite dev` on the laptop, pointed at the container origin | nothing in the container | never |

The prefix and the unit name are the contract `zcp init z3` (S2) builds on: it runs
`$PREFIX/node_modules/.bin/t3` when present, else installs the pinned version into the same
prefix; the unit is a `zsc unit create z3 …` → `zerops@z3.service` (the sshfs primitive;
`zsc unit` has only `create`/`remove`, restarts go through `sudo systemctl restart`). nginx
runs as `zerops`, so `nginx -s reload` needs no sudo.

Access = VPN to the target project + `ssh zerops@zcp`. VPN needs sudo: the owner brings it up
once per session; agents then run the script themselves.

Facts that shape the loop (recipe read live 2026-08-27, mirrored in `deploy/zcp-container.yml`):
- **A restart wipes the dev build.** The platform recipe runs `install.sh` (unpinned → latest
  *release*) on every container start. After any restart: push again. Restart only to measure
  S0.2, then re-push.
- **The POC's z3 is upstream `npx t3@0.0.35`, not the fork** — every server change needs the
  tarball push above.
- **`zcp init z3` is local-bundle-first**: a bundle already at the local bundle path is used
  as-is; fetch happens only when it is absent; no network and no bundle → the step degrades.
  One logic, two sources — the dev loop places the bundle, the release path fetches it.
- **Agent auth on the dev targets is a copied subscription login — never an API key.** The
  `z3-eval` zcp already has Claude logged in through the owner's subscription. Stash its
  credential artifacts off the container (`~/.claude/.credentials.json` plus the account part
  of `~/.claude.json`; `~/.codex/auth.json` when Codex is logged in) into a laptop directory
  outside every repo, and copy them into each further throwaway service. Not correct — one
  identity in N containers, and a refresh in one container can invalidate the copy in another
  (re-stash from the one that still works) — but enough for testing. Never print or commit the
  contents. The product flow is S7, phase 2; subscription login stays the primary path there.
- `http://localhost:*` sits on the z3 Origin/CORS allowlist as a product-level dev convenience
  (the rule the welcome bridge already has), not a temporary hack.

Acceptance split — **now (manual push)** vs **release gate**:
- Now: everything in S1–S6 a pushed build can prove on `z3-eval`.
- Release gate (one release, then run naked): a fresh `zcp@1` from the platform recipe answers
  `/healthz {z3Up:true}` on its own (S2); a restart of an older container brings z3 up (S2/S4
  "Enable Zerops Code"); a brand-new pool account reaches a thread with no operator touch (S4).
  Until then S4's new-account run pushes the dev build into the freshly claimed container by
  hand and tests the rest of the flow whole. The pool turns over after midnight — plan the
  gate around it.
- S0.6 (bundle distribution channel) is decided at the release gate, not before; S0 only
  measures the container's Node version.

Ledger: the moment the loop is first used, `hacks.md` gets "dev builds delivered by hand,
restart wipes them" (in place; real fix = the release gate). The rig's runbook lives in
`CLAUDE.local.md`.

## 5. Decisions (what / why / what it replaces)

**D1 — One door, Zerops identity.** The client talks to the Zerops API and to the container's
public origin. To get in, it presents its Zerops access token; the z3 server validates it
against the Zerops API, checks the user is a member of *this* project (the container knows its
`projectId`), mints a short-TTL pairing grant with `subject = <zerops user id>`, and the client
does the ordinary token exchange. Per-user revocation; membership re-checked on connect. Also
fix two exposures: no `Origin` check on the WS upgrade, wildcard CORS. *Replaces* the POC's
`/z3-pair/<VSCODE_PASSWORD>` mint and sidecar. *Why:* a shared long-lived container secret was
doing a per-user job. The server already has the template for "external proof → grant" (the
cloud-mint path); this is an extension, not new machinery.

**D2 — z3 rides in the zcp binary, under `/z3/` on the existing 8080 origin.** `zcp init`
uses a local z3 bundle when present, else fetches the pinned one (§4a), starts it as a
supervised unit, renders an nginx location outside
the code-server cookie gate (with WS upgrade). Because `install.sh` runs at every container
start and fetches the latest zcp, **a service restart via the API upgrades the container** —
the client can enable z3 on an old container itself. *Replaces* the POC's own port 3773 and
the mirror recipe (both need the platform-owned recipe). *Cost:* base-path support in the z3
server (a URL helper that overwrites `pathname`, contract route prefixes, static catch-all,
`/ws`, Vite `base`). Port 3773 returns when the platform bakes z3 into the image.

**D3 — Project model.** Environment = Zerops project (1:1). One z3 project per Zerops project,
`workspaceRoot = /var/www`. Thread = one conversation = one agent PID = one zcp work session,
cwd `/var/www`. Services are not projects; they are rows in a **service map**. *Replaces* the
POC's `/home/zerops/app` local workspace.

**D4 — Git is multi-repo and runs on each dev service.** The repos are the mounted dev
services (`/var/www/<host>` ⇄ `/var/www/.git` on host `<host>`). The z3 git driver enumerates
them from the zcp topology (never by scanning for `.git`) and runs `ssh <host> git -C /var/www
…` with one multiplexed SSH connection per host, mapping paths at the driver boundary.
Checkpoints, diff, restore, review = z3's (turn-level history). Init, identity, PAT, commit +
push + deploy = zcp's workflow, triggered from z3 by the agent. T3's per-thread **worktree mode
is off** on Zerops. T3's own commit→push→PR action on Zerops projects delegates to zcp's
git-push flow or is hidden — never two commit pipelines. *Gate:* measure sshfs vs SSH first.
**The isolation unit on Zerops is a service (or a project), not a directory:** a worktree is a
second checkout nobody serves — a dev service has one `/var/www`, one process, one subdomain,
one database, and with more services the story explodes. A parallel feature is a sibling dev
service on a branch, provisioned by the agent through MCP (a possible S6 quick action later);
a large one is its own project. Two threads on one service stay possible and are made
*visible* (strip: "thread Y also works on kanbandev"), never locked.

**D5 — Zerops-aware client.** Two feeds into the client: a **topology feed** (z3 server runs
`zcp studio topology` + `watch`, republishes per environment) and a **lifecycle feed** (z3
server extracts the `StateEnvelope` from every `zerops_*` tool result in the provider stream,
publishes per thread). UI: service map, lifecycle strip in the thread header, Zerops cards for
plan / import / mount / deploy / verify / subdomain / errors, quick-action prompts, embedded
Data Console. User questions come through T3's existing provider-agnostic `user-input` events
(§8). *Replaces* nothing — this is what makes it Zerops Code.

**D6 — Clients.** Web is the product (hosted static bundle). Desktop is the same bundle in
Electron — one smoke build to learn the cost, not a product stream. Mobile already runs on an
iPhone (personal-team build); it inherits D1 through the shared client runtime.

**Out of scope, recorded:** VPN anywhere (product or operations); cost / scale-to-min /
wake-on-connect; thread history off the container; `t3code:` prefix and URL-scheme rename.

### S1 — The door (z3 server)

- **Deliverables:** bootstrap method `zerops-identity` (validate token → membership → grant,
  `subject` = Zerops user id); `revokeBySubject`; membership re-check on WS connect (cached
  minutes); `Origin` allowlist on the WS upgrade; CORS allowlist; bearer-only for the hosted
  client; DPoP-bound tokens enabled for it; a framed **exec RPC** (scope `exec:operate`: run a
  command in the container, stream output, return the exit code — the replacement for SSH in
  scripts and for us as operators).
- **Acceptance:** a member signs in from a hosted origin and reaches a thread with no
  pairing code; a non-member gets 403 and no grant; removing the member ends access at the
  next connect; a page on a foreign origin cannot open the WS; upstream pairing still works for
  a non-Zerops environment; exec RPC returns `{exitCode, stdout, stderr}` for `zcp version`.
- **Don't:** keep `/z3-pair`; store the Zerops token server-side beyond validation; invent a
  second session model.
- **Start here:** the cloud-mint handler in `apps/server/src/cloud/`, `auth/EnvironmentAuth.ts`,
  `auth/SessionStore.ts`, `packages/contracts/src/auth.ts`, `ws.ts` upgrade path.

### S2 — Delivery (zcp + z3 base path)

- **Deliverables (z3):** `--base-path` end to end (server routes, static, `/ws`, well-known,
  client URL helper joins instead of replacing).
  **Deliverables (zcp):** `zcp init z3` — local-bundle-first (§4a): use a bundle already at

  cwd `/var/www`, base dir `/home/zerops/.t3`; nginx `location /z3/` outside the cookie gate

  mint; init-complete marker; `docs/spec-z3.md` section; CLAUDE.md pointer only if a new trap.
- **Acceptance:** a fresh `zcp@1` service imported with the *platform's* recipe answers
  `/healthz` `{z3Up:true}` after boot with no manual step; a restart of an older container
  brings z3 up; `zcp init` on a container without network for the bundle degrades (names the
  step) and the container still starts; `go test ./... -short` + `make lint-fast` green.
- **Don't:** add ports or `startCommands` to any recipe; live-edit nginx; fail the boot.
- **Start here:** `git show feat/z3-container` (keep the init step, service entries, healthz;
  drop the mint and the port); `internal/init/`, `internal/content/templates/nginx.conf.tmpl`,

### S3 — Git (z3 server)

- **Deliverables:** SSH-backed process runner behind the git driver (ControlMaster per host);
  path map at the driver boundary for every path-returning call; throwaway `GIT_INDEX_FILE`
  in the host's tmp; repo-identity resolver routed through the driver; multi-repo
  enumeration from the topology feed; per-service grouping in checkpoint/diff/review; worktree
  mode forced to `local` **server-side** for Zerops environments (`ThreadEnvMode`,
  `worktreePath` stays null — an enforced rule, not a default, so neither a `.t3/project` file
  in a repo nor the client can switch it back); hook-progress streaming (the raw spawner)
  dropped; poll/detection TTLs tuned; T3's stacked commit→push→PR action hidden or delegated
  on Zerops.
- **Checkpoint rules** (mechanics: temp `GIT_INDEX_FILE` → `add -A` → `write-tree` →
  `commit-tree` → hidden `refs/t3/checkpoints/*`; restore = `git restore --source` +
  `clean -fd`). They live in the dev service's `/var/www/.git` and share its fate — nothing new
  to guard; `push` / `buildFromGit` / `log` never see them; the author is T3's, zcp's identity
  untouched. Guard four things: (1) `add -A` swallows untracked files — a repo without
  `.gitignore` gets `node_modules`/uploads into its first checkpoint: refuse or warn, and check
  what zcp's host-side `git init` writes; (2) restore's `clean -fd` deletes untracked files the
  *running* app wrote after the checkpoint — restore tracked files only, or say it in the card
  before confirming; (3) refs accumulate per turn × repo × thread — verify T3 prunes on thread
  delete, else prune; (4) both costs are measured in S0.3/S0.13 before the design is fixed.
- **Acceptance:** a turn that edits two services produces two checkpoints and a diff grouped
  by service; restore works per service; no git process ever runs against the sshfs path;
  timings within the S0.3 budget; a project with zero mounts shows "no repositories yet", not
  an error.
- **Don't:** scan `/var/www` for `.git`; run `git init` from z3 (zcp owns it); touch identity,
  remotes, or push.
- **Start here:** `apps/server/src/vcs/{VcsProcess,GitVcsDriver,GitVcsDriverCore}.ts`,
  `checkpointing/`, `orchestration/Layers/CheckpointReactor.ts`.

### S4 — Client flow (web)

- **Don't:** read `VSCODE_PASSWORD`; use the search endpoints for "does it exist yet" right

- **Start here:** `docs/internals/zerops/poc-findings.md` — the web/mobile seam map (where

- **Deliverables:** one Electron build of our fork with the remote-only configuration (local

  preview webview kept) — a written cost note, not a product; mobile: identity bootstrap
  through the shared runtime, the manual pairing-code field gone for Zerops projects.
- **Acceptance:** desktop opens the hosted flow and reaches a thread; mobile reaches a thread
  with no code typed.

### S6 — Zerops-aware client (z3 server + web)

- **Deliverables (server):** topology feed (`zcp studio topology` + `watch` per environment →
  a new additive contract slice); lifecycle feed (a reducer over provider tool results that
  extracts the `StateEnvelope` per thread); both survive reconnects and compaction.
  **Deliverables (web):** service map panel (Runtimes / Data / Infra; type, status, URL,
  mounted, live process, dev↔stage pair; prod project as a link); lifecycle strip in the
  thread header; Zerops cards (plan → confirm, import with per-service progress, mount, deploy
  with build progress → URL chip, verify, subdomain, structured errors); quick-action prompts
  ("Deploy", "Show logs", "Add Redis" → prefilled message); **credential card** (token goes
  card → z3 server → service secret through a zcp verb, never through the chat — needs a zcp
  CLI verb, design it with the owner); embedded Data Console; `/zerops` overview page from the
  POC folded into the environment view.
- **Acceptance:** the §7 kanban walk-through is reproducible on a fresh project by the owner;
  a service created from the web GUI appears in the map without a refresh; a thread reopened
  after compaction shows the correct strip after one `status` call; every card degrades to the
  generic tool block when the payload is unexpected.
- **Don't:** call mutating Zerops APIs from the client; parse `.zcp/state` directly; invent a
  lifecycle state machine — the envelope is the state.
- **Start here:** `cmd/zcp/studio.go` (zcp), `apps/server/src/provider/` event stream,
  `packages/contracts/src/providerRuntime.ts`; `docs/internals/zerops/poc-findings.md` for

### S7 — Agent authorization (phase 2)

The agent (Claude Code / Codex) needs its own provider login inside the container. Today the
Zerops GUI does this with a walker (`zcp-agent-auth-dialog` in `../frontend-legacy`): it
opens a platform web terminal into the container, sends the login command, scrapes the PTY
bytes for the auth URL / device code (chunk-boundary parser, OSC 8 links, a stall timer that
presses Enter), auto-opens the URL, takes the pasted code, detects "login successful", then
writes `ZCP_AGENT_OAUTH_<SUFFIX>=true`. Three flow modes: paste-code (Claude), device-code
(Codex), url-poll (Cursor). It is complex because it runs *outside* the container through a
platform terminal. z3 runs inside.

**Premise: the user's own subscription login (Claude Pro/Max, ChatGPT) is the primary and
only planned path.** That is the reason z3 is a T3 fork driving the vendors' own CLIs — it
uses subscription auth the way the vendors allow it. API keys (`ANTHROPIC_API_KEY`,
`OPENAI_API_KEY`) are not a product path and are not offered. No webview.

- **Primary — OAuth in z3's own terminal, nothing scraped:** a card "Sign in to Claude / Codex"
  opens T3's terminal pane with the login command pre-typed (`claude` paste-code flow,
  `codex login --device-auth`); the user follows the CLI's own prompts — the URL is a link in
  the terminal (verify T3's terminal renders links), the code goes straight back into it. The
  z3 server watches the credential artifact (`~/.claude/.credentials.json`,
  `~/.codex/auth.json` — the same probe the welcome panel uses) and on appearance runs
  `zcp agent mark-oauth <agent>`; the card flips to Authorized and code-server's welcome panel
  + the GUI agree. The terminal is the UI.
- **Alternative, also subscription — `claude setup-token` card:** a long-lived token the user
  mints on the laptop → the S6 credential card → service secret (`sensitive`, through the S6
  credential verb) → never the chat; the z3 server reads the live env store
  (`/etc/zerops-zembed/env.json`, rewritten on every env change, no restart) and injects it
  into the provider process, then sets the flag the welcome panel reads
  (`ZCP_AGENT_TOKEN_<SUFFIX>`). For users who would rather not log in inside the container;
  needs the laptop CLI. Env name + adapter pass-through verified in S0.8.
- **Polish, later:** the GUI's pure output parser + handler table
  (`zcp-agent-auth-dialog.output-parser.ts`, `.handlers.ts`) are ours and portable — reuse them
  inside the z3 server (local PTY, no websocket chunking) to render URL / code as a card
  without the terminal. Only if the terminal proves clumsy on a phone.
- **Rejected:** embedding the GUI's dialog in a webview / iframe — it needs the GUI's session
  and its platform terminal, cannot be iframed cross-origin without a GUI change, and has no
  counterpart in the mobile app.
- **Acceptance:** a user with a subscription and nothing else signs in from the terminal card
  on a browser and on a phone, the flag lands within seconds, nothing credential-shaped enters
  the chat; the setup-token card reaches an answering agent with the token never in the chat.
- **Until S7 lands:** the copied subscription login from `z3-eval`'s zcp (§4a).
- **Start here:** `../frontend-legacy/apps/zerops/src/modules/feature/zcp-agent-auth-dialog/`
  (reference), `docs/spec-welcome-mode.md §3–4.2` (state matrix + flag contract),
  `internal/init/adapters/{claude,codex}.go` (what zcp does with the keys),
  `apps/server/src/terminal/Manager.ts` (T3 terminal).

## 7. The user's journey (this is the acceptance narrative)

**New user:** opens z3 → registers (claim flag) → sees "preparing your project" → the project
appears with zcp → if the container is old: "Enable Zerops Code" → restart → connects → a
thread opens with zcp's onboarding greeting. No VPN, no code, no secret typed.

**Existing user:** signs in → picks a project (or *New project*) → thread.

**"Vytvoř mi kanban"** (what the agent does in zcp → what the user sees in z3):

| Agent (zcp) | z3 client |
|---|---|
| discover: proposes `kanbandev` + `kanbanstage` (nodejs) + `db` (postgresql), asks to confirm | **question card** (§8): three services with types; Confirm / Change |
| provision: `zerops_import` → processes; `zerops_mount kanbandev`; env discovery | service map: three rows *creating* → *running*; `kanbandev` gets *mounted*; file tree shows `kanbandev/`; import card with per-service progress |
| close: evidence written; develop starts | strip: `infrastructure ready · 3 services` → `developing kanbandev` |
| writes `zerops.yaml` + code under `/var/www/kanbandev/` | files change; turn checkpoint on the `kanbandev` repo; diff grouped by service |
| `zerops_deploy kanbandev` → build → subdomain; `zerops_verify` | deploy card with build progress → URL chip; map row shows *Open*; verify card `HTTP 200 ✓`; strip `kanbandev deployed ✓ verified ✓ · kanbanstage pending` |
| close-mode decision; git-push setup needs a PAT | question card (auto / manual); **credential card** — token never enters the chat |
| auto-close derived | strip `task complete`; next-task shortcut |

Two threads = two agent processes = two work sessions; bootstrap is exclusive per project —
the strip says "infra session held by thread X" instead of letting the user hit a refusal.

## 8. User questions — one card for every agent

T3 already normalises "the agent asks the user to choose" into provider-agnostic runtime
events: `user-input.requested` / `user-input.resolved` with
`UserInputQuestion { question, header?, options[{label, description}], multiSelect? }`.
Claude Code's `AskUserQuestion`, Codex's `item/tool/requestUserInput` and Grok's ask all map
into it today; the web client renders it and answers through `respondToUserInput`. Build on
this, never on per-provider parsing.

What we add:
1. **Web card quality** — single/multi select, option descriptions, an "Other" free-text
   answer, keyboard navigation, a visible "waiting for you" state in the thread and the strip.
2. **zcp always asks structurally under z3.** Today zcp's atoms and error suggestions hedge:
   "use `AskUserQuestion` when your harness exposes it, else ask in plain text". The z3 server
   sets `ZCP_HARNESS=z3` on the provider process (verify the env passes the adapter's
   blocklist); zcp reads it and drops the hedge — plan confirmation, route choice, close-mode,
   launch scope, blockers with option lists all become structured questions. Add the axis in
   the atom corpus the way other environment axes exist; extend `atoms_lint`, not per-topic
   tests.
3. **Credentials are not questions.** A credential-class ask (PAT, launch token) renders the
   credential card (S6), whose value goes to the service secret through the server — never as
   an answer text the LLM reads.
4. **Future agents** (Cursor, OpenCode) map into the same event when they gain an ask
   primitive; until then their plain-text asks stay plain text.

  is cut from `upstream/main`, the subscription login is stashed (§4a), and the §4a push loop
