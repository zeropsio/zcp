## 1. Frame

A user on Zerops has one z3 project per Zerops project, workspace root `/var/www`, and N dev services mounted at
`/var/www/<host>`. Each is a real git repository — but the repo lives on the *service*, at `/var/www/.git` on host
`<host>`, reachable only over SSH. After S3: a turn editing `kanbandev` and `apidev` yields **two checkpoints**, one
in each service's own `.git`, and the diff lists files as `kanbandev/src/x.ts` / `apidev/main.go` — grouped by
service. Restore targets one service at a time; zero mounts shows "no repositories yet", not an error. Nothing else
about a turn changes.

**The invariant, absolute: no git process ever runs against an sshfs path.** Measured cost of violating it: 12.7 s
per turn vs 1.37 s over multiplexed SSH; 245 s for a first checkpoint on a repo without `.gitignore`; a workspace
rescan that trips T3's own 15 s timeout twice in four runs.

## 3. Design

**(a) The SSH executor.** One new `ChildProcessSpawner` decorator. Per spawn: `command !== "git"` → delegate
verbatim (this leaves `claude`, `codex`, `gh`, `glab`, `az`, shells and node-pty untouched). Else resolve the host —
first from `args[0..1] === ["-C", p]`, else from `options.cwd` — by matching `/var/www/<host>` against the
repository source; no match → delegate verbatim. Match → spawn `ssh <pinned opts> <host> env <K=V…> git -C /var/www
<args…>`, every remote token POSIX single-quoted (zcp's `shellQuote` rule; never `Sprintf`-style concatenation). ssh
passes remote stdout/stderr/stdin through unchanged, so `collectOutput`, the line callbacks and truncation keep
working. Exit code is the remote code, except **255 = ssh transport** → a distinct transport error, never a git
failure. *Pinned options* (S0 decision 2 — pin, do not inherit `~/.ssh/config`): `-l zerops`, `ControlMaster=auto`,
`ControlPath=/tmp/ssh-mux-%r@%h:%p`, `ControlPersist=600`, `BatchMode=yes`, `StrictHostKeyChecking=no`,
`UserKnownHostsFile=/dev/null`, `LogLevel=ERROR`, `ServerAliveInterval=15`, `ServerAliveCountMax=3` — that
ControlPath deliberately matches `zcp:internal/content/templates/ssh-config`, so z3 reuses the master zcp already
holds (8 ms vs 59 ms per round trip; `/tmp` is wiped on restart, masters re-form on demand). *Env:* T3 spreads the
whole `process.env` into the checkpoint env (`GitVcsDriver.ts:721`) — wrong and huge to ship over the wire. Send an
**allowlist** (`GIT_*`, `LC_ALL`) as `env K=V` remote-side, let the login shell supply the rest, strip
`GIT_TRACE2_EVENT` (§h). *Concurrency:* a `Semaphore` per host (4 in flight, under sshd's default `MaxSessions`),
unbounded across hosts — three repos in parallel cost what one does (802 ms vs 2 333 ms sequential).

**(b) The path map — one rule, both directions.** *Everything T3 hands us is mount-side; everything we hand git is
host-side; everything git hands back becomes mount-side again.* `/var/www/<host>` ⇄ `/var/www`. Mapped **inbound**:
`options.cwd`, the value after `-C` / `--git-dir` / `--work-tree`, and path-valued env keys (`GIT_INDEX_FILE`,
`GIT_DIR`, `GIT_WORK_TREE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CEILING_DIRECTORIES`).
Never the rest of argv — a commit message or pathspec containing `/var/www` must not be rewritten. Mapped
**outbound**: stdout of exactly two argv shapes — `rev-parse --show-toplevel` (`RepositoryIdentityResolver.ts:100`,
`GitVcsDriver.ts:502`, `GitVcsDriverCore.ts:1074`, `:2470`) and `worktree list --porcelain`
(`GitVcsDriverCore.ts:2557`). Nothing else emits an absolute path: `--git-common-dir` returns `.git` *relative*, and
both consumers resolve it against the mount-side cwd (`GitVcsDriver.ts:707`, `GitVcsDriverCore.ts:1064-1066`) —
correct unmapped, and it keeps the local `fileSystem.realPath` at `:1067` working through the mount. Assert that
relativity; map the absolute form defensively. **cwd for providers and terminals stays the mount path**
(`ProviderCommandReactor.ts:653-657`, `ws.ts:2228-2231`) — the agent never sees a host path.

**(c) temp index, (d) identity resolver, (h) hook progress — three deliverables that fall out of (a)+(b) with no
code of their own.** *(c)* `captureCheckpoint` joins the returned common dir with a uuid (`GitVcsDriver.ts:714-717`)
→ a **mount-side** path; the map turns it host-side for `env GIT_INDEX_FILE=…`, so git writes the index on the
host's own disk, and the local cleanup `fileSystem.remove()` at `:728-730` unlinks it **through the mount** — a
by-path operation, immediate (S0.4: `stat` 11–23 ms; only *directory listings* lag 20 s). *(d)* The identity
resolver never reaches the driver — it calls `ProcessRunner` directly, and the spawner sits below `ProcessRunner`
(`processRunner.ts:307`), so it gets the same executor and the same map **with the file untouched**; the brief's
deliverable met by a different mechanism. *(h)* The trace2 monitor writes `GIT_TRACE2_EVENT` to a **local** temp
file and `fs.watch`es it (`GitVcsDriverCore.ts:497-500, 604`) — meaningless under SSH, and inotify never fires for
host-side changes anyway (S0.4). The spawner strips the variable, the callbacks never fire, and the cost is nil: the
only producer of hooks is `commit`, which is zcp's job (§k).

**(e) Enumeration — the Zerops repository source.** Shell out to `zcp studio topology` from `/var/www` (a direct,
ES-lag-free read: `zcp:cmd/zcp/studio.go:123-142` → `ops.Discover` → `ListServicesDirect`; 0.26 s for 5 services).
Take services with a non-empty `mountPath` that are not `isInfrastructure` → `{host, mountPath: "/var/www/<host>",
remotePath: "/var/www"}`; TTL cache 30 s, refreshed at turn start. **Never scan for `.git`.** Ledger correction:
`verified.md` S0.11's field list omits `mountPath` — it *is* emitted, via `tools.EnrichWithMetaStatus` →
`zcp:internal/tools/discover.go:127-131`, which stats `/var/www/<hostname>`. Two distinct empties: topology
**unavailable** (no creds / call failed) → degrade, name the reason, warn once, skip checkpointing; **zero mounted
runtimes** → "no repositories yet". S6's feed later replaces the shell-out behind the same interface.

**(f) Per-service grouping.** The refs need **no rename**: each repo has its own ref store, so
`refs/t3/checkpoints/<b64(threadId)>/turn/<n>` (`checkpointing/Utils.ts:6-10`) is unambiguous *within* each service,
and one string names the turn in all of them. `projection_turns` therefore needs no migration either — `UNIQUE
(thread_id, checkpoint_turn_count)` and the single `checkpoint_ref` column (`Migrations/005_Projections.ts:85-90`)
stay as they are, the repo set recovered at read time from (e). Fan-out lands in
`CheckpointReactor.captureAndDispatchCheckpoint` (`:221-352`): N captures concurrently, N diffs merged into the one
flat `files[]` (`orchestration.ts:362-369`), each path prefixed `<host>/`. Sorted by path that renders grouped by
service, with **zero contract change**.

**(g) Worktree mode, enforced not defaulted.** Force `worktreePath: null` in `decider.ts:379` (`thread.create`) and
`:849` (`thread.meta.update`), and `defaultThreadEnvMode: "local"` at `:289-291` (`project.meta.update`) — the
single state transition every command funnels through, so neither a `t3.json` file nor a crafted RPC can flip it
back. Belt: skip the `prepareWorktree` branch in `ws.ts:890-893` so `createWorktree` at `:1068` is unreachable. One
helper in a new file, called from three one-liners, keeps the rebase diff minimal.

**(i) Rescan on the host.** Decided by evidence: the index is `@ff-labs/fff-node`'s native Rust `FileFinder`
(`workspace/WorkspaceSearchIndex.ts:306-308`), whose `basePath` is strictly local-fs — it **cannot** be pointed at a
remote host. Rooted at `/var/www` it scans every mount at once: 2.6–16 s for 94 k dirents, past
`WORKSPACE_INDEX_SCAN_TIMEOUT_MS = 15_000` (`:31`) in two of four runs, versus 483 ms for `ssh host find`. So the
whole workspace surface moves off the mount: a Zerops `WorkspaceEntries` serving `list`/`search` from `ssh <host>
find` per repo, merged into one mount-relative namespace, and `searchContents` from `ssh <host> grep`. The three
existing `refresh()` triggers work unchanged (`CheckpointReactor.ts:260`, `:775`, `WorkspaceFileSystem.ts:296`).

**(j) Poll / detection TTLs.** The numbers say **leave them alone**: at 85 ms per `status` over multiplexed SSH the
30 s cadence (`VcsStatusBroadcaster.ts:28`) is cheap — the mount, not the cadence, was the problem. Two exceptions,
both one-line and optional to the rest of the slice. (1) **Disable the automatic upstream refresh**:
`statusDetailsRemote` triggers a background `fetch --quiet --no-tags` at ≥15 s per remote (`GitVcsDriverCore.ts:56,
1014-1030, 1261-1274`); remotes and push are zcp's domain, and once a PAT-backed origin exists that is unwanted
network from N services — pass `refreshUpstream:false` (`GitManager.ts:1119-1121`). (2) Raise `DETECTION_CACHE_TTL`
(`VcsDriverRegistry.ts:15`) from 2 s to 60 s — a mounted service's repo identity does not change.

**(k) The stacked commit→push→PR action.** Hidden **and** refused. `ExecutionEnvironmentCapabilities` already
carries `pullRequests?: boolean` (`environment.ts:61`, hardcoded `true` at `ServerEnvironment.ts:142-165`, read at
`ChatView.tsx:2122`): set it `false`. Add one optional sibling `vcsStackedActions?: boolean` for the commit/push
half and guard the single `<GitActionsControl>` render (`ChatHeader.tsx:404-409`). Hiding a button is not
enforcement, so `GitManager.runStackedAction` (`:2179-2384`) also refuses server-side — same lesson as (g). Never
two commit pipelines.

**(l) The `add -A` guard.** `add -A` (`GitVcsDriver.ts:744-748`) swallows every untracked file, and `status` never
reveals it because it collapses untracked directories. Before the *first* capture on a repo, probe `ls-files
--others --exclude-standard -z` with `maxOutputBytes` capped at 256 KB and treat the executor's own
`stdoutTruncated` flag as the signal (≈4 000 paths) — no new threshold invented, probe stays cheap. On trip:
**refuse that repo's checkpoint**, warn naming the collapsed offenders (`--directory --no-empty-directory`), let the
turn proceed — capture is already best-effort (`CheckpointReactor.ts:209-211`). Companion, a **separate zcp slice
out of S3**: `zcp:internal/ops/git_identity.go:78-81` initialises the repo and writes **no `.gitignore`**.

**Restore, one behaviour change.** `restoreCheckpoint` runs an unguarded `clean -fd` (`GitVcsDriver.ts:816-820`). On
a laptop the tree is a checkout; on Zerops it is a **running application's disk** — uploads, sqlite files and logs
the live app wrote after the checkpoint sit right there. So: restore tracked files only (`restore --worktree
--staged` + `reset`), no `clean -fd`; then refresh what z3 shows over SSH, because the mount's listing lags 20 s
(S0.4 reverse).

## 4. How the driver knows it is on Zerops

**Decided by S1, and S3 does not define a second rule:** `process.env.T3CODE_ZEROPS_PROJECT_ID` set and non-empty ⇒
Zerops; nothing else votes. The predicate lives in `apps/server/src/zerops/ZeropsEnvironment.ts`, S1's file on branch
`z3-s1`, exported for S3 to import. S3 consumes it at two decision points — SSH driver selection (§a) and the
server-side `worktree mode = local` forcing (§g) — plus every other Zerops branch in §3 transitively. The property
S3 leans on is that it **fails closed**: absent ⇒ every branch here is dead, upstream behaviour bit-identical.
Two consequences for this stream, neither re-opening the decision. (1) A raw `process.env` read is not injectable
the way an Effect `Config` value would be, so S3's unit tests drive it by **setting the variable around the case**
rather than providing a layer. (2) S3.1 is no longer self-contained — it imports a file S1 owns (risk 1).

Dependency order. Each is one rebase on `upstream/main` → RED → GREEN → verify → report. Verification targeted only

## 6. Risks / open questions

1. **S3.1 now imports S1's `ZeropsEnvironment.ts`** (§4, branch `z3-s1`), so the "first slice merges alone" property
   is gone and the streams are coupled at their first commit. *Settle:* land that one file on the integration branch
   ahead of both streams, or start S3.1 after `z3-s1` — a scheduling call for the orchestrator, not a design one.
2. **A global `ChildProcessSpawner` override sits under every spawn in the server**; non-git passthrough
   must be byte-identical. *Settle:* a RED identity test, plus one `z3-eval` session read argv by argv.
3. **`zcp studio topology` needs API credentials in the z3 unit's environment** — present in the
   container's process env (S0.11), but `zcp init z3` creates the unit. *Settle:* run the call from
   inside the unit's environment, not from an ssh login shell.
4. **sshd `MaxSessions` caps concurrent channels per host** and the fan-out assumes 4. *Settle:*
   `ssh -O check` plus a 16-way parallel probe against one dev service; adjust the semaphore.
5. **Post-restore visibility** — host-side deletes stay visible through the mount ~20 s (S0.4 reverse),
   so a restored tree can read stale. *Settle:* re-read affected paths over SSH after restore, and
   measure the user-visible window once on `z3-eval`.
6. **The identical-ref-per-repo trick (§f) is untested against the revert rewrite** at
   `ProjectionPipeline.ts:1489-1508`, which deletes and re-inserts a thread's turn rows. *Settle:* a unit
   test over the projection with two repos and a revert — cheap, no live target.
7. **Upstream churn** — `vcs/` and `checkpointing/` are active (~15 commits/day). *Settle:* rebase at
   every slice start; all real logic lives in new files, so only the `decider.ts` / `ws.ts` /
   `CheckpointReactor.ts` one-liners can conflict.
8. **`@ff-labs/fff-node`'s ignore semantics are inside a closed-source Rust binary** — whether it skips
   `node_modules` decides whether S3.5 is required or merely nice. *Settle:* one timed `list` call on the
   container against a mount containing `node_modules`.

**Ledger items to write when the work starts:** `verified.md` S0.11 gains the `mountPath` correction (§e).
`hacks.md` **H-14** ("keep the project root a real local directory, mounts outside it") is **superseded** by D3 + S0
decision 1 and must be re-stated — its "real fix" is now the opposite of the product direction, and leaving it as
written will mislead the next reader.

## 7. Out of scope

Git identity, remotes, `push` and repo initialisation — all zcp's, reached from z3 only by the agent through MCP ·
the zcp-side `.gitignore`-on-init slice (§l), a separate zcp `/flow` run · S6's topology and lifecycle feeds (S3
shells out behind an interface S6 replaces) · S1's auth, membership and CORS · checkpoint ref retention/GC (upstream
prunes only on revert, `CheckpointReactor.ts:793-796`; nothing deletes refs on thread delete — a real gap, not this
stream's) · content-search parity beyond the `ssh grep` fan-out · desktop and mobile clients.

## 8. What shipped

Landed on `z3-s3` and merged into `z3`: S3.1 repository source · S3.2 SSH git spawner · S3.3 policy
(worktrees off, one commit pipeline, no background fetch) · S3.4 multi-repo checkpoints, grouped diff,
non-destructive restore · the untracked-file guard and its fix · the topology-read convergence onto S6's
`ZeropsCli` · checkpoint-ref pruning on `thread.delete`.

**S3.5 was not built, and the measurement says it is not needed.** Plan risk 8 was decided live on
`z3-eval`: with 32 764 dirents under `/var/www` — two docusaurus clones plus a mount carrying a
19 308-file `node_modules` — the native `FileFinder` reached `waitForIndexReady` **ok in 2.0 / 3.6 /
2.0 s**, nowhere near `WORKSPACE_INDEX_SCAN_TIMEOUT_MS`. It returns paths already mount-relative and
indexes the unignored service, yet **no `node_modules` path** comes back for any query, so it excludes
them without a `.gitignore`. Reimplementing `search`/`searchContents` over `ssh find`/`grep` would have
replaced a closed-source ranked index (frecency, smart case, grep cursors, per-file caps, time budget)
with something measurably worse.

### Known costs, accepted

- **Two processes read the topology.** S6's feed (`ZeropsCli` under `ZeropsTopology`: doorbell + 3 s
  active poll) and this stream's `ZeropsRepositorySource` (30 s TTL) each spawn their own
  `zcp studio topology`. The convergence removed the duplicated *code* — one implementation, one
  parser, one error taxonomy — but not the second process. Collapsing them means the source consuming
  the feed's published snapshot, and the feed sits above the git spawner in the layer graph while the
  source must sit below it; that is a graph change the owner declined for now.
- **`ZeropsCli` is constructed inside the source's layer, not taken from the context.** `ZeropsCli.layer`
  provides the `ProcessRunner` *tag*; a runner memoised against the raw spawner could then reach
  `RepositoryIdentityResolver`, which runs **git** through that same tag — putting git back on the
  sshfs mount. The local construction is load-bearing, not style.
- **Ref pruning changes behaviour off Zerops too.** Deleting a thread now removes its hidden checkpoint
  refs everywhere, where upstream left them. Judged correct — the refs are named by thread id and are
  garbage once the thread is gone — but it is a change beyond the Zerops path.
- **The probe runs on every capture**, not once per repository. The memoisation that avoided that was
  the guard's whole failure: the reactor drives the baseline twice per turn, so the second call
  committed the tree the first had refused.
