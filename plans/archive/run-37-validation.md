## Top 5 surprises

### 1. v9.78.0 binary actually ran this time

The pre-flight gate caught run-36's silent version drift (binary
running was pre-v9.78.0; templates rendered v9.77.0 shape). Run-37's
pre-flight passed cleanly — every v9.78.0 marker present. **The lesson
the user already drew from run-36 — add a pre-flight version gate at
zcprecipator3 `start` (engine emits version into `plan.json`;
validation reports read it; mismatch fails loudly before payment) —
should still ship**: today the gate is "ask the validation agent to
read the artifacts first," which works but costs a manual check. An
automated gate would catch the next drift before payment. Not blocking
this iteration's close.

### 2. RF1+PD1 leaked onto appdev — substrate-fix side-effect

Run-35 had RF1+PD1 only on apidev. Run-37 has them on apidev AND on
appdev. The engine gate enforces presence on the canonical apps-repo
(apidev) but doesn't forbid it on others — so the duplication is
silent. The substrate teaching is "the api/central-app codebase owns
this section" but the agent applied it to every codebase that has
`base: nodejs@22` or `base: static` (i.e. every apps-repo). 

Hypothesis: when the substrate added the lead-pattern teaching in the
env-content brief (substrate fixes 3-5), the agent's stitch logic for
RF1/PD1 may have been re-derived from the same brief and over-applied.
Need to inspect cc-content sub-agent logs for `Recipe features` /
`Production vs. Development` stitch counts vs run-35 to confirm.

**Recommended next move (per "engine teeth beat substrate teaching"):**
add an absence-gate to `gate_canonical_apps_repo.go` — non-canonical
apps-repos must NOT contain RF1+PD1. Three lines of Go + table-driven
test. Pin alongside the existing presence gate.

### 3. Tier-4 db+cache comments still TY2 BAD — substrate fix #5 partial residual

Run-35's TY2 BAD pattern was the lead "Single-instance Postgres —
restoring from snapshot still means downtime, the rehearsal-grade
tradeoff at stage." Run-37 closed this on tier 0 (jetstream-pure 8/8),
tiers 1-3, and tier 5 (HA-cluster shape naturally leads with role).
Tier 4 (Small Production) reproduced it on db (`# Single-instance
NON_HA Postgres — restoring from snapshot means downtime, the small-
prod tradeoff`) and cache (`# Single-instance NON_HA Valkey — the
api's cache demo and queue counters tolerate a brief restart window`).

Why tier 4 specifically? Hypothesis: tier 4 is the "small-prod" tier
where the porter is past rehearsal — the operational-tradeoff voice
is the *thematically natural* lead for this audience, so the agent
reverted to the teaching it had pre-substrate-fix. Tier 5 avoided the
trap because HA-cluster shape naturally leads with role. Tier 3 avoided
it because the rehearsal-tier audience-purpose absorbed the descriptor.

Recommended next move if persistent in run-38: engine teeth — complete-
phase gate refusing managed-service comments on production tiers that
lead with `restoring from snapshot` / `tolerate a brief restart window`
/ similar tradeoff-lead patterns. Or substrate-side TY2 worked-BAD
example explicitly on the small-prod tier (currently the substrate's
worked-BAD example is only on stage tier).

every cross-service reference under a fresh own-key…" — recipe-already-
