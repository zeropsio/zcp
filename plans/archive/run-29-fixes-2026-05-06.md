## Fix #1 — Brief delivery: designed disk-fallback (TRANSPORT)

### Surface symptom

Run-28 main session hit MCP cap on three `build-subagent-prompt` calls
(cc-api 79,874 / cc-worker 78,251 / refinement 85,727). Each OOM
triggered a 1500-char help-text recovery instructing the main agent
to `python3 -c "print(open('...').read()[A:B])"` slice the saved file.
Main agent did 7 jq extractions to `/tmp/<*>-prompt.txt`, then dispatched
each sub-agent with a thin wrapper pointing at the temp file.

Run-22→26→27→28 cap history: 44 KB → 48 → 52 → 56 → 60 → 64 KB
([briefs.go:189-201](internal/recipe/briefs.go) `RefinementBriefCap = 80 * 1024`,
codebase-content cap implicit). Each bump shipped under-cap then drifted
over as new atoms / facts landed. The treadmill was already noted in
[briefs_content_phase.go:218-222](internal/recipe/briefs_content_phase.go):
*"Resist the cap-bump habit — the 56 KB cap was already bumped 44→48→52→56."*

### Root cause

Brief delivery uses MCP tool result inline JSON (`{"ok":true,"action":
"build-subagent-prompt","slug":"...","prompt":"<escaped body>"}`). The
prompt body is JSON-string-escaped (every `\n` → `\\n`, every `"` → `\\"`),
inflating ~5%. For an 81 KB body, the encoded JSON exceeds the ~80 KB
MCP tool-result cap. Lowering the body cap is reactive — the underlying
shape (inline-in-JSON) is fundamentally cap-bound while content grows.

The runtime ALREADY persists oversized results to disk
(`/home/zerops/.claude/projects/.../tool-results/mcp-zerops-zerops_recipe-<id>.txt`)
and returns help-text describing how to slice it. **The fix is to make
disk-write the designed primary path for large briefs**, not the
error-recovery fallback path.

### TEACH/DISCOVER classification

TEACH — engine-construction transport reshape. Same for every recipe;
expressible as a positive shape ("when brief > X, write to disk and
return pointer"). No regex, no ban-list. Per system.md §4: *"Recoverable
as TEACH: rewrite as engine-emitted shape."*

### Fix shape

Threshold: `BriefDiskFallbackThreshold = 40 * 1024` bytes. Below the
cap, the inline path stays; above, engine writes and returns pointer.
40 KB chosen empirically: even with ~5% JSON-escape inflation + envelope
overhead, 40 KB body → ~43 KB encoded result, comfortably under MCP cap.
Test predicate: `Brief.Bytes > Threshold` triggers the disk path; agents
never see OOM on briefs the engine could deliver.

Engine path:

1. Add `BriefDiskFallbackThreshold` constant in
   [internal/recipe/briefs.go](internal/recipe/briefs.go) alongside the
   existing `RefinementBriefCap`.
2. In `handleBuildSubagentPrompt`
   ([handlers.go:433-472](internal/recipe/handlers.go)), after
   `buildSubagentPromptForPhase` returns the prompt string:
   - If `len(prompt) > BriefDiskFallbackThreshold`:
     - Write to `<sess.OutputRoot>/.briefs/<kind>-<codebase>-<unix>.md`
       atomically — mirror the existing atomic-write pattern in
       [plan.go::WritePlan](internal/recipe/plan.go) lines 240-264
       (`os.CreateTemp` + `(*os.File).Sync` + `os.Rename`). `OutputRoot`
       is populated before this handler runs (set at handlers.go:148 via
       `NewSession` and handlers.go:302 via `OpenOrCreate`).
     - Set `r.Prompt = ""` (no inline body).
     - Set `r.BriefPath = <abs path>` and `r.BriefSize = len(prompt)`.
     - Set `r.Hint = "brief written to disk; dispatch sub-agent with this path"`.
   - Else: existing inline path unchanged.
3. Extend `RecipeResult` shape ([handlers.go:203](internal/recipe/handlers.go))
   with optional fields: `BriefPath string` (json `briefPath,omitempty`)
   and `BriefSize int` (json `briefSize,omitempty`). `Prompt` stays as-is for
   inline path. `BriefSize` is a byte COUNT (int), not the body bytes —
   the body lives on disk; the count lets the main agent sanity-check the
   pointer before dispatching the sub-agent (small-int response, not
   payload-bearing).
4. Update the build-subagent-prompt action documentation in `RecipeInput`
   to teach: *"For briefs > 40 KB, response carries `briefPath` instead
   of `prompt`. Dispatch sub-agent with a thin wrapper telling it to
   Read briefPath first thing."*

Brief atom path (so the main agent learns the dispatch shape):

5. Extend
   [internal/recipe/content/phase_entry/codebase-content.md](internal/recipe/content/phase_entry/codebase-content.md)
   and the parallel phase entries (refinement, env-content) with a
   "Dispatch — inline-or-pointer" section teaching the two-shape result
   pattern. Brief body teaches the agent to read the response, not the
   plumbing — agent doesn't care which shape; the dispatch wrapper
   handles both.

### Tests

`internal/recipe/briefs_disk_fallback_test.go`:

- `TestHandleBuildSubagentPrompt_BriefUnderThreshold_ReturnsInline` —
  composed brief is 30 KB → response carries `Prompt` non-empty,

- `TestHandleBuildSubagentPrompt_BriefOverThreshold_WritesDiskAndReturnsPointer` —
  composed brief is 50 KB → response carries `Prompt=""`, `BriefPath` is
  absolute, file at path contains exact composed prompt body.
- `TestHandleBuildSubagentPrompt_DiskWrite_AtomicSyncRename` — verify
  the writer uses temp + rename pattern; injected partial-write doesn't
  leave a half-written file at the target path.
- `TestHandleBuildSubagentPrompt_DiskWriteFails_ReturnsError` — disk
  full / permission denied → `r.Error` populated; no half-state.
- `TestRecipeResult_BriefPath_OmitemptyJSON` — JSON marshaling drops
  `briefPath` and `briefBytes` when empty (back-compat for existing
  consumers).
- `TestPhaseEntryCodebaseContentAtom_TeachesInlineOrPointer` — atom
  contains the dispatch-shape teaching.

`internal/recipe/handlers_test.go` (extension):

  fixture-driven: nestjs-showcase worker codebase-content brief (the
  largest run-28 shape, 78 KB) verifies disk-fallback path fires; no
  inline body in response.

### Dual-mode rollout note

`RecipeResult` extension is purely additive — `Prompt` field stays
populated for under-threshold briefs (existing consumers continue to
read it). Over-threshold response carries `BriefPath` + `BriefBytes`
ALONGSIDE `Prompt=""`. Existing consumers that only read `Prompt`
will see an empty string and must update to handle the pointer shape.
The transition is breaking-then-replace, not deprecation:

- Engine code path lands in one commit.
- All in-tree consumers updated in same commit (sim CLI, replay
  tooling, e2e tests).
- Documentation in `RecipeInput.Action` JSON-schema description teaches
  the two response shapes so external consumers (the live MCP main
  agent) update their dispatch wrapper.

Test: `TestHandleBuildSubagentPrompt_OverThreshold_PromptIsEmptyBriefPathSet` —
verifies the contract (no dual-population to avoid confusion).

### What this fix does NOT do

- Does NOT lower `RefinementBriefCap`. Disk-fallback removes the need.
  The eviction code stays as defense-in-depth (if `OutputRoot` is empty
  in some edge path, eviction prevents unbounded growth).
- Does NOT touch `composeRefinementFactsBlock` or any of the existing
  Fix #2 plumbing. Run-28 fix #2 holds at its current shape.
- Does NOT add a regex check on brief content.
- Does NOT populate `Prompt` AND `BriefPath` on the same response.
  Either-or semantics; consumers branch on `BriefPath != ""`.

## Fix #2 — IG #1 validator scope correction

### Surface symptom

[apidev/README.md:16-18](docs/zcprecipator3/runs/28/apidev/README.md) IG
#1 ships as a 2-line pointer (*"The full annotated yaml lives at
`/zerops.yaml`..."*) instead of the full annotated yaml verbatim. appdev
and workerdev IG #1 both correctly embed the yaml. The cc-content
sub-agent overrode IG #1 to clear the `codebase-ig-scaffold-filename`
validator that flagged `migrate.ts`/`seed.ts` literals
([TIMELINE.md:107](docs/zcprecipator3/runs/28/TIMELINE.md)).

### Root cause

[validators_codebase.go:81-93](internal/recipe/validators_codebase.go) bans
`migrate.ts`/`seed.ts`/`main.ts`/`api.ts` literals across ALL IG content:

```go
scaffoldOnly := []string{"migrate.ts", "seed.ts", "main.ts", "api.ts"}
for _, name := range scaffoldOnly {
    if strings.Contains(ig, name) {
        vs = append(vs, violation("codebase-ig-scaffold-filename", path, ...))
    }
}
```

The validator's intent (per the comment): *"porters bringing their own
code don't have these files; an IG item naming them is giving scaffold
implementation."* That intent is correct for IG #2-#N narrative prose.
But IG #1 is engine-stamped from the codebase's verbatim zerops.yaml
([handlers.go:1105](internal/recipe/handlers.go) — *"engine-stamped IG #1
yaml block"*). When the codebase's actual zerops.yaml contains
`run.initCommands: [npx ts-node -T src/migrate.ts]`, IG #1 contains
`migrate.ts` BY ENGINE CONSTRUCTION.

The validator catalog-drift: it bans strings the engine itself emits.
Per system.md §4: *"a piece of DISCOVER-side knowledge gets reified as an
engine-side ban-list because a specific run produced a specific bad
output."* The agent's evasion (delete engine-emitted yaml) became the
shape that ships.

### TEACH/DISCOVER classification

The original `codebase-ig-scaffold-filename` validator (validators_codebase.go:81-93)
is a textbook catalog-drift artifact per system.md §4: a string-ban
list reified into an engine Blocking gate because run-K shipped output
the analysis named. Per §4 lifecycle ("Recoverable as TEACH: rewrite as
engine-emitted shape. Example: IG item #1 was originally enforced by
validator; now engine *emits* the item from the yaml itself, so the
validator is structurally unnecessary"), the corrective action splits:

- **TEACH-side** — the engine ALREADY emits IG #1 from the codebase's
  verbatim zerops.yaml. The shape is enforced by construction.
- **DISCOVER-side** — the underlying intent (porters bringing their own
  code don't have `migrate.ts`/`seed.ts`/`main.ts`/`api.ts`) becomes a
  record-time Notice — signal, not gate.
- **Validator deletion** — the Blocking regex check is structurally
  unnecessary once the positive-shape teaching covers the IG #2-#N
  authoring contract.

### Fix shape

Three-part fix:

**1. Delete the Blocking scaffold-filename ban** in
[validators_codebase.go:81-93](internal/recipe/validators_codebase.go).
The for-loop emitting `violation("codebase-ig-scaffold-filename", ...)`
is removed. Per system.md §4 corrective example for IG #1.

**2. Demote the underlying signal to a record-time Notice** at
`record-fragment` time. When the agent records a `codebase/<host>/integration-guide`

OUTSIDE the engine-emitted IG #1 yaml fenced block, emit a non-blocking
Notice on the response: *"IG step prose mentions a scaffold-source
filename — porters bringing their own code don't have these. Consider
demoting the teaching to a code-comment in the codebase, or rewriting
the IG step around the platform contract (init-commands key shape,
the env-var alias rule) rather than the recipe's own helper file."*
Notice path lives in
[handlers_fragments.go::recordFragment](internal/recipe/handlers_fragments.go)
line 32 onward; the Notice emission shape mirrors the
`refinement-replace-reverted` `SeverityNotice` path at
[handlers.go:612-625](internal/recipe/handlers.go) (run-22 R3-C-3

**3. Positive shape teaching in the brief atom** — extend
[internal/recipe/content/briefs/codebase-content/synthesis_workflow.md](internal/recipe/content/briefs/codebase-content/synthesis_workflow.md)
with two adjacent rules:

```md

## Fix #3 — Tier-yaml comment scope teaching (per_tier_authoring atom)

### Surface symptom

Run-28 tier 3 + tier 4 import.yamls contain 5 `Switch ... to HA at tier 5` /
`Switch mode to HA once you need failover` sentences in service-block
comments (db / cache / broker). Spec Surface 3 §107-108 forbids
tier-promotion narratives in service blocks — the goldens
(laravel-showcase, laravel-jetstream) write none.

### Root cause

[per_tier_authoring.md:86](internal/recipe/content/briefs/env-content/per_tier_authoring.md)
teaches the friendly-authority phrasing list:

```
- *"Bump ... if ..."* / *"Switch ... when ..."*
- *"... once you ..."* (conditional adapt)
```

[embedded_rubric.md:215](internal/recipe/content/briefs/refinement/embedded_rubric.md)
anchors 9.0 quality at *"≥3 phrasings AND each tied to a real adapt
path the porter would actually take."*

[embedded_rubric.md:617-633](internal/recipe/content/briefs/refinement/embedded_rubric.md)
forbids tier-promotion narratives — but **scopes the rule explicitly to
"Tier README extracts"**, not yaml service-block comments.

The agent followed the rubric byte-for-byte: pick a porter signal,
write `Switch ... when`, score 9.0. The signal it picked at tier 3
NON_HA db block was *"once you need failover without a manual-restore
window"* — naturally a tier-5-graduation event because tiers 3→5 ARE
the recipe's NON_HA→HA design ladder.

The vocabulary teaches PROMOTION verbs (Switch, Bump, Adjust), the
9.0 anchor REWARDS naming a porter signal, and the forbidden rule
DOESN'T COVER the surface where these verbs land.

### TEACH/DISCOVER classification

TEACH — atom-level positive scope teaching. Same for every recipe;
expressible as a positive rule (porter signal must reference a knob
reachable WITHIN this tier's deployment shape). Not a regex ban-list —
the regex test in §Run-29 success predicates is the OBSERVABLE; the
fix is the positive teaching that prevents the shape.

### Fix shape

Extend [per_tier_authoring.md](internal/recipe/content/briefs/env-content/per_tier_authoring.md)
with a new section AFTER the canonical phrasing patterns block (line 87)
and BEFORE the worked examples (line 106):

```md
## Porter signals MUST be reachable within THIS tier's deployment shape

A friendly-authority phrasing names an adapt path — a knob the porter
turns to handle a different deployment context. The knob must be
something the porter changes WITHIN this tier's yaml, not a path that
crosses the tier ladder.

**Within-tier knobs (adapt paths — porter signals OK):**

- `verticalAutoscaling.minRam` / `maxRam` — RAM headroom adjustments
- `minFreeRamGB` — spike-buffer tuning
- `objectStorageSize` — storage quota
- `backup` retention windows
- `enableSubdomainAccess` toggle
- `initCommands` script keys (`.v1` → `.v2` re-run lever)
- Per-service environment-variable values

**Cross-tier moves (NOT adapt paths — DO NOT NAME):**

- `mode: NON_HA` ↔ `mode: HA`
- `minContainers` jumps that cross the tier ladder's design points
- `corePackage` tier changes
- Runtime base swaps (`@22` → newer LTS at a tier rollover)
- Adding/removing a service from the canonical set

The recipe's tier ladder ALREADY encodes the cross-tier moves — the
porter graduates by re-importing a higher tier yaml, not by editing
this one. A comment that says *"Switch mode to HA at tier 5 if X"*
names a path the porter takes by changing tiers, not by editing this
yaml; that's tier-promotion narrative, not friendly-authority.

### Worked example — db block at tier 3

**BAD** — names a cross-tier knob as an adapt path:

```yaml
- hostname: db
  type: postgresql@18
  mode: NON_HA
  # Single instance — restoring means downtime; acceptable at stage.
  # Switch mode to HA once you need failover without a manual-restore
  # window.
  verticalAutoscaling:
    minRam: 0.25
    minFreeRamGB: 0.25
```

The "Switch mode to HA" sentence reaches across the tier ladder — porter
graduates to tier 5 to get HA, doesn't edit this yaml. Forbidden.

**GOOD** — porter signal stays within-tier:

```yaml
- hostname: db
  type: postgresql@18
  mode: NON_HA
  # Single instance — restoring means downtime; acceptable at stage.
  # `minFreeRamGB` headroom prevents swap thrash during rehearsal load
  # spikes; bump verticalAutoscaling.minRam if QA load runs push the
  # working set above 0.25 GB.
  verticalAutoscaling:
    minRam: 0.25

### Surface symptom

### Root cause

Criterion-6 dups across IG ↔ yaml-comment pairs slip through when the
phrasing isn't byte-identical.

### TEACH/DISCOVER classification

TEACH — positive authoring-order rule. Same for every recipe;
expressible as a positive shape ("yaml-comments first; IG steps
cross-reference"). The author-time order rule prevents the duplication
by construction; refinement Criterion-6 sweep stays as defense-in-depth.

### Fix shape

Per spec-content-surfaces.md §Surface 4 (lines 152-179) and §Surface 7
(lines 275-302), the surfaces have DISTINCT ownership:

- **IG (Surface 4)** owns *porter-transferable mechanism teaching*

  their OWN code.
- **zerops.yaml comments (Surface 7)** own *field-adjacent WHY-choices*

Extend [synthesis_workflow.md](internal/recipe/content/briefs/codebase-content/synthesis_workflow.md)

```md
## Surface ownership — mechanisms on IG, field-choices on yaml comments

The four codebase-content fragments do NOT share content equally. Each
surface owns a distinct content class per spec-content-surfaces §§4, 7:

- **IG #2-N owns porter-transferable mechanisms.** A mechanism is a
  general rule the porter applies to their OWN code: bind to 0.0.0.0,
  set `trust proxy`, alias-own-key vs platform-side env names, drain on
  SIGTERM, build-time-bake for static SPAs. The teaching transfers —
  the porter reads it and changes their own application code.
- **zerops.yaml comments (Surface 7) own field-adjacent WHY-choices.**
  A WHY-choice explains a specific field's value in THIS codebase's
  deployed runtime: why `execOnce` wraps migrate, why
  `--retryUntilSuccessful` bounds the boot retry, why `deployFiles:
  ./` in dev vs `./dist/~` in prod, why `npm ci` in prod vs `npm install`
  in dev. The teaching does NOT transfer (it's about THIS yaml's
  specific fields).
- **KB owns post-deploy symptoms.** A KB bullet starts with a symptom

  second container's boot") that mechanism-teaching alone wouldn't
  surface.

   recorded facts surface, write an IG step. The mechanism's mechanism-

   `npm install` line).
2. **Author zerops.yaml comments second, as field-adjacent WHY-choices

   own-key on the left."* The comment owns WHY-this-name-here; IG owns
   the mechanism that justifies the rule.
3. **Author KB last.** If a KB candidate restates an IG mechanism, drop
   it. KB only adds value when it surfaces a symptom mechanism-teaching
   wouldn't preempt.

Each Zerops mechanism is taught on exactly ONE surface (IG); the yaml
comment cross-references when the field's choice flows from that
mechanism. Cross-references replace duplications.

### Worked example — same-key shadow trap (api codebase)

The yaml comment teaches the mechanism. Surface 7 owns field-adjacent

```md
## Dev loop — appdev HMR first, cross-deploy last

For each feature card (Items / Cache / Queue / Storage / Search):

1. **Author the card on appdev.** Self-deploy via `git push` is the
   only deploy; the dev container's HMR (`npm run dev` already running

   on appdev. The bundle is the same one appstage will run; build
   pipeline is shared. There is no class of bug visible only on
   appstage that is invisible on appdev.

   all five cards browser-walk green on appdev, ONE cross-deploy
   verifies the production bundle path (build-time `VITE_API_URL`
   bake, CORS allow-list, TLS termination, `dist/~` strip). One pass
   per feature-pass; not one per iteration.

### Why this matters

`zerops_deploy sourceService=appdev targetService=appstage` runs
`npm ci` + `vite build` + ships `dist/~`. That's 30-60 s per
iteration. Eight iterations cost 4-8 min — equal to the entire
features-frontend pass for two cards in run-26. Run-28 features-
frontend agent dispatched 8 cross-deploys debugging one card; the
right loop was appdev HMR + browser-verification + a single
cross-deploy at close.

### When cross-deploy IS the right tool

- The card's behavior depends on a build-time env-var bake
  (`VITE_API_URL`) and you suspect the bake is wrong. Cross-deploy
  once; inspect the compiled JS.
- A CORS / cross-origin / TLS issue surfaces only against the
  HTTPS subdomain (appstage), not the dev http://localhost path
  (appdev with port-forwarded HTTPS via L7 covers most of these).
- The feature-pass is closing and you want stage-side smoke. One
  cross-deploy.

### When cross-deploy is the WRONG tool

- The click handler doesn't fire. Fix on appdev — same JS.
- A fetch returns wrong data. Fix on appdev — same backend.
- A card renders incorrectly. Fix on appdev — same component.
- ANY in-bundle behavior. The bundle is shared.

If you've cross-deployed the same source twice in a row debugging
the same card, stop and reach for appdev HMR.
```
