## Fix #1 — F-31 cross-codebase propagation gap

**Surface symptom**: Run-27 worker scaffold's NATS-Pattern-A finding did
not reach the apidev codebase-content brief; valkey-no-auth fact (which
cites `${cache_user}`) did.

**Root cause**: `factMentionsAnyConsumedService`
([internal/recipe/consumes_services.go:277-303](internal/recipe/consumes_services.go))
matches only braced env-token references via
`envVarReferencePattern = \$\{([A-Za-z0-9_-]+)\}`. The worker scaffold's
NATS porter_change facts cite `nats://user:pass@host:4222` (literal
example URL) and `connectionString` (alias name) — no `${broker_*}` form.
Predicate doesn't match.

**Two-pronged fix** (defense in depth — codex-validated):

### 1a) Engine predicate broadening (downstream)

Extend `factMentionsAnyConsumedService` to also match unbraced
hostname-prefix shape at word boundaries. Specifically: for each host
H in `consumed`, match `\bH_[A-Za-z]+\b` (hostname-prefix form like
`broker_hostname`, `broker_connectionString`).

NOT matched: bare hostname word `\bH\b` alone (would over-propagate;
"broker" is a common word in tier-decision narration). Alias-only
prose (`connectionString`) NOT matched (too ambiguous, no host anchor).

Code shape:
```go
// New regex compiled once per call (cheap; consumed is small).
// Suffix character class: [A-Za-z0-9_]+ so multi-token aliases like
// hypothetical `broker_connection_string` would also match.
for host := range consumed {
    pat := regexp.MustCompile(`\b` + regexp.QuoteMeta(host) + `_[A-Za-z][A-Za-z0-9_]*\b`)
    if pat.MatchString(field) {
        return true
    }
}
```

Place AFTER the existing braced-match path so braced matches short-circuit
first (faster, more specific).

**Codex revision applied** (2026-05-06): suffix character class widened to
`[A-Za-z0-9_]+` to accommodate any future multi-segment aliases.

**Tests** (`internal/recipe/consumes_services_test.go`):
- `TestFactMentionsAnyConsumedService_UnbracedHostnamePrefix_Matches` —
  fact with `broker_connectionString` in `Why` field, consumed=[broker] →
  true.
- `TestFactMentionsAnyConsumedService_AliasOnly_DoesNotMatch` — fact with
  only `connectionString` in `Why`, consumed=[broker] → false.
- `TestFactMentionsAnyConsumedService_BareHostnameWord_DoesNotMatch` —
  fact with only "the broker is a NATS server" in `Why` → false.
- `TestFactMentionsAnyConsumedService_HostnameSubstring_DoesNotMatch` —
  fact with `broker_chronicle` (hypothetical `chronicle` is not an env
  suffix the platform produces) — actually this IS in shape so does
  match. Test instead: `embroker_hostname` (substring of broker but
  word-boundary fails) → false.
- Existing braced tests still pass.

### 1b) Scaffold fact-authoring atom (upstream)

Extend
[internal/recipe/content/briefs/scaffold/decision_recording_slim.md](internal/recipe/content/briefs/scaffold/decision_recording_slim.md)
with a section after the existing "Skip rule" (line 86):

When a `porter_change` fact describes managed-service wiring (NATS
connection, S3 endpoint, DB credentials), at least one text field
(`why`, `fixApplied`, `surfaceHint`, `evidence`) MUST cite the
`${<host>_*}` env-token form for every managed service the fact

Why: cross-codebase fact propagation
(`CrossCodebaseManagedServiceFacts`) matches on env-token references
to decide which sister facts are relevant to this codebase. A fact
that cites only the alias-name (`connectionString`) or literal URLs
(`nats://user:pass@host:4222`) won't propagate to consumer codebases

Worked example (BAD vs GOOD):

- topic: nats-pattern-a-separate-credentials

# GOOD — env-token cite makes propagation predicate match.
- topic: nats-pattern-a-separate-credentials
  kind: porter_change
  why: |
    Pattern B (single ${broker_connectionString}) crashes at boot —
    nats@2.29 hostPort() IPv6-misidentifies the auto-generated
    password by colon-count. Use Pattern A: ${broker_hostname} +
    ${broker_port} + ${broker_user} + ${broker_password} as

## Fix #2 — Refinement brief size cap + eviction

**Surface symptom**: Run-27 + run-26 hit MCP cap (97,700 chars in run-27;
multiple OOMs in run-26). Refinement sub-agent recovered via file-fallback
but with 30–60s overhead per OOM.

**Root cause**: `BuildRefinementBrief`
([internal/recipe/briefs_refinement.go:58-181](internal/recipe/briefs_refinement.go))
has NO enforced cap (per comment at line 137). Brief accumulates phase
entry + synthesis_workflow + embedded_rubric + stitched-output-pointer +
embedded_parent_baseline + engine_flagged_suspects + filtered facts. For
nestjs-showcase: 143 facts + 3-codebase suspects → 97KB.

**Fix**: Add `RefinementBriefCap = 80 * 1024` constant in
[internal/recipe/briefs.go](internal/recipe/briefs.go) (40% margin under
MCP 25K-token cap, accounting for ~3.5 chars/token average). Restructure
the tail of `BuildRefinementBrief`:

1. Compose all NON-FACT blocks first (header, phase-entry pointer,
   stitched-output-pointer, embedded_parent_baseline,
   engine_flagged_suspects). Measure size.
2. Pre-compute remaining budget: `budget := RefinementBriefCap - b.Len()`.
3. Compose the facts block into a separate `factsBuf strings.Builder`.
   Stream `filteredFacts` MOST-RECENT-FIRST until adding the next fact
   would exceed `budget`. Stop and emit a single elision marker line:
   `> _N facts elided to fit RefinementBriefCap (80 KB); the most recent
   M are included above. Full fact stream is on disk under the run
   output directory._`
4. Append `factsBuf` to `b`.
5. If facts were elided, add `"facts_evicted_for_cap"` to `parts`.

Phase-entry + synthesis_workflow + embedded_rubric + stitched-output-pointer
+ engine_flagged_suspects must NOT be evicted — these are the rubric and
investigation surface. Only facts (the variable-size component) are
elided.

**Codex revision applied** (2026-05-06):
- `BuildRefinementBrief(plan,parent,runDir,facts)` does NOT receive a
  facts.jsonl path. Elision marker is path-free per the spec above
  ("Full fact stream is on disk under the run output directory").
- `build-subagent-prompt` discards `Brief.Parts`. Surfacing the notice
  requires handler work. PRAGMATIC choice: bake the elision marker
  into the brief body itself (visible to the agent) AND add a
  one-line `## Notice` block above the facts: `> Refinement brief
  approached the cap; N facts were elided.` The agent reading the
  brief sees the notice; no Parts-surface plumbing needed. If a
  separate Notice surface becomes necessary later, follow up
  separately.
- Iteration order: most-recent-first per codex (`for i := len(filteredFacts)-1; i >= 0; i-- ...`)
  so newest facts are kept; elision tail is oldest.

**Tests** (`internal/recipe/briefs_refinement_test.go`):
- `TestBuildRefinementBrief_OverCap_TrimsFacts` — synthetic plan with
  200 facts → brief stays under 80KB → parts contains
  `facts_evicted_for_cap` → elision marker present.
- `TestBuildRefinementBrief_UnderCap_NoElision` — small recipe with
  20 facts → no elision, no `facts_evicted_for_cap` in parts.
- `TestBuildRefinementBrief_EvictionKeepsRecentFacts` — 200 facts
  numbered; elision keeps the LAST N (most recent) that fit; oldest
  are dropped.
- `TestBuildRefinementBrief_EvictionPreservesRubricBlocks` — verify
  embedded_rubric / synthesis_workflow / engine_flagged_suspects all
  still appear after eviction.
- `TestBuildRefinementBrief_AtCapBoundary_NoElision` — synthetic plan
  whose composed brief (with all facts) is exactly RefinementBriefCap
  bytes — no elision fires.
- `TestBuildRefinementBrief_OneCharOver_TrimsOneFact` — same plan
  +1 byte over cap → exactly one fact elided.

## Fix #4 — Scaffold preship gate refuses missing `.gitignore`

**Surface symptom**: workerdev shipped without `.gitignore`. node_modules
(242 dirs) + dist/ committed into recipe deliverable.

**Root cause**: scaffold preship_contract atom
([internal/recipe/content/briefs/scaffold/preship_contract.md](internal/recipe/content/briefs/scaffold/preship_contract.md))
teaches what to do but no engine-side gate enforces it. complete-phase
scaffold accepts the codebase without `.gitignore` for runtimes that
need one.

**Codex revision applied** (2026-05-06):
- File glob in original plan was stale. Implementation goes in
  `internal/recipe/gates.go` (existing `CodebaseScaffoldGates()` at
  line 59) — register a new gate function alongside the existing ones.
- `Violation` struct ([surfaces.go:61](internal/recipe/surfaces.go))
  has Code/Path/Message/Severity ONLY; no Recovery field. Two options:
  (a) extend `Violation` with optional `Recovery *Recovery` field, or
  (b) drop the Recovery wire and put the recovery hint in the Message
  text (e.g. `Message: "missing .gitignore — write it via Write tool
  before complete-phase scaffold; standard Node.js content: dist/\n
  node_modules/\n*.tsbuildinfo"`). PRAGMATIC choice: option (b) for
  this fix; defer Violation-Recovery extension to a separate change.
- Role names: actual enum is `RoleAPI`, `RoleWorker`, `RoleFrontend`
  (NOT `RoleBackend`). Verify against `internal/topology/` enum at
  implementation time.
- `gatesForPhase` applies `CodebaseScaffoldGates` to BOTH scaffold and
  feature phases — ensure the gitignore gate is keyed on phase=scaffold
  only, OR is idempotent (passes cleanly when the file exists, which
  it should after scaffold lands it).

**Fix**: Add a new gate in
[internal/recipe/gates.go](internal/recipe/gates.go) registered in the
existing `CodebaseScaffoldGates()` function. Logic:

1. Read each codebase's on-disk `<SourceRoot>/zerops.yaml`.
2. Walk all setups; collect `run.base` and `build.base` runtime
   identifiers.
3. If any base matches `nodejs|python|go|deno|bun|ruby|php|rust|elixir`
   (or any runtime that produces build artifacts in working tree):
   require `<SourceRoot>/.gitignore` to exist AND be non-empty.
4. If absent or empty → return Violation with
   Code=`MISSING_GITIGNORE`, Severity=blocking, Message naming the
   runtime family + a one-line recommended `.gitignore` content for
   that family.

Static-only runtimes (`base: static`, `base: nginx`) skip this gate.

**Tests** (`internal/recipe/gates_test.go`):

- `TestCodebaseScaffoldGate_StaticRuntime_AllowsNoGitignore` — base

- `TestCodebaseScaffoldGate_NodeJSWithGitignore_Passes` — base

## Fix #5 — Scaffold brief: env-wrapper-script ban + env-roll teaching

**Surface symptom**: workerdev shipped `start-dev.sh` that exports
`NATS_HOST/PORT/USER/PASS` from `$broker_*` and runs `npm run start:dev`,
duplicating zerops.yaml `run.envVariables` mapping. Agent invented this
because it SSH'd in before env-roll completed and saw missing env vars.

**Root cause**: scaffold brief atom does not teach env-roll timing
(env vars only appear in container after container restart with new
zerops.yaml) and does not explicitly forbid env-wrapper scripts when
`run.envVariables` already maps the same keys.

**Fix**: Add a section to
[internal/recipe/content/briefs/scaffold/preship_contract.md](internal/recipe/content/briefs/scaffold/preship_contract.md)
or a new atom under `briefs/scaffold/`:

```md
## Env-roll timing — wait for new container before SSH-probing

`run.envVariables` set in zerops.yaml only appear in the container's
environment AFTER the container restarts with the new zerops.yaml.
Sequence:

1. `zerops_deploy` ships the zerops.yaml.
2. Platform stops the old container, starts a new one with the new
   `run.envVariables`.
3. SSH into the new container — env vars now present.

If you SSH in BEFORE step 2 completes, env vars from your new
zerops.yaml will not yet be set. The fix is to wait, NOT to write a
wrapper script that re-exports them. Wrapper scripts that duplicate
`run.envVariables` mapping become dead code as soon as the next deploy
lands.

## Env-wrapper-script ban

Do NOT author a script (`start-dev.sh`, `run.sh`, `entrypoint.sh`,
`bootstrap.sh`, etc.) whose only job is to:

```sh
#!/bin/sh
export NATS_HOST="$broker_hostname"
# ... more exports ...
npm run start:dev
```

When zerops.yaml `run.envVariables` already maps the same keys
(`NATS_HOST: ${broker_hostname}`), the platform sets them on the
container at boot. Your wrapper is dead code. Use the `start:` field
in zerops.yaml directly:

```yaml
run:
  start: npm run start:dev   # NOT: start: sh start-dev.sh
```

For dev-pair carve-out (`zsc noop --silent` + manual SSH workflow),
the env vars ARE set on the noop container — porter SSHing in after
container roll inherits them. No wrapper needed.
```

**Tests**:
- `TestScaffoldPreshipContract_EnvRollTimingSection_Present` —
  atom contains the section.
- `TestScaffoldPreshipContract_EnvWrapperScriptBan_Present` — atom
  contains the ban + worked example.

**No engine code change.** Brief atom edit only. (Optional follow-up:

## Fix #6 — Codebase-content brief: voice-template caveat for known-broken alternatives

**Surface symptom**: workerdev/zerops.yaml:80-83 + workerdev/README.md:163
endorse Pattern B as a swap-in (`Feel free to switch to Pattern B by
replacing these four vars with a single NATS_URL: ${broker_connectionString}`)
even though the worker scaffold's own facts established Pattern B
crashes at boot.

**Root cause**: Codebase-content brief
([internal/recipe/content/briefs/codebase-content/](internal/recipe/content/briefs/codebase-content/))
teaches friendly-authority voice ("Feel free to change", "Configure
this to...") but does not caveat that the friendly-authority template
must NOT be applied to alternatives that scaffold or feature facts
established as broken.

**Fix**: Add a section to
[internal/recipe/content/briefs/codebase-content/synthesis_workflow.md](internal/recipe/content/briefs/codebase-content/synthesis_workflow.md):

```md
## Friendly-authority voice scope — never on broken alternatives

Friendly-authority phrasing ("Feel free to swap", "Configure this to
use", "Bump this when") signals that an alternative path is supported
and porter-controlled. Do NOT apply this voice to alternatives the
scaffold or feature phase recorded as failing.

If a porter_change fact says "Pattern A wires NATS via separate
${broker_hostname}, ${broker_port}, ${broker_user}, ${broker_password}
vars; Pattern B (single ${broker_connectionString}) crashes at boot
because nats@2.29 hostPort() IPv6-misparses the auto-generated
password" — you may NOT author "Feel free to swap to Pattern B" in
any KB / IG / yaml-comment surface. The friendly-authority voice
implies the alternative works; the recipe's own facts established it
does not.

Worked example — yaml comment:

```yaml
# BAD — friendly-authority on a known-broken alternative.
NATS_HOST: ${broker_hostname}
NATS_PORT: ${broker_port}
# Feel free to switch to Pattern B by replacing these with a
# single NATS_URL: ${broker_connectionString}.
NATS_USER: ${broker_user}
NATS_PASS: ${broker_password}

# GOOD — name the alternative as broken with the recipe's own
# evidence, no friendly-authority hedge.
NATS_HOST: ${broker_hostname}
NATS_PORT: ${broker_port}
NATS_USER: ${broker_user}
NATS_PASS: ${broker_password}
# Pattern A (separate vars). Pattern B (${broker_connectionString})
# crashes at boot — nats@2.29 hostPort() IPv6-misparses the auto-
# generated password's `-` characters by colon-count.
```

When unsure whether an alternative is broken: search the recorded
facts (`zerops_recipe action=read-facts`) for the topic before
authoring a "Feel free to" hedge. If a `porter_change` fact in scope
says the alternative fails, the friendly-authority template does not
apply.
```

**Tests**:
- `TestCodebaseContentSynthesis_VoiceScopeCaveat_Present` —
  atom contains the section.
- `TestCodebaseContentSynthesis_BadGoodExamples_BothPresent` —
  worked example shows BAD and GOOD.

**No engine code change.** Brief atom edit only.
