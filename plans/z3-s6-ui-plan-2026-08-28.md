## 0. The finding that reshapes this stream

**`zerops_*` tool result text does not reach the browser.** Deliverable 4 as briefed — "each
parsed from the tool result text (JSON document or the fenced `json zcp-envelope` block)" —
is not implementable client-side today. Measured, not inferred:

| Fact | Where |
|---|---|
| Every activity payload is slimmed before it leaves the server, on **both** the live WS path and the reconnect/history snapshot path | `apps/server/src/orchestration/ActivityPayloadProjection.ts`; called at `ws.ts:1498,1543` (live), `:1607` (reconnect snapshot), `orchestration/http.ts:88` (detail snapshot) |
| For an MCP item, `result` is explicitly dropped and replaced by a summary | `ActivityPayloadProjection.ts:171-181` `MCP_ITEM_KEPT_FIELDS` = `type,id,tool,server,status,arguments,appContext,error,durationMs` — no `result`. The file's own comment: *"notably `result`, which carries the full tool output and dominates wire size on MCP-heavy threads"* |
| The replacement is **the first non-empty line, ≤84 characters** | `summarizeToolTextOutput`, `ActivityPayloadProjection.ts:146-163` |
| For **Claude** the client sees nothing at all — not even the 84-char teaser | server produces `data = {toolName, input, result}` with no `item` (`ClaudeAdapter.ts:2762-2766`); the client only reads `data.item` (`apps/web/src/session-logic.ts:1001-1006`), so `entry.toolData` stays `undefined` |
| `detail` is separately capped at 180 chars and describes the *request*, not the result | `ProviderRuntimeIngestion.ts:210-212` |

So the plan splits deliverable 4's parsing across the wire differently from the brief, and adds
one enabling slice. Everything else in the brief stands.

**What is unaffected:** the lifecycle strip (D3) and most of the map (D2) need no result text at
all — the envelope already carries `services[]` (mode/status/deployed/gitPushState/stage pair),
`workSession.deploys`/`.verifies` (`AttemptInfo`: success, iteration, setup, strategy, reason,
failureClass, summary) and `bootstrap` (route/step/recipeMatch), and it arrives over
`subscribeZeropsLifecycle` already. The topology feed carries the rest.

### Decision D-U1 — one bounded server-side seam, parsing stays client-side

Rejected alternatives first:

- **Parse server-side into typed card payloads.** Would invent a third contract surface, put the
  card vocabulary in the server half's file set (collision), and freeze card shapes before a
  single card has been drawn.
- **Carry cards on the lifecycle feed's `recentTools`.** The join key is right (`ZeropsRecentTool.itemId`
  ⇄ `WorkLogEntry.toolCallId`, `ProviderRuntimeIngestion.ts:812`) but the ring is `ZEROPS_RECENT_TOOLS_LIMIT = 8`
  — the ninth tool call silently un-renders the first eight cards, and scrollback has none. A card
  that disappears from history is worse than one that never existed.

**Taken:** widen the projection for `zerops_*` tools only, carrying the **raw result text**, capped.
The client parses it exactly as the brief specifies. Concretely:

1. `apps/server/src/zerops/zeropsToolResult.ts` — export `readZeropsToolCallData(data)`;
   `readZeropsToolCall(payload)` becomes a two-line wrapper over it. No rule duplicated: the
   shape-driven Claude/Codex dispatch and the tool-name gate (`isZeropsToolName`, `:41-42` — the
   gate is the name, never `itemType`, `:107-116`) are reused verbatim. *This is the server half's
   file — coordinate through main before committing.*
2. New `apps/server/src/zerops/zeropsActivityResult.ts` (pure): `projectZeropsResult(data)` →
   `{toolName, resultText, truncated} | undefined`. Cap `ZEROPS_RESULT_TEXT_LIMIT = 48_000` bytes;
   over the cap the text is **dropped, not sliced** (`{toolName, truncated: true}` with no
   `resultText`) — half a JSON document parses as nothing, and a card that renders from a
   truncated document would render a lie. The client degrades to the generic block, which is the
   behaviour the brief already demands for an unexpected payload.
3. `ActivityPayloadProjection.ts` — one branch in `projectMcpToolCallData` (~4 lines) attaching
   `projectedData.zerops`. Additive; no existing key changes; non-Zerops tools bit-identical.
4. `apps/web/src/session-logic.ts` — one field on `WorkLogEntry` (`zeropsResult?`) and one block
   next to the existing `data.item` read (~6 lines).

Cost on the wire: bounded by the cap, and only on `zerops_*` items — single digits per thread.
Benefit: history works for free (the snapshot path uses the same projection), and the parsing
lives where the brief put it.

**Rebase exposure** is `ActivityPayloadProjection.ts` and `session-logic.ts`, both upstream-hot.
Both touches are single self-contained blocks placed at the end of their function/interface, which
is the cheapest possible conflict to resolve. Logged in `hacks.md`? No — this is a design change,
not a hack; it belongs in `docs/spec-z3.md` when S6 lands.

## 2. Decisions

**D-U2 — presentation logic is exported pure functions; components are dumb.**
`renderToStaticMarkup` cannot click, and the house has no DOM testing library. So every rule worth
a RED test (which §7 phrase the strip shows, which group a service lands in, whether a card can
render this payload) is a pure function in a `*.ts` beside the `.tsx`, tested directly; the
component test only asserts that the output reaches the markup. This is the existing house split
(`ChatHeader.tsx`/`ChatHeader.test.ts`, `MessagesTimeline.logic.ts`), not an invention.

**D-U3 — the strip is a projection of the envelope, never a state machine.**
`stripState(lifecycle, pendingUserInputs)` is total: unknown `phase` falls through to a default
branch using `KNOWN_ZEROPS_PHASES` (the contract ships the const array for exactly this,
`contracts/src/zerops.ts:130-138`). Precedence, highest first: `user-input.requested` pending →
`waiting for you`; a `recentTools` entry with `status:"inProgress"` → that tool's name; else the
phase wording from §7. Brief §6 "Don't": no lifecycle state machine — the envelope is the state.

**D-U4 — every card is a *decoder*, and failure to decode is the normal path.**
Card shape: `decode(resultText) → Payload | undefined`, and `SimpleWorkEntryRow` renders
`PlainWorkEntryRow` on `undefined`. This makes the brief's "degrades to the generic tool block"
testable as one table per card rather than a defensive sprinkle, and makes the two absent-text
cases (over the cap; a pre-S6U-0 server) ordinary rather than special. Decoders read only the
fields they render, so an added zcp field never breaks one.

**D-U5 — cards read the JSON document, and the fence only where zcp uses it.**
Per the server plan §10 and `zeropsEnvelope.ts`, a result whose text parses as a JSON object IS
the carrier — the fence rule is never tried on it. Carriers, measured from `../zcp/internal/tools/`:
JSON-document + top-level `envelope`: `zerops_import` (`import.go:346` `importResponse`),
`zerops_mount` (3 action shapes), `zerops_deploy` (`deployLocalResponse`/`deploySSHResponse`
wrapping `ops.DeployResult`; `strategy=git-push` forks to `GitPushResult`), `zerops_verify`
(`verifyResponse` / `verifyAllResponse`), the bootstrap actions. JSON-document with **no envelope
key at all**: `zerops_discover` (`discover.go:79` returns `ops.DiscoverResult` bare) and
`zerops_subdomain` (`subdomain.go:111`). Prose + fence: `zerops_workflow` status/develop-start/close.
Errors are `ErrorWire` (`internal/tools/errwire.go:21`) and carry **no** envelope by contract.
Each decoder cites its Go struct in a doc-comment.

**D-U6 — the service map is one component with two mounts.**
`ZeropsServiceMap` renders (a) as right-panel kind `"zerops"` in the environment view and (b) as a
section on `/zerops` (deliverable 7). One component, one set of tests. The tab is registered only
when the topology feed reports `available: true`, which satisfies the brief's "`available:false` ⇒
the panel is absent" through the existing `SURFACE_DISABLED_REASONS`/availability machinery rather
than a second rule.

**D-U7 — quick actions prefill, and prove they cannot do anything else.**
`insertTextAtEnd` via `useComposerHandleContext` (the `FileBrowserPanel` precedent), never a
direct call. A lint-shaped unit test asserts the Zerops component tree imports no mutating RPC
(brief §6 "Don't": no mutating Zerops API calls from the client), mirroring how zcp pins its own
"never call X directly" traps.

**D-U8 — `mounted` is zcp's answer, never derived.** `ZeropsService.mounted` comes from zcp's
`mountPath` (server plan §2.1). The UI never infers it from the file tree. Same for `transient`
(the contract's settled allow-list) — no client-side status vocabulary.

### Changed from the plan

- **The projection hook could not live in `projectMcpToolCallData`.** `projectActivityPayload`
  gates that branch on `payload.itemType === "mcp_tool_call"`, and Claude types `zerops_delete`
  as `file_change` — the exact trap `zeropsToolResult.ts:107-116` documents. The hook sits in
  `projectActivityPayload` itself and feeds both return paths.
- **Cards are 3 files, not 16.** One decoder module with a per-tool registry and one component
  rendering a discriminated union, rather than a file per card. Same test surface, far less
  ceremony; the per-card split can happen if a card grows.
- **Slice 7 needed no code.** "Fold the service map into the environment view; keep the S4
  picker page as is" is satisfied by the map living in the environment's right panel. `/zerops`
  stays the picker — it is account-scoped, has no connected environment to draw a map for, and
  belongs to S4.
- **The strip mounts beside `ChatHeader`, not inside it.** It needs the pending-question state,
  which lives in `ChatView`. Threading it in would have meant new props on a component every
  thread renders; as a sibling inside `WorkspacePageHeader` it also never touches S3.3's
  `vcsStackedActions` gate, which the rebase confirmed.
- **The running-tool indicator is on the MAP, not per row.** `ZeropsRecentTool` carries a tool
  name and an `itemId`, never a hostname; per-service attribution would be a guess rendered as
  a fact. Accepted by the owner.
- **`doorbellConnected` arrived mid-stream** and is rendered as `liveness: "live" | "polling"`,
  absent when the feed reports none — three distinct states, none an error.
- **Question-card keyboard rules are an exported pure function.** `renderToStaticMarkup` cannot
  press a key, so the rules are tested directly rather than written and hoped for.

### Known, bounded

- Cards are proven against fixtures built from the Go response structs, not against live
  payloads: the container's z3 unit lacked the container env, so live `zerops_*` calls fail
  auth until the zcp push lands. Each decoder's fixture is replaced with a captured live
  result once one is available, and the test re-run.
- Every card renders from the tool result; a result over the 48 KB cap has no card by design
  and degrades to the generic tool block.
