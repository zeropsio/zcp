## Why (live-verified 2026-08-21; spec `docs/spec-zerops-env-lifecycle.md` §1/§7 state this)

- The Zerops platform changed the SERVICE env (userData) contract: `POST /api/rest/public/service-stack/{id}/user-data` now REQUIRES a boolean body field `sensitive`. Without it the API returns HTTP 400 `{"error":{"code":"invalidUserInput","message":"Invalid user input","meta":[{"code":"invalidUserInput","error":"Invalid user input","metadata":{"sensitive":["field is required"]}}]}}`. This is exactly what users see today from `zerops_env set serviceHostname=…`, `zerops_workflow git-push-setup` (GIT_TOKEN), launch-production token staging and `zcp agent mark-oauth`.
- The pinned zerops-go SDK (`github.com/zeropsio/zerops-go v1.0.20` in `go.mod`; v1.0.21 and upstream main too) cannot send it: `body.UserDataPost` is `{Key types.String; Content types.Text}` (`$(go env GOMODCACHE)/github.com/zeropsio/zerops-go@v1.0.20/dto/input/body/userDataPost.go:16-19`). ZCP's `internal/platform/zerops_env.go:40-56` builds that body → every write 400s. Do NOT bump the SDK (no fix there) and do NOT add a `replace`.
- `ZeropsClient` already keeps an authorized `sdkBase.Environment` in its `env` field for hand-rolled calls the SDK lacks (`internal/platform/zerops.go:27-56`); precedent `internal/platform/zerops_delegation.go:97-131` (URL concat → `sdkBase.Get(ctx, z.env, u)` → decode success / `apiError.Error` → `mapSDKError`). `sdkBase.Post(ctx, e Environment, url string, in interface{}) *Response` exists (`zerops-go@v1.0.20/sdkBase/utils.go:24`). The SDK's generated `PostServiceStackUserData` (`zerops-go@v1.0.20/sdk/PostServiceStackUserData.go:48-77`) decodes `output.Process` on `< 300` and `struct{Error apiError.Error}` + `HttpStatusCode` stamp otherwise — BUT on a malformed error body it returns `errors.New(status + ": " + rawBody)`: do NOT copy that (the body could echo the submitted credential).
- Semantics ZCP keeps: everything ZCP ever wrote at service scope was a masked SECRET, so both write paths now send `sensitive:true` — no behavior change for users; project scope keeps `false` (`CreateProjectEnv(..., false)` unchanged).
- New platform fact affecting the existing delete-then-create upsert: yaml-baked `zerops.yaml run.envVariables` keys now ALSO appear on slim `GET /service-stack/{id}/env` as `type:"USER"` and are read-only — `DELETE /user-data/{id}` on such a record → 400 `{"error":{"code":"userDataDeleteForbidden","message":"Deleting system userData is forbidden."}}`; `POST` of the same key → 400 `userDataDuplicateKey` (unchanged). So `EnvSet`/`EnvDelete` can now hit `userDataDeleteForbidden` where they previously got "not found"/`userDataDuplicateKey` — translate it to the SAME yaml-owned guidance that already exists for `userDataDuplicateKey`.

**Outcome** (observable): `zerops_env set serviceHostname=X KEY=V` creates/updates the service var again (POST carries `sensitive:true`); `git-push-setup` writes `GIT_TOKEN`, launch staging writes `ZCP_LAUNCH_TOKEN`, `zcp agent mark-oauth` writes its flag — all with `sensitive:true`; a yaml-baked key hit by `zerops_env set`/`delete` yields "…owned by zerops.yaml run.envVariables…" guidance instead of a raw API error; a drift-guard test fails the day the SDK gains the field.

## Design (do exactly this)

1. **`platform.Client`** (`internal/platform/client.go:45-50`): `CreateServiceEnvVar(ctx context.Context, serviceID, key, content string, sensitive bool) (*Process, error)`. Doc: creates ONE service userData record; `sensitive` is REQUIRED by the platform (masked for read-only roles, encrypted at rest); hand-rolled because the SDK body lacks the field (see `TestSDKUserDataBody_StillLacksSensitive`); API codes: `userDataDuplicateKey` when the key already exists (incl. a yaml-baked `run.envVariables` key). Rewrite the stale header comment at `client.go:40-43` ("different SDK enums…" → the new model, spec §1).
2. **Real impl** (`internal/platform/zerops_env.go:40-56`): replace the SDK call with `sdkBase.Post(ctx, z.env, "/api/rest/public/service-stack/"+serviceID+"/user-data", userDataPostBody{Key: key, Content: content, Sensitive: sensitive})` where `userDataPostBody` = `struct{ Key string `json:"key"`; Content string `json:"content"`; Sensitive bool `json:"sensitive"` }` (NO `omitempty` on `sensitive` — `false` must be on the wire). Decode: transport error (`sdkResp.Err != nil`) → `mapSDKError(err, "service")`; status `< 300` → decode `output.Process` → `mapProcess`; status `>= 300` → decode `struct{ Error apiError.Error `json:"error"` }`, stamp `HttpStatusCode`, return `mapSDKError(apiErr, "service")` (preserves `APICode`); a DECODE FAILURE on either branch → `NewPlatformError(ErrAPIError, fmt.Sprintf("service env write: malformed %d response", status), "Retry; if it persists the platform API changed — report it")` with the decode error attached via `withCause` and WITHOUT the response body. Mirror `zerops_delegation.go:97-131` for shape (URL, decode, error mapping); add no logging.
3. **Drift guard** (`internal/platform/zerops_env_test.go`): `TestSDKUserDataBody_StillLacksSensitive` — `reflect.TypeOf(body.UserDataPost{})` has no field named `Sensitive`; if it appears, FAIL with "zerops-go now carries Sensitive on UserDataPost — retire the hand-rolled POST in zerops_env.go and use the SDK handler".
