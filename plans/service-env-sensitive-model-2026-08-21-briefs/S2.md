## Why (live-verified 2026-08-21; spec `docs/spec-zerops-env-lifecycle.md` §1/§6/§7 state this)

- Slim `GET /service-stack/{id}/env` now returns only `type: SYSTEM` (intrinsics: hostname, serviceId, projectId, zeropsSubdomain, PATH, ZEROPS_*…) and `type: USER` — for BOTH user-set vars (set via `zerops_env set`, GUI, import `envSecrets`) AND yaml-baked `zerops.yaml run.envVariables` (NEW: they used to be absent from this endpoint; they are read-only there). Legacy `READ_ONLY|EDITABLE|SECRET|INTERNAL|ENV` are gone live. `sensitive` is a separate boolean.
- `GET /app-version/{activeAppVersionId}` `userDataList` carries the yaml-baked `run.envVariables` as `type: "USER"` (was `ENV`; the wire also has `editable:false`, which the pinned SDK `output.AppVersionUserData{Key, Content, Type}` does NOT decode) plus `SYSTEM` intrinsics (incl. `ZEROPS_YAML`). User-set vars NEVER appear in the app-version list (verified on three services, also after the env-change process FINISHED).
- Consequences in ZCP today: `classifyAppVersionUserData` (`internal/platform/zerops_appversion.go:63-77`) maps only legacy enum values → every live item falls to `default → kindIntrinsic` → `GetAppVersionUserData` returns EMPTY with `err == nil` → `ops.AppVersionEnvVars` empty → the yaml-baked layer silently vanishes from discover (`internal/ops/discover.go:365-403`), `ops.ServiceHigherLayers`/`EffectiveServiceEnv` (`internal/ops/env_effective.go:160-200`) and shadow detection. `ops.FetchServiceSecretEnvs` (`internal/ops/lookup.go:39-58`, filter `Type == ServiceEnvSecret`) returns EMPTY → export (`internal/tools/workflow_export.go:205-213`) and launch-production (`internal/tools/launch_bundle_compose.go:84-91`) silently drop the user-set service env from `envSecrets` (GAP0-1 regression). A naive `Type == USER` filter would instead ADMIT yaml-baked keys into `envSecrets` (`internal/ops/bundle/helpers.go:113-150` would emit their KEYS with `REPLACE_ME`) — hence the subtraction.
- No test at any tier writes a SERVICE-scope env against the real API, and the e2e type canary (`e2e/launch_baseline_test.go:49-55,114-126`, `TestLaunchBaseline_*`) still pins the legacy five — that is how the regression shipped.

**Outcome** (observable): `platform.ServiceEnvType` is exactly `USER|SYSTEM`; `ops.AppVersionEnvVars` returns the yaml-baked layer again (USER items, `Sensitive=false`); export/launch carry exactly the user-set vars (never a yaml-baked or SYSTEM key) and fail loudly (error → existing warning) instead of silently when the yaml layer cannot be read; `zerops_discover includeEnvs` lists a yaml-baked key once (tagged `source: zerops.yaml` as today); no stale Type=SECRET prose; one e2e round-trip test proves the live write/read contract and the canary uses the new set.
