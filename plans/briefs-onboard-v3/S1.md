## Part A — onboarding.md rewrite

**Menu block (rendered verbatim — the playbook must say so; adaptation license applies only to transitions and explanations):**

```
> Welcome to Zerops! Zerops builds and runs apps and their supporting
> services, connects them on a private project network, and can expose web
> services at a public URL. I'm an agent that drives it through ZCP.
>
> What would you like to do?
>
> - **Build something** — describe an idea in one line, with a technology if
>   you care ("a weather dashboard in Bun"); I set up the environment from a
>   ready-made recipe and build it with you to a live URL.
> - **Try a ready-made recipe** — a complete working app (Node, Python, PHP,
>   Laravel, Go, Rust, …) running in minutes — and it becomes yours to
>   develop further.
> - **What are Zerops & ZCP?** — a short explanation before we change
>   anything.
>
> Or just tell me what you want, in plain words — that works for everything
> here: "scale the cpu to 4 cores", "show me the logs", "add a Postgres
> database".
```

Keep the existing §2 state-read section (status-first, classify from discover only, no pre-greeting read, `**Continue this project**` joins only once state is known, no mutating directive before the `## 3. Branches` heading).

**Consent sequence for both recipe branches (author exactly this order):**
1. FOOTPRINT CONSENT: before any route commit, name what will be created (dev + stage + database; "the stage service is the one that will serve your public URL"), offer dev-only narrowing (`recipeNarrow="dev-only"`) only on explicit ask, and get a yes. Choosing the menu option is NOT this consent.
2. COMMIT + DERIVE/CONFIRM: `zerops_workflow action="start" workflow="bootstrap" route="recipe" recipeSlug="<slug>"`, then the derive/confirm step per the returned guide.
3. RENEWED CONSENT ON EXISTS: if confirm flips a managed dependency to EXISTS, say plainly that the recipe's boot migration may create tables/write into that existing database, and get a fresh yes before provisioning. In a POPULATED project (existing non-system services), do not propose mixing the scaffold in at all until the person deliberately confirms after this disclosure — offer **Continue this project** first.
4. NARRATE, THEN IMPORT: explain the three concepts (below), then run the blocking `zerops_import` — there is no narration during it.

**The three concepts (author these, anchored to the services just named):**
1. A project is a private network; each service in it runs in its own containers (your app) or is a managed service (your database).
2. Services reach each other by hostname on that private network — the app finds its database as `db`, no addresses or credentials in code.
3. Source becomes a running app through build → deploy → run; the subdomain URL is the public door to the stage service.

**After import (both branches):** poll to ACTIVE; the handoff URL is the STAGE service's subdomain URL — the dev service idles by design (`zsc noop`) and answers 502; never present the dev URL as the app; verify the URL responds before presenting it (per spec-workflows §8 RCO, the close/status payload carries the composed URLs — use those, don't hand-compose).

**Failure ending (author it):** if provisioning or build fails, name exactly which services/processes succeeded and which failed; do NOT claim a URL, do NOT proceed to ownership; offer cleanup of services created by THIS attempt only after an explicit yes (`zerops_delete`, per-service), and NEVER offer to delete or rewrite a pre-existing dependency; surface the recovery the tool reported.

**Branch-specific tails:**
- Build something: after the verified URL, continue into the normal develop loop toward the user's idea (routing rules / guided skill own it).
- Try a ready-made recipe: after the verified URL, offer ownership — wire delivery to the user's own Git repository (`git-push-setup`; GIT_TOKEN is a user-held secret the agent never fabricates) or export the project setup; link `https://app.zerops.io/recipes/<slug>` for the human-readable guide. Do NOT promise recipe-specific takeover content from the corpus.
- What are Zerops & ZCP?: fetch `zerops_knowledge uri="zerops://playbooks/orientation"` once, explain at the person's altitude, mutate nothing, close by re-offering the two active options + the plain-words escape.
- Freeform bring lane (behind the escape line): source in this workspace or a Git repository the workspace can access; laptop-only code → "push it to a Git repository and I'll take it from there"; never fabricate credentials.
- End-of-flow tip after any completed provision/build: plain words drive everything from here (scaling, logs, env, domains).
